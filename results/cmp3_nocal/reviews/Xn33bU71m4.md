## Summary

This paper systematically evaluates nine open-source mid-sized LLMs (12–16B parameters) on two core reverse engineering tasks — name recovery and type inference — from stripped binaries. It constructs a multi-architecture (x86-64, x86-32, ARM, MIPS), multi-optimization-level (O0–O3) dataset of 40,000 unique functions and finds that all evaluated models perform poorly (F1 < 0.1 on most settings), with fine-tuning yielding only modest, inconsistent improvements. The motivation — that the field lacks principled model selection — is sound, and the dataset is a reasonable foundation.

## Strengths

1. **Clear task formulation that extends prior scope (§2).** The paper cleanly separates name recovery and type inference, and extends name recovery beyond predicting only the function name to predicting *all* callee function names appearing inside a function body — a more realistic and challenging formulation than prior work.

2. **Systematic multi-architecture, multi-optimization dataset (§4.1).** The dataset spans four architectures and four optimization levels with deduplication, yielding 40,000 unique functions. This provides a reasonable foundation for comparative evaluation.

3. **Identifies a genuine gap in the literature (§2).** The observation that prior reverse engineering work selects LLMs without justification (e.g., CodeLlama-34B vs. StarCoder-3B with no rationale) is a concrete, useful critique that motivates systematic benchmarking.

## Weaknesses

### Fatal
None.

### Major

1. **Abstract contains an unsupported quantitative claim.** The abstract states: "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37" (line 19). This value appears *nowhere* in any table or result in the paper. DeepSeek-R1's best fine-tuned F1 across all reported results is 0.17 (variable name recovery, O0, Table 3); the highest F1 achieved by *any* model is 0.33 (Qwen2.5/WizardCoder/Phi4, same table). The 0.37 claim is not merely exaggerated — it is unsupported by the evidence. While the paper's core finding (LLMs perform poorly) holds, this specific error in the headline number erodes confidence and must be corrected.

2. **Evaluation pipeline relies on an uncalibrated auxiliary LLM (§3.2).** Model outputs are normalized by "an auxiliary LLM specialized in formatting" that is never named, specified, prompted, or tested for accuracy. The auxiliary model's prompt template, error rate, and size are not reported. This is critical because: (a) errors or biases in the auxiliary LLM could dominate the near-zero scores of the target models; (b) without an ablation (e.g., comparing against rule-based parsing for a subset), the measurement instrument is a black box. The results conflate the target model's reverse engineering ability with the auxiliary model's parsing accuracy.

3. **Fine-tuning protocol is critically underspecified (§3.3, §4.3).** Only "LoRA" and "200 steps" are reported. No LoRA rank, alpha, dropout, learning rate, batch size, optimizer, scheduler, or number of epochs is provided. With a training set of 160,000 functions and only 200 steps mentioned, the reader cannot determine whether models were trained to convergence or how much data was seen. This makes the fine-tuning results non-reproducible and raises the question of whether the observed modest gains reflect undertrained models rather than genuine limitations.

### Minor

4. **No non-LLM baselines for comparison.** The paper evaluates only LLMs and does not compare against pre-LLM neural approaches (e.g., SYMLM, Debin). Without such a baseline, the reader cannot tell whether the near-zero scores reflect intrinsic task difficulty or genuine LLM limitations. Adding even one traditional baseline would significantly strengthen the negative result.

5. **No prompt ablation or optimization.** A single, fixed prompt template is used. The paper acknowledges that format compliance is a major issue (Finding 8), yet does not explore whether different prompts would yield different rankings. This conflates reverse engineering ability with instruction-following ability.

6. **No statistical variance reported.** All results appear to be single-run. Given stochasticity in LLM generation, the comparative claims would be more reliable with error bars or multiple runs.

7. **CodeWordNet analysis (§4.4) is a self-validating point presented as a finding.** Showing that removing the CodeWordNet semantic similarity metric lowers F1 scores merely validates that the metric does what it was designed to do. This is a property of the evaluation metric, not an empirical finding about LLM capabilities.

8. **Minor inconsistency in model count.** The text says "We support eight mainstream code LLMs" (§4.2), but Table 1 lists nine models.
