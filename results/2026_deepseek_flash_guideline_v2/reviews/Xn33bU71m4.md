## Summary

This paper evaluates nine open-source mid-sized LLMs on two reverse engineering tasks — name recovery (function and variable) and type inference — using a 40,000-function dataset spanning four architectures (x86-64, x86-32, ARM, MIPS) at four optimization levels. Models are tested in both zero-shot and LoRA-fine-tuned settings. The core finding is that all LLMs perform poorly across the board (most F1 < 0.1), and fine-tuning yields inconsistent, often marginal gains. The paper fills a genuine gap by providing the first systematic cross-model comparison in this domain.

## Strengths

- **First systematic cross-model comparison on a unified RE benchmark.** The paper evaluates nine LLMs on the same 40,000-function dataset with identical prompts, evaluation pipeline, and LoRA fine-tuning — addressing the explicit gap identified in Section 2 (lines 87–91) that prior work (SYMGEN, ReSYM) selects models without justification. Tables 2–4 provide the head-to-head data that was missing.

- **Quantifies that CodeWordNet is essential for fair evaluation.** Figure 1 shows that removing CodeWordNet causes F1 scores to drop by roughly 3× (e.g., Qwen3 at O0: ~0.25 with CodeWordNet → ~0.08 without). While CodeWordNet itself is not new, this is the first systematic demonstration of its impact across multiple LLMs and optimization settings.

- **Multi-decompiler real-world firmware evaluation across all nine models.** Table 6 evaluates every model on real firmware using both Ghidra and IDA Pro, revealing that IDA Pro outputs yield consistently higher F1 scores. This is a concrete, actionable finding for practitioners.

- **Fine-tuning time sensitivity with quantified template impact.** Table 7 and Finding 7 show that prompt template design can cause up to 4× variation in fine-tuning time (DeepSeek-V2: 186,720s vs. Phi4: 33,120s), and the paper validates the mechanism by modifying CodeLlama's template.

## Weaknesses

### Fatal
None.

### Major

- **Unsupported F1=0.37 claim in the introduction (Section 1, line 19).** The introduction states: "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." No F1 score of 0.37 appears in any table or figure in the paper. The highest DeepSeek-R1 score is 0.17 (variable name recovery at O0, Table 3), and the highest overall score across any model is 0.33 (WizardCoder/Qwen2.5/Phi4 at variable name recovery O0). This is a direct factual error in a headline quantitative claim. While removing the sentence would suffice (the paper's core negative finding does not hinge on it), its presence undermines trust in the paper's reporting.

- **Discrepancy between Table 2 and Figure 1 for the same metric.** Figure 1 reports function name recovery F1 scores (with CodeWordNet) of ~0.15–0.25 for CodeLlama, Llama2, DeepSeek-V2, and Qwen3 on x86-64. Table 2 — which evaluates function name recovery on the same architecture — shows these same models scoring only 0.01–0.06. If both use CodeWordNet (as Section 3.4 states), the numbers should be compatible. The paper does not explain this ~3–5× discrepancy, making it unclear which numbers are correct or what experimental conditions differ.

### Minor

- **F1 metric-to-CodeWordNet mapping is underspecified (Section 3.4, line 133).** The paper states that CodeWordNet computes "semantic distances between sub-names" and that "the inferred name could obtain partial scores." However, the standard F1 formulation requires binary (or near-binary) classification of each prediction. How partial semantic similarity scores map to precision/recall counts is never defined. A concrete example (ground truth, model output, and the resulting F1 calculation) would resolve the ambiguity.

- **Auxiliary LLM for response extraction is neither identified nor controlled (Section 3.2, line 107).** The paper uses an auxiliary LLM to post-process model outputs into a consistent format but does not name the model, state its size, or validate that it only reformats without altering content. This introduces a confound: if the auxiliary model is strong, it could be doing more than formatting; if weak, it could miss correct predictions. A control experiment (comparing F1 with vs. without the auxiliary model on a subset) would address this.

- **Fine-tuning hyperparameters are not reported (Section 3.3).** The paper reports "200 steps" and uses LoRA, but does not specify batch size, learning rate, LoRA rank, target modules, or number of epochs. Without these details, it is impossible to assess whether the fine-tuning was adequate, and the finding that fine-tuning sometimes *decreases* performance (e.g., DeepSeek-V2 from 0.10 to 0.05 at O1) cannot be properly interpreted.

- **No statistical testing or confidence intervals.** With 9 models × 4 architectures × 4 optimization levels × 2 conditions, the number of comparisons is large. No confidence intervals, standard deviations, or significance tests are reported. Many observed differences (e.g., 0.04 vs. 0.05) could be noise.

### Trivial

- Table 5's caption should explicitly note that "0.00" values are rounded at the third decimal place, rather than relying on the body text (line 306) to clarify this.

## Nice-to-Haves

- Comparison against existing specialized RE systems (SYMGEN, ReSYM) would clarify whether the negative conclusion applies to general-purpose LLMs specifically, or to the state of the art broadly.
- A discussion of data contamination (GNU software is widely used in LLM pre-training corpora) would strengthen the negative findings.

## Suggestions
