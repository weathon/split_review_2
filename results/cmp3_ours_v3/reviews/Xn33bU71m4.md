## Summary

This paper evaluates nine open-source LLMs (12B–16B parameters) on two reverse engineering tasks — name recovery (function and variable names) and type inference — using decompiled code and assembly from stripped binaries. The study covers 4 architectures (x86-64, x86-32, ARM, MIPS), 4 optimization levels (O0–O3), and both zero-shot and fine-tuned settings. No new method is proposed; the contribution is the evaluation itself. The headline finding is that all models perform poorly (most F1 scores < 0.1), with fine-tuning providing inconsistent and generally modest gains.

## Strengths

1. **Multi-dimensional evaluation design.** 9 models × 4 architectures × 4 optimization levels × 2 input representations (decompiled code + assembly) × 2 settings (zero-shot + fine-tuned). This breadth exceeds any single prior study in this domain and gives the evaluation genuine coverage.

2. **CodeWordNet-based evaluation for name recovery.** Using semantic distance (Section 3.4) rather than exact string match is the right methodological choice for names, since developers may use synonyms. The ablation in Figure 1 confirms that strict matching would unfairly penalize semantically correct predictions.

3. **Real-world firmware evaluation with two decompilers.** Table 6 tests on real firmware using both Ghidra and IDA Pro, adding ecological validity beyond synthetic datasets.

4. **Honest reporting of negative results.** Findings 2 and 3 (type inference ≤0.1 F1, assembly code → 0.0 F1) are presented without hype. In a field that often suppresses negative results, this transparency is valuable.

## Weaknesses

### Major

1. **Unexplained discrepancy between Table 2 and Figure 1.** Table 2 reports function name recovery F1 scores (x86-64, original models) of 0.00–0.06. Figure 1, measuring the same task ("F1 Score on Function Name Recovery via Decompiled Code"), reports values of ~0.08–0.25 for the same models — higher by a factor of 3–5×. For example, CodeLlama O0 is 0.04 in Table 2 but ~0.15 in Figure 1; Qwen3 O0 is 0.05 in Table 2 but ~0.25 in Figure 1. The paper does not explain whether these use different data subsets, different prompts, or different metric configurations. Since both are labeled as F1 on function name recovery via decompiled code on x86-64, this inconsistency undermines confidence in the evaluation pipeline. **This is the single most important issue to resolve.**

2. **Fine-tuning hyperparameters are critically underspecified for a paper that claims reproducibility.** The fine-tuning section (lines 111–125) mentions LoRA but gives no LoRA rank, alpha, target modules, learning rate, batch size, number of epochs, optimizer, or convergence criterion. Only "200 steps" is provided (Table 7). For a paper that aims to "establish fair and reproducible benchmarks" (line 91), this is insufficient. Without these details, the fine-tuning results cannot be reproduced or meaningfully compared across models.

### Minor

3. **Headline F1=0.37 claim in the introduction is not traceable in the main body.** Line 19 states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." The highest DeepSeek-R1 F1 score in the main tables is 0.17 (Table 3, variable name recovery, O0). The 0.37 result may appear in the appendix (which was stripped by parsing), but a headline claim this central should be clearly referenced in the main body — the paper should state which task, architecture, and optimization level this corresponds to.

4. **No non-LLM baselines.** The paper cites specialized non-LLM methods (SYMLM for function names, VARBERT for variable names, Debin for types) but does not compare against them. Without baselines, the reader cannot calibrate whether F1=0.33 (best fine-tuned variable name recovery) is meaningful or poor relative to existing specialized tools. This limits the paper's ability to deliver on its goal of providing "evidence-driven insights."

5. **Auxiliary LLM for response extraction is never identified.** Line 107 describes using "an auxiliary LLM to post process outputs" but never specifies which model. Since this auxiliary model's formatting quality directly affects all reported metrics, this is a reproducibility gap.

6. **No project-level train/test split for fine-tuning.** The training and test sets (160k/40k functions) are both drawn from the same set of GNU software projects (lines 139, 186), but the paper does not specify whether the same source projects appear in both splits. If they do, fine-tuned gains could reflect project-specific memorization rather than genuine reverse-engineering capability.

7. **No variance or significance reporting.** F1 scores are reported as point estimates with no confidence intervals, standard deviations, or error bars. With many scores near zero, small variances could make rankings meaningless.

### Trivial

- The model is referred to as "DeepSeek-R1" throughout the text but listed as "Deepseek-R1-Qwen" (14B) in Table 1. The 14B model is the distilled variant (DeepSeek-R1-Distill-Qwen), not the 671B full model. Table 1's label is more precise.
- No link to code/data repository is provided (line 428 mentions "executing the identical scripts" without a URL).
- The exact prompt template is referenced by an external URL (line 103) rather than quoted in the paper.

## Nice-to-Haves

- Adding specialized non-LLM baselines (e.g., SYMLM for function names, VARBERT for variable names, Debin for types) would provide essential context for interpreting the F1 scores.
- Reporting statistical significance or confidence intervals for the main results.
- Disentangling whether fine-tuning gains come from genuine task learning or project-specific memorization via project-level train/test splitting.

## Suggestions

2. **Provide full fine-tuning hyperparameters** (LoRA rank, alpha, learning rate, batch size, optimizer, number of epochs) in the main paper or appendix.

3. **Trace the headline F1=0.37 claim** to its corresponding task/architecture/setting in the main body, or remove/rephrase the claim if it only appears in the appendix.
