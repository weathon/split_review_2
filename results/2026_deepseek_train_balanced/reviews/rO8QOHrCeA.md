## Summary

This paper proposes GIFT4Code, an instruction fine-tuning method for code LLMs that uses synthetic data generated by the model itself, augmented with I/O specifications derived from program execution. The idea is to generate synthetic intents and code solutions, execute the code, extract I/O specifications (type descriptions, concrete I/O examples, or natural language summaries) from execution traces, and then fine-tune the LLM on intents inlined with those specifications. Evaluation is on ARCADE and DS-1000.

## Strengths

- **Execution-derived I/O specifications as a training signal**: The paper is the first to extract I/O specifications at multiple abstraction levels (TypeDesc, I/O Examples, I/O Summary) from program execution states and use them as in-line specification constraints during instruction tuning (Section 3.2). Prior synthetic-data instruction tuning (SELF-INSTRUCT, Alpaca) uses only surface-form heuristics; this work operationalizes execution feedback as a structured learning signal, which is a concrete and well-motivated contribution.

- **Execution rate vs. pass@k diagnostic analysis (Section 4.4, Figure 3)**: The paper decomposes errors into schema errors vs. syntax errors and shows that the baseline has high executability but low pass@k (executable but wrong), few-shot prompting with I/O specs reduces schema errors but introduces syntax errors, and GIFT4Code combines the strengths. This diagnostic goes beyond reporting aggregate scores and directly supports the paper's motivating claim about "executable but incorrect" code.

- **Genuine quantitative gains on the primary (ARCADE) benchmark**: Table 2 shows substantial improvements over the base model in both zero-shot and few-shot settings across multiple I/O specification types. The up-to-10%-absolute improvement from synthetic fine-tuning alone is notable, and further gains from I/O specifications are reported.

## Weaknesses

### Fatal
None.

### Major

- **StarCoder / WizardCoder comparison invoked but actual numbers not reported.** The paper states "We also evaluated Starcoder and its instruction tuned variant WizardCoder on ARCADE and DS-1000" (line 126) and claims GIFT4Code is more effective, but no actual scores for these baselines appear anywhere in the text or Table 2. The reader cannot verify the claimed advantage over existing instruction-tuned code models. This is a critical omission: a method paper on two established benchmarks needs at least one external reference point to calibrate its results.

- **DS-1000 evaluation uses a non-standard train/test split that invalidates comparison with the literature.** The paper holds out 500 of the 1000 DS-1000 problems for training and evaluates on the remaining ~500 (line 94). This makes results incomparable with every published result on DS-1000, which uses the full benchmark. Moreover, since both splits are drawn from the same Stack Overflow source, there is a risk of similar problems appearing in train and test, potentially inflating results. The paper does not discuss or control for this. The DS-1000 experiments therefore provide significantly weaker evidence than they otherwise would.

### Minor

- **Marginal contribution of I/O specifications over synthetic data alone is not cleanly quantified in prose.** The paper's framing centers I/O specifications as the key innovation, yet the introduction and results admit that synthetic data without I/O specs already yields substantial gains (up to 10% absolute on ARCADE). While Table 2 does contain both "no spec" and specification-augmented conditions, the text describes the added benefit only qualitatively as "significantly better results" (line 124). The paper would be stronger by explicitly stating the marginal improvement (e.g., "I/O specifications add X absolute points on top of the synthetic-fine-tuning baseline"). This is easily fixable but matters for the paper's narrative precision.

- **Test-time I/O specification protocol simulates specs derived from the correct answer, not from genuine user uncertainty.** At test time, I/O summaries are generated by a generalist LLM from the ground-truth code solution (line 105), with variable states removed to simulate "noise." As the paper acknowledges, this is common practice in program synthesis (Balog et al., 2016). However, the stated motivation is that "users might give noisy I/O specifications" — and the noise from an LLM summarizing a correct answer is structurally different from the noise of a user with partial or incorrect understanding. This limits what the evaluation tells us about the target deployment scenario. The paper's acknowledgment mitigates this, but the gap remains.

- **The base code LLM (62B) and the generalist LLM ("competitive with GPT-4") are not named.** This is a basic reproducibility concern. While the model identity may have been in a footnote stripped during parsing, it is absent from the main text and should be stated explicitly. The 62B parameter count narrows the set of candidates (e.g., CodeLlama-70B, Falcon-180B is too large, etc.) but does not uniquely identify the model.

### Trivial

- **"API diversity filter" invoked but never defined** (Section 3.1, line 57 / line 90). The paper says data was filtered "based on executability and API diversity" but never explains what the API diversity criterion is or how it was applied. Its effect on the ~7× reduction from ~135K executable candidates to ~20K training examples cannot be assessed.
- **"Python data" mixed into the training mixture to prevent regression is never described** (line 92) — its source, size, and content are opaque.
- **Standard error claim (<0.5% for all table cells, line 114)** is presented without explanation of how it was computed, which is noteworthy for pass@k metrics with only 50 samples.
