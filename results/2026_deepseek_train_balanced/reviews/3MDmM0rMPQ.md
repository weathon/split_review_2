## Summary

This paper proposes Inverse Prompt Engineering (IPE), a framework for building task-specific LLM safety guardrails from prompt engineering data (the final system prompt and the development set of test inputs). IPE formalizes this as an inverse problem grounded in Inverse Reward Design (IRD), training small reward models via a contrastive objective that distinguishes completions from the chosen prompt vs. synthetic alternative prompts. The method is evaluated on a travel assistant chatbot against GPTFuzz and GCG attacks, and on the TensorTrust benchmark where it improves defense robustness by 93%. The core idea — repurposing prompt engineering artifacts for task-specific safety — is novel and the IRD formalization is principled.

## Strengths

- **Principled formulation via Inverse Reward Design (Section 3).** IPE models prompt engineering as a Boltzmann-optimal decision process (Eq. 1) and casts safety guardrail construction as an inverse problem, providing a clean mathematical foundation. The sampling-based approximation of the normalizing constant (Eq. 3) is a practical contribution that makes the IRD framework tractable for LLM prompts.

- **Evaluation against dynamic adversaries rather than static datasets only (Section 4.2.1).** The paper evaluates IPE against GPTFuzz (LLM-powered genetic algorithm) and GCG (gradient-based optimization), explicitly noting this differs from prior guardrail evaluations (Inan et al., 2023; Han et al., 2024) that only test static datasets. This is a genuine methodological improvement that reveals meaningful robustness differences — e.g., LlamaGuard2 and Perspective API, which perform well on static benchmarks, reach nearly 100% ASR under dynamic attacks.

- **TensorTrust evaluation on real-world data collected without knowledge of IPE (Section 4.3).** The 93% reduction in average attack success rate on TensorTrust is compelling because the data (126K+ attacks, 46K defenses) was generated by online game players with no knowledge of the method. This directly validates the paper's central thesis: robust task-specific guardrails can be derived from prompt engineering data already on hand.

- **Task-specific attack evaluation (Section 4.2.1).** The paper proactively constructs a "task-specific GPTFuzz variant" that incorporates knowledge of the travel assistant prompt, honestly reporting that IPE's ASR rises from 6% to 22% under these targeted attacks — still well below the best baseline (44%). This demonstrates genuine safety-reasoning capability beyond simple domain rejection.

- **Computational efficiency (Section 4.1).** Training ensembles of 8 LoRA-adapted GPT-2 reward models takes ~35 minutes on an H100 GPU, making the approach practical for real-world deployment without requiring large-scale data collection or annotation.

## Weaknesses

### Major

- **Unsupported quantitative claims in the abstract and introduction.** The abstract and line 22 claim IPE "reducing successful attacks by 98% compared to the popular OpenAI moderation API" on human-written jailbreaks and "generalizes well to distribution shifts in benign user inputs." The introduction's contribution list (line 28) states IPE "improves robustness to both human-written and automated adversarial attacks." **No experiment evaluating against human-written jailbreaks or distribution-shift robustness appears anywhere in the body.** The 98% figure has no corresponding dataset, baseline comparison, or methodology described. The Related Work section (line 39) states "We evaluate IPE against all three methods" (human-written, LLM-assisted, gradient-based), but only two of these (GPTFuzz, GCG) have experimental sections. A paper's most prominent quantitative claims must be traceable to experiments in the text. These claims either need to be removed or substantiated.

- **Structural asymmetry in the main comparison advantages IPE.** IPE operates as an *allow-list*: it learns to accept only content consistent with a specific task (travel assistance). The baselines (OpenAI moderation, Perspective API, LlamaGuard2) are general-purpose *deny-lists* that must detect harmfulness across any domain. The evaluation uses 200 harmful queries from HarmBench's standard subset — which are *not* travel-specific. IPE can reject these simply because they are out-of-domain, not because it detects harmfulness. The paper's framing of IPE's 6% ASR vs. OpenAI moderation's 50% ASR as evidence of superior robustness conflates scope-enforcement with safety-reasoning. The task-specific GPTFuzz variant partially mitigates this (IPE's ASR rises to 22%), but the main comparison remains structurally confounded. A fairer evaluation would separately report in-domain vs. out-of-domain harmful query performance, or adapt baselines to the task-specific setting (e.g., fine-tuning on the same development data).

### Minor

- **No ablation study isolating key design choices.** IPE involves several unexamined decisions: the number of synthetic alternative prompts (512), the specific contrastive objective, the choice of Llama2-13B-Chat for generation, the ensemble size (8 GPT-2 models), and the uncertainty-weighting scheme. None are systematically ablated. The paper mentions "using an ensemble of small models worked better than using one larger model" (Section 3.3) but provides no comparison. The uncertainty estimation section (Table 2) compares architectures on AUC, but these results are on a different metric from the main ASR evaluations, and the connection is unclear. Without ablations, it is difficult to attribute the observed performance to the specific IPE framework vs. simpler alternatives (e.g., embedding-based task classifiers).

- **GCG transfer robustness experiment is too narrow to support the conclusions drawn.** The transfer test (Section 4.2.1) trains only two IPE guardrails with different random seeds and finds zero transfer. This is a minimal test — it does not vary training data, model architecture, ensemble composition, or attack budget. The paper's conclusion that IPE "would likely be robust against GCG transfer attacks" overstates what this narrow experiment can support.

- **Main ASR results reported without statistical significance or confidence intervals.** The GPTFuzz and GCG results (Figure 3) are presented as point estimates without variance. The uncertainty estimation section reports standard deviations for AUC (0.402%), but the paper's central experimental claims (ASR comparisons) lack this basic statistical information.

- **Missing development set description for the travel assistant.** The development set of inputs $\mathcal{X}$ is never characterized: how many inputs, what travel-related domains they cover, how they were collected. This is a basic reproducibility gap.

### Trivial

- **No Conclusions section.** The paper ends abruptly with a Discussion paragraph embedded in Section 4.3. A brief conclusions section summarizing findings and limitations would improve the paper.

## Nice-to-Haves

- Evaluate or remove the human-written jailbreak and distribution-shift claims from the abstract/intro.
- Include confidence intervals or standard deviations for the main ASR comparisons (GPTFuzz, GCG).
- Ablate the number of synthetic prompts, the contrastive objective against a simpler classifier, and the ensemble size.
- Describe the travel assistant development set composition.

## Suggestions

1. Remove the unsupported 98% and distribution-shift claims from the abstract and introduction, or add the corresponding experiments. The paper's contributions are already interesting without these overclaims.
2. Restructure the GPTFuzz evaluation to separately report ASR for in-domain harmful queries (travel-related jailbreaks) vs. out-of-domain harmful queries, to disentangle scope-enforcement from safety-reasoning.
3. Add a basic ablation: compare IPE against a simple embedding-similarity baseline that rejects inputs far from the development set in embedding space. This would clarify whether the IPE likelihood provides meaningful value beyond domain detection.
4. Expand the GCG transfer experiment to vary training data, not just random seeds, and test transfer across different development sets.
5. Add a Conclusions section that summarizes findings, limitations, and future work.
