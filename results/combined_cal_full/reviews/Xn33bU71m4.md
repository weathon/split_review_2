## Summary

This paper systematically benchmarks 9 open-source LLMs (7–16B parameters) on two reverse engineering tasks — name recovery (function and variable names) and type inference from stripped binaries — across 4 CPU architectures and 4 optimization levels, using both decompiled code and assembly input. It finds that all models perform poorly (near-zero F1 zero-shot, ≤0.33 fine-tuned on variable name recovery) and shows that fine-tuning helps but inconsistently.

## Strengths

- **Identifies a genuine gap in the literature (Section 2, lines 82–91):** Model selection for LLM-based reverse engineering has been poorly motivated in prior work (SYMGEN picks CodeLlama-34B arbitrarily, RESYM picks StarCoder-3B without justification), and the field lacks a systematic comparison. The need for principled benchmarking in this area is real and well-articulated.

- **The evaluation scope is unusually broad:** 9 models × 4 architectures (x86-64, x86-32, ARM, MIPS) × 4 optimization levels × 2 input formats (decompiled and assembly) × 2 tasks (name recovery and type inference). This is more comprehensive than any single prior study, and the inclusion of assembly alongside decompiled code is a useful contrast.

- **The automated output-normalization pipeline (Section 3.2) addresses a practical obstacle:** LLMs generate heterogeneous response formats that make large-scale evaluation difficult. Using an auxiliary LLM to standardize outputs is a sensible engineering solution for a real operational problem.

- **The CodeWordNet-based evaluation for name recovery (Section 3.4) is methodologically appropriate:** Exact string matching would incorrectly penalize valid synonyms (e.g., "init" vs. "initialize"). The ablation in Figure 1 cleanly quantifies the difference between semantic matching and exact string matching, confirming that low scores are not an artifact of overly strict evaluation.

## Weaknesses

### Fatal
None.

### Major

- **The auxiliary LLM used for response normalization (Section 3.2, lines 95–107) is never identified.** The paper neither names which model serves this role nor validates its formatting accuracy. Since every model's raw output passes through this pipeline before evaluation, errors in the auxiliary model could systematically bias results (e.g., if it struggles more with verbose outputs like DeepSeek-R1's chain-of-thought), and the pipeline cannot be independently reproduced. This is a reproducibility gap for a paper that claims reproducibility (line 428).

- **No variance or statistical significance is reported for any result.** All tables (Tables 2–6) present single point-estimates. The paper acknowledges LLM stochasticity (line 428: "The number will be similar, but not identical, due to randomness"), yet draws qualitative conclusions from small F1 differences — Finding 4 (model size vs. quality) rests on 0.01–0.02 gaps that could easily be noise. Without confidence intervals or multiple runs, finer-grained comparative claims are not statistically grounded.

### Minor

- **The introduction claims an unsupported headline number (line 19):** "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." The main x86-64 tables (Tables 2–4) show a maximum of 0.17 for this model. Results for other architectures are deferred to the appendix, but the main text does not state which architecture/task yields 0.37, creating an inconsistency in the paper's headline quantitative claim. The data may exist in the appendix, but the main text must cross-reference it clearly.

- **LoRA hyperparameters (rank, alpha, target modules, learning rate) are not reported (Section 3.3).** These are standard architectural choices that affect fine-tuning behavior and are needed for reproducibility.

- **Fine-tuning uses only 200 gradient steps (Table 7, line 394).** For a dataset of 160,000 samples, this represents well under one epoch. The paper does not check convergence or quantify sensitivity to training duration — important because fine-tuning sometimes degrades performance (Finding 1), and under-training could be a contributing factor.

- **Dataset sources are described only as "diverse open-source projects, mostly from GNU software" (line 139).** No specific projects are listed. This limits assessment of domain coverage and generalizability.

- **The training/test split is described as "independent" (line 186), but the paper does not specify whether de-duplication is done at the project level.** If functions from the same source file or project appear in both training and test sets, cross-project leakage could inflate fine-tuning results.
