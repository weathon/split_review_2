## Summary

This paper argues that pixel-level reconstruction metrics (PSNR, SSIM) used to evaluate frequency-domain privacy-preserving face recognition (PPFR) systems fail to capture identity-level leakage. The authors propose FaceLinkGen, a distillation-based attack that extracts identity embeddings from protected templates and uses them for linkage (matching) and face regeneration (via Arc2Face). Evaluated on three recent PPFR systems (PartialFace, MinusFace, FracFace), FaceLinkGen achieves >98.5% matching accuracy and >96% regeneration success. Critically, the constrained-attack variant (Section 6)—which assumes no oracle access, only ~30 validation pairs and a generic high-pass filter proxy—still achieves >92% matching and >94% regeneration success, showing the vulnerability is intrinsic to the representation, not an artifact of strong attacker assumptions.

## Strengths

1. **Demonstrates that pixel-level metrics are insufficient for identity privacy.** The paper shows that three recent PPFR systems achieve high protection under PSNR/SSIM yet are vulnerable to FaceLinkGen, which yields >98.5% matching accuracy and >96% regeneration success (Tables 2, 3, 4). Table 6 directly compares FracFace's own frequency-channel "protection rate" metric against FaceLinkGen's actual identity recovery, exposing a critical gap between claimed protection and true privacy.

2. **Constrained-attack results show the vulnerability is intrinsic.** With only 800 training images (50 seconds of training), FaceLinkGen achieves 97.0% regeneration pass rate and 99.5% linkage accuracy (Section 5.1). More importantly, the constrained adversary (Section 6)—no oracle access, no knowledge of PPFR internals, only a generic high-pass proxy—still achieves >92% matching and >94% regeneration on Face++. This is the strongest evidence in the paper because it rules out the critique that the results depend on unrealistic attacker capabilities.

3. **Cross-validated with independent commercial APIs.** Regeneration success is verified using both Face++ and Amazon face comparison APIs (Tables 2 and 5), avoiding reliance on the same embedding model used in the attack. This significantly strengthens ecological validity.

4. **Extends beyond frequency-domain PPFR.** The same distillation framework generalizes to a non-frequency-domain method (CanFG) and an adversarial de-identification method (TIP-IM), achieving near-perfect linkage accuracy (Table 8). Soft biometrics (age, gender, race) remain recoverable at near-original accuracy (Table 9), further underscoring the privacy risk.

## Weaknesses

### Fatal
None.

### Major

None that are truly fatal. The weaknesses below are addressable in revision.

### Minor

1. **Threat model framing overstates the oracle-access case.** The paper's main results are obtained under an oracle-access adversary (service provider who can query the conversion process arbitrarily). The paper argues this is the correct threat model per Erkin et al. (2009) and addresses alternative deployments in Section 6 with the constrained attack. This argument is reasonable and the constrained attack validates the findings under weaker assumptions. However, the paper frames its primary contribution around the oracle-access scenario, and the argument that a locally running model "can be reverse-engineered" is stated without a citation demonstrating feasibility. This is not a fatal flaw—the constrained attack largely mitigates the concern—but the paper would be stronger if it restructured to give the constrained attack greater primacy and presented the oracle-access results as an upper bound.

2. **No direct quantitative comparison with pixel-level attacks on identity metrics.** The paper's central thesis is that pixel-level metrics underestimate identity leakage. To make this fully convincing, the paper should run existing pixel-level attacks (U-Net, StyleGAN from FracFace) on the same test images and measure their identity similarity (via ArcFace or Face++) alongside FaceLinkGen's results. The paper references FracFace's own figures showing these attacks fail, but a direct replicated comparison under identical conditions would definitively prove the claim. Without it, a skeptical reader could argue FaceLinkGen is simply a better attack rather than exposing a paradigm flaw.

3. **Missing training details for reproducibility.** The student model architecture is described as "Antelopev2 with one additional 3x3 Conv2D layer prepended" but no hyperparameters are given in the main text: optimizer, learning rate, batch size, weight decay, number of epochs, data augmentation. The paper states the distillation "was completed in under two hours" but does not specify the training configuration. If the appendix (which may have been stripped by the parser) contains these details, they should be summarized in the main text.

4. **Constrained-attack results on Amazon API show notable degradation.** The constrained attack achieves 94-96% regeneration on Face++ but only about 45-57% on Amazon API (Table 7). The paper attributes this to Amazon being "more strict or sensitive to AI-generated images" but provides no analysis. A 45-57% rate is still meaningful but substantially weaker than the Face++ results, and the discrepancy should be investigated (e.g., are false positives on Face++ due to API bias, or do Amazon's rejections indicate genuine identity inconsistency?).

5. **No confidence intervals or variance estimates.** All main results (Tables 2, 3, 4, 5, 7) report single numbers without variance across multiple training seeds or bootstrapped confidence intervals. For claims as strong as "over 98.5% matching accuracy," single-run results leave uncertainty about robustness. The results are impressively high, so CIs are unlikely to change the conclusions, but they would increase confidence.

## Novel Insights

The most insightful observation from the reviews is that the paper's core argument would be significantly strengthened by a simple structural change: giving primacy to the constrained attack (Section 6) rather than the oracle-access attack. The constrained attack is both more realistic and more scientifically compelling because it shows the vulnerability is not an artifact of strong attacker assumptions. The oracle-access results serve as an informative upper bound. Additionally, the Table 6 comparison—directly juxtaposing FracFace's frequency-channel "protection rate" against FaceLinkGen's actual identity recovery—is one of the paper's most effective pieces of evidence, yet it is somewhat buried. Highlighting this contrast more prominently would sharpen the paper's message.

## Suggestions

1. Restructure the paper to lead with the constrained attack (Section 6) as the primary result, and present the oracle-access results as an upper-bound demonstration of worst-case leakage. This would preempt the main threat-model criticism.

2. Add a direct experimental comparison: run the U-Net and StyleGAN attacks from FracFace on the same test images used for FaceLinkGen, measure identity similarity via Face++/ArcFace, and report the results side-by-side. This would definitively prove that pixel-level metrics fail to capture identity leakage.

3. Include key training hyperparameters (optimizer, learning rate, batch size, epochs) in the main text, even if briefly. Add variance estimates (e.g., 3 seeds) for main numerical claims.

4. Investigate and discuss the Face++ vs. Amazon API discrepancy in the constrained attack (Section 6). A small-scale manual inspection of failure cases would help determine whether the gap reflects genuine identity inconsistency or API-specific threshold differences.

5. The discussion of soft biometrics (Section 9) is a valuable extension but somewhat underspecified. Clarify whether the MLP predictor was trained on original images or protected templates, and how the one-epoch training was configured.
