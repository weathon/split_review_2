## Summary

This paper systematically evaluates 9 open-source LLMs on two reverse engineering tasks — name recovery and type inference — across 4 CPU architectures and 4 optimization levels. It honestly documents that current LLMs perform poorly (most F1 scores below 0.1) and finds that fine-tuning provides inconsistent improvements. The motivation (model selection in RE papers is often unjustified) is sound, and the scope is broad.

## Strengths

- **Broad architectural coverage.** Evaluating 9 open-source LLMs spanning CodeLlama, Llama2, DeepSeek variants, Qwen variants, WizardCoder, Phi4, and Gemma3 (§3.3, Table 1) across 4 CPU architectures and 4 optimization levels gives the study a scope that individual RE papers lack. (weight: +3.21)

- **Honest documentation of negative findings.** The paper consistently reports poor performance (most F1 scores below 0.1 in the primary tables) without attempting to inflate or spin the results, which is valuable for the community. (weight: +2.39)

- **Timely and well-motivated benchmark.** The observation that existing RE papers (SYMGEN using CodeLlama-34B, ReSYM using StarCoder-3B) select models without justification (§2, lines 82–91) is a genuine gap, and the paper correctly identifies the need for a systematic evaluation. (weight: +2.34)

## Weaknesses

### Fatal

None.

### Major

- **Unexplained 3–20× discrepancy between Table 2 and Figure 1 for the same claimed measurement.** Table 2 reports function name recovery F1 scores on x86-64 decompiled code (e.g., CodeLlama O0=0.04, Llama2 O0=0.01, DeepSeek-V2 O0=0.01). Figure 1 reports F1 on what is captioned as the same task (function name recovery, x86-64, decompiled code, w/ CodeWordNet) with values 3–20× higher (CodeLlama O0≈0.15, Llama2 O0≈0.18, DeepSeek-V2 O0≈0.20). Neither the table nor figure captions explain the discrepancy, and the paper offers no discussion. The Table 2 values (~0.01–0.06) are closer to the "wo CodeWordNet" values in Figure 1 (~0.02–0.08), suggesting either that Table 2 reports results without CodeWordNet (contradicting §3.4, which states name recovery uses CodeWordNet) or that a different experimental condition is at play. Either way, the inconsistency undermines confidence in all reported numerical results. (weight: -4.63)

- **The auxiliary LLM used for response normalization is never identified or validated.** The paper (§3.2, lines 107–108) states it uses "an auxiliary LLM specialized in formatting" to normalize heterogeneous model outputs into a consistent schema, but does not name the model, report its prompt, or provide any validation that it preserves correct predictions without introducing systematic bias. Given that DeepSeek-R1's chain-of-thought reasoning is "normalized away" (line 412), the interaction between target-model output style and auxiliary-model behavior is a first-order concern that is left completely unexamined. This also makes the evaluation pipeline unreproducible. (weight: -2.46)

- **Fine-tuning protocol is reported with insufficient detail.** All models are fine-tuned with LoRA for only 200 steps (Table 7), but no LoRA hyperparameters are disclosed (rank, alpha, target modules, learning rate, batch size, optimizer). Without knowing whether each model received a reasonably configured setup, cross-model comparisons are not informative — a model that underperforms after 200 LoRA steps may simply require different hyperparameters or more training, not be inherently worse at the task. (weight: -2.28)

### Minor

- **No variance or statistical significance reporting.** Every result in every table is a single point estimate. Given that LLM outputs are stochastic and the dataset involves random sampling, differences of 0.01–0.03 in F1 (which constitute the entire meaningful range for most comparisons) cannot be distinguished from noise without confidence intervals or multiple runs. (weight: -4.06)

- **The abstract claims DeepSeek-R1 reaches an F1 of 0.37 after fine-tuning (line 19), but this number does not appear in any main-text table.** The paper notes that additional architectures are deferred to the appendix (line 217), which the parser stripped, so the result may exist there. However, placing a single cherry-picked best number in the abstract without specifying the task, architecture, or optimization level is misleading framing. (weight: -2.04)

## Nice-to-Haves

- A small human evaluation (e.g., 100 outputs) validating the auxiliary LLM normalization pipeline against human judgment would substantially increase trust in the results.
- Including confidence intervals or standard deviations for the main results would address the stochasticity concern.
