## Summary
This paper systematically benchmarks 9 open-source LLMs (12-16B parameters) on reverse engineering tasks—function name recovery, variable name recovery, and type inference—from stripped binaries across 4 architectures and 4 optimization levels using a 40,000-function GNU software dataset. The central finding is that all models achieve very low F1 scores (mostly below 0.1), with inconsistent and often marginal improvements from LoRA fine-tuning.

## Strengths
- **Comprehensive multi-factor evaluation design**: Evaluates 9 LLMs across 4 architectures (x86-64, x86-32, ARM, MIPS), 4 optimization levels (O0-O3), and 3 distinct tasks using 40,000 unique function samples (Section 4.1). This breadth surpasses prior work such as SYMGEN (function names only) and VARBERT (variable names only).
- **Real-world firmware evaluation with two decompilers**: Table 6 evaluates all models on real-world firmware binaries decompiled using both Ghidra and IDA Pro. The consistent finding that IDA Pro yields higher F1 scores provides a practical insight for practitioners.
- **Model size does not improve RE performance**: Figure 2 shows CodeLlama 7B/13B/34B variants perform nearly identically despite the 34B model being ~5x larger—a concrete, actionable finding that contradicts assumptions from other NLP domains.
- **Same-architecture comparison isolating training data quality**: Finding 5 compares DeepSeek-R1 (a fine-tuned variant of Qwen2.5) against Qwen2.5 itself, controlling for architecture and showing that training data/strategy, not architecture, is the dominant factor.

## Weaknesses

### Fatal
None

### Major
- **Unsubstantiated key claim in the introduction**: Line 19 states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." No result table supports this. Table 2 shows DeepSeek-R1 fine-tuned max at 0.05 (function names), Table 3 at 0.17 (variable names), Table 4 at 0.01 (type inference). The highest scores in any table are 0.33 (WizardCoder/Qwen2.5/Phi4 on variable name recovery at O0), achieved by different models. The paper notes other architectures' results are in the appendix, but the introduction's claim is unqualified. For a benchmarking paper whose core value is trustworthy reporting, this factual inconsistency in the most prominent quantitative claim is seriously damaging.

- **Unexplained numerical discrepancy between Figure 1 and main results**: Section 3.4 states CodeWordNet is the evaluation method for name recovery. Yet Figure 1's "w CodeWordNet" F1 scores (e.g., CodeLlama O0: ~0.15, Llama2 O0: ~0.18, Qwen3 O0: ~0.25) are 3-5× higher than the corresponding values in Table 2 (CodeLlama O0: 0.04, Llama2 O0: 0.01, Qwen3 O0: 0.05). If the main tables use CodeWordNet (as Section 3.4 claims), Figure 1's "w CodeWordNet" values should match—they don't. If the main tables use strict matching, Figure 1's "wo CodeWordNet" values should match—they also don't (e.g., Llama2 O0: ~0.06 in Figure 1 vs. 0.01 in Table 2). The paper provides no explanation for this discrepancy. This undermines trust in the quantitative results.

- **No comparison with dedicated reverse engineering baselines**: The paper mentions SYMGEN, RESYM, VARBERT, SymIm, and Debin but never includes their performance. Without this context, "LLMs achieve F1 below 0.1" is unactionable—readers cannot determine if this is near-optimal or far below what dedicated methods achieve. A benchmark's primary value is contextualizing performance against existing approaches.

### Minor
- **Fine-tuning protocol underspecified**: Section 3.3 mentions LoRA but provides no learning rate, batch size, epochs, LoRA rank, or target modules. Only "200 steps" is specified. Some models degrade after fine-tuning (e.g., DeepSeek-V2 in Table 3: O1 original 0.10 → fine-tuned 0.05; several Gemma3 rows decline), raising questions about whether poor results reflect task difficulty or suboptimal training. Reporting key hyperparameters and convergence behavior would help distinguish these.

- **Shallow analysis of failure modes**: The 8 "findings" are largely unsurprising aggregate observations (fine-tuning sometimes helps, assembly is harder than decompiled code, bigger models don't always help). The paper doesn't analyze what kinds of names/types are recoverable, what patterns exist in errors, or why models fail. Table 8 shows only 4 cases from one model. Breaking down by function complexity, name length, or type category would substantially strengthen the contribution.

## Novel Insights
The paper's genuinely novel observations are: (1) model scale has essentially zero impact on RE performance within the 7-34B range (Figure 2), (2) training data quality—not architecture—is the dominant factor, demonstrated by DeepSeek-R1 consistently underperforming its base model Qwen2.5 (Finding 5), and (3) prompt template design can increase fine-tuning time by 3×+ (Finding 7, Table 7). These are concrete, evidence-backed findings.

## Suggestions
- Correct or remove the 0.37 F1 claim in the introduction, or clearly qualify which architecture/task it refers to if supported by appendix data.
- Reconcile Figure 1 values with the main tables—either explain the discrepancy or recompute with consistent methodology.
- Add at least one dedicated RE baseline comparison (e.g., re-run RESYM or SYMGEN on your dataset) to contextualize the LLM results.
- Add failure mode analysis: break down results by function complexity, name type, and error category.
