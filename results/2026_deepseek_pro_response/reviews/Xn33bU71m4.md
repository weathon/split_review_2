## Summary
This paper systematically benchmarks nine open-source mid-sized LLMs (~12-16B parameters) on two reverse engineering tasks: function/variable name recovery and type inference from stripped binaries. The authors evaluate models zero-shot and after LoRA fine-tuning across four architectures, four optimization levels, and two input representations (decompiled code and assembly). The headline finding is that LLMs perform poorly across the board — most F1 scores are below 0.1 for original models — and that fine-tuning provides modest gains for name recovery but actively harms type inference for most models.

## Strengths
- **Systematic multi-model benchmarking fills a documented gap**: The paper directly addresses the problem identified in §2 — that prior reverse-engineering work selects LLMs arbitrarily without justification. By running all nine models through identical pipeline conditions on the same dataset, the paper provides the first fair comparative evidence base for model selection in this domain. Tables 2-4 could only be produced through this systematic approach.
- **Multi-dimensional evaluation design**: The experiments vary architecture (x86-64, x86-32, ARM, MIPS), compiler optimization level (O0-O3), input representation (decompiled/assembly code), and task (function name, variable name, type inference). This breadth means the consistent finding of poor performance is unlikely to be an artifact of any single experimental condition.
- **Equal-footing fine-tuning comparison**: All nine models are fine-tuned on the same 160,000-function training set and evaluated on the same held-out test set. Tables 2-3 reveal clear winners and losers (e.g., WizardCoder, Qwen2.5, and Phi4 reach ~0.33 F1 on variable name recovery while Gemma3 stagnates at ~0.03), giving practitioners concrete model-selection guidance.
- **CodeWordNet ablation validates a key methodological choice**: Figure 1 demonstrates that removing CodeWordNet semantic matching causes F1 scores to drop roughly 3x across all models, showing that string-exact matching would systematically underrate LLM name recovery.
- **Practical engineering contribution**: The automated post-processing pipeline (§3.2) using an auxiliary LLM to normalize heterogeneous outputs solves a real bottleneck for large-scale LLM evaluation and is reusable by other researchers.
- **Real-world firmware evaluation**: Table 6 tests all nine models on actual firmware binaries decompiled with both Ghidra and IDA Pro, corroborating the main findings in a more realistic setting.

## Weaknesses

### Fatal
None.

### Major
- **Unsupported headline claim (0.37 F1)**: The introduction (line 19) prominently states that fine-tuned DeepSeek-R1 reaches an F1 of 0.37. This number does not appear in any visible table. Across Tables 2-6, the highest DeepSeek-R1 score is 0.17 (Table 3, variable name recovery, O0, fine-tuned), with most results below 0.05. The paper notes that results for non-x86-64 architectures are in the appendix (line 217), so this number may exist in stripped material. However, the introduction presents it as the paper's single most emphatic quantitative claim without any indication of which task, architecture, or condition produced it. The claim is therefore misleading as written and must either be supported by visible evidence or corrected.
- **Numerical discrepancy between Figure 1 and Table 2**: Both report function name recovery F1 on x86-64 via decompiled code with CodeWordNet. Figure 1 shows values of ~0.08-0.25 across models while Table 2 shows 0.01-0.06 for the same models — a 3-5x difference. For a benchmarking paper whose contribution rests on quantitative results, this internal inconsistency undermines trust in the reported numbers. The authors must reconcile or explain this discrepancy.
- **Misleading characterization of type inference results**: Table 4 shows that fine-tuning drives type inference F1 to 0.00 for 7 of 9 models (DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, WizardCoder, Phi4, Gemma3). This is active degradation — fine-tuning is harmful, not merely ineffective. Yet Finding 2 (line 304) describes this as "limited impact." The paper never investigates whether this is a LoRA configuration issue, catastrophic forgetting, a data problem, or an evaluation artifact. A benchmark paper should at minimum acknowledge and probe such a striking negative result rather than dismiss it.

### Minor
- **No validation of auxiliary LLM normalization**: Section 3.2 uses an auxiliary LLM to normalize heterogeneous model outputs. If this normalizer misparses or hallucinates, errors propagate into all reported metrics. The paper does not report any validation (e.g., agreement with human-annotated samples).
- **LoRA hyperparameters not specified**: Rank, alpha, target modules, learning rate, and optimizer are not reported. This matters particularly because type inference fine-tuning fails — readers cannot assess whether hyperparameter choices contributed to the degradation.
- **Dataset restricted to GNU projects**: The dataset draws primarily from GNU software, biasing toward systems-software idioms (stack checking, OpenSSL, etc.). This limits the generality of conclusions about LLM name recovery capability, though the real-world firmware evaluation (Table 6) partially mitigates this concern.

### Trivial
- The abstract mentions only 3 models as examples (CodeLlama, Llama 2, DeepSeek-R1) while the paper evaluates 9. This understates the paper's actual breadth.

## Nice-to-Haves
- No non-LLM baselines (DIRT, Debin, SYMLM, VARBERT) are included to calibrate what an F1 of 0.06 or 0.33 means in absolute terms relative to specialized systems.
- No confidence intervals or statistical significance measures are reported despite 2,500-sample test sets, making it unclear whether small inter-model differences (e.g., 0.01 vs. 0.03) are meaningful.
- The exclusion of models above ~16B parameters is acknowledged but limits the study's ability to speak to whether scale alone would close the gap.

## Novel Insights
The finding that fine-tuning actively degrades type inference to zero for most models — while simultaneously improving name recovery — suggests a fundamental tension in how LoRA fine-tuning interacts with these two tasks. This pattern is not merely "LLMs are bad at RE" but hints at task-specific barriers: name recovery benefits from semantic priors learned during code pretraining while type inference may require structural reasoning about data flow that current fine-tuning approaches disrupt rather than enhance. This is a genuinely interesting negative result that the paper itself under-analyzes.

## Suggestions
- Either provide the table supporting the 0.37 DeepSeek-R1 claim in the main body (with task/architecture/condition clearly identified) or correct the introduction to reflect the highest visible result (0.17).
- Audit and reconcile Figure 1 with Table 2. If they measure different conditions, state the difference explicitly. If they should match, fix the error.
- Investigate why LoRA fine-tuning destroys type inference: try varying LoRA rank, testing with a subset to rule out data issues, or checking whether the fine-tuned models simply learn the output template without learning types. This is the paper's most scientifically interesting result.
- Add a small validation study for the auxiliary LLM normalization step (e.g., 200 human-annotated samples with agreement rates).
- Report LoRA hyperparameters for reproducibility.
