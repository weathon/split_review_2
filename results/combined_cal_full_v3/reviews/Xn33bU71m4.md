## Summary

The paper systematically evaluates 9 open-source LLMs (CodeLlama, Llama 2, DeepSeek-R1, etc.) on two reverse engineering tasks — name recovery and type inference from stripped binaries — across 4 architectures and 4 optimization levels. The central finding is that all models perform poorly (near-zero F1 scores), though fine-tuning provides inconsistent improvements. The paper also contributes an automated post-processing pipeline for normalizing LLM outputs.

## Strengths

- **Addresses a genuine gap in the literature.** As noted in §2 (lines 82–91), recent RE works (SYMGEN, RESYM) adopt specific LLMs without justifying the choice. A systematic, evidence-driven comparison across models is a contribution the field needs.

- **Non-trivial experimental effort.** The evaluation covers 4 architectures (x86-64, x86-32, ARM 32-bit, MIPS 32-bit), 4 optimization levels (O0–O3), 40,000 test functions, and 160,000 fine-tuning samples. Dataset construction and deduplication are described adequately (§4.1, lines 137–139).

- **Automated post-processing pipeline (§3.2) is a practical engineering contribution.** Using an auxiliary LLM to normalize heterogeneous model outputs into a uniform schema is a sensible solution that others can reuse.

## Weaknesses

### Fatal
None.

### Major

- **Abstract/introduction claim (F1=0.37 for DeepSeek-R1) is unsupported in the main paper body.** The abstract and introduction (line 19) state that after fine-tuning, "DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." However, this value does not appear in any table or figure in the main paper (Tables 2–6, Figures 1–2). The highest F1 for DeepSeek-R1 in any main-paper table is 0.17 (Table 3, variable name recovery, O0). Even if the 0.37 resides in the (stripped) appendix, the paper provides no cross-reference, and a headline claim in the abstract should be traceable to presented data. This is a structural problem that must be resolved before the paper can be evaluated on its merits.

- **Unexplained 2–5× discrepancy between Table 2 and Figure 1.** Table 2 reports function name recovery F1 scores of 0.00–0.06 for original models on x86-64, while Figure 1 reports "with CodeWordNet" F1 scores of 0.08–0.25 for the same model families on what is described as the same task (function name recovery, x86-64, decompiled code). For example, CodeLlama at O0 scores ~0.04 in Table 2 but ~0.15 in Figure 1 — a ~3.75× difference. The paper never explains this discrepancy. The most likely explanation (Table 2 uses the extended task of predicting all callee names within a function body, while Figure 1 uses the standard task of predicting only the function's own name) is never stated, leaving readers unable to interpret which numbers apply to which task formulation.

### Minor

- **No non-LLM baseline comparisons.** The paper's title and framing ("LLMs as Reverse Engineers? Not Yet") implicitly invite comparison with specialized non-LLM RE approaches (SYMNN, DIRE, Debin, etc.). Without such baselines, the reader cannot tell whether the near-zero F1 scores reflect a limitation of LLMs specifically or the inherent difficulty of these tasks for any approach. (The paper's stated scope is LLM evaluation, so this is a scope limitation rather than a design flaw, but the framing amplifies the need for context.)

- **Fine-tuning hyperparameters and convergence not reported.** The paper (line 380) states only "200 steps" for LoRA fine-tuning. Essential details — rank, alpha, learning rate, batch size, target modules — are missing. No learning curves or validation loss trajectories are provided. Without evidence of convergence, the fine-tuning results (both improvements and regressions, e.g., DeepSeek-V2 at O1 in Table 3 dropping from 0.10 to 0.05) cannot be interpreted as reliable measures of model capability.

- **Auxiliary LLM normalization accuracy not validated.** The response extraction pipeline (§3.2) uses an auxiliary LLM to normalize outputs, but the paper never reports the accuracy of this step on a manually labeled subset. Errors in normalization would directly lower measured F1 scores, potentially creating artifacts rather than reflecting model capability.

- **Output truncation not quantified.** The paper notes (line 422) that models "sometimes exceed output size limits, causing truncation before the answer is generated" but gives no statistics on how often truncation occurred or whether truncated responses were filtered from the evaluation.

- **Only F1 reported; precision and recall omitted.** The paper states it uses precision, recall, and F1 (line 139) but only reports F1 in all tables. At the very low F1 values observed (0.00–0.06), precision versus recall breakdowns would help diagnose failure modes.
