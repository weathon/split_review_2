## Summary

This paper systematically evaluates nine open-source LLMs (CodeLlama, Llama2, DeepSeek-R1, Qwen2.5/3, WizardCoder, Phi4, Gemma3, DeepSeek-V2) on two reverse engineering tasks — name recovery (both function and variable names) and type inference — using decompiled and assembly code across four architectures (x86-64, x86-32, ARM, MIPS) and four optimization levels (O0–O3) on 40,000 unique functions. The main finding is that all models perform poorly in zero-shot settings (F1 < 0.1), and while fine-tuning yields modest improvements (best variable name recovery F1 = 0.33), performance remains far from practically useful.

## Strengths

1. **First systematic evaluation covering both name recovery and type inference across multiple LLMs simultaneously.** The paper explicitly notes that prior work focused on narrow aspects (function name only, or without LLMs), while this evaluation spans 9 models × 2 tasks × 4 architectures × 4 optimization levels (Section 2, line 91; Tables 2–4). The breadth enables the paper's central negative result to be robust rather than an artifact of a narrow testbed.

2. **Automated post-processing pipeline to handle heterogeneous LLM outputs.** Section 3.2 describes using an auxiliary LLM to normalize outputs, addressing the real problem that "no LLM consistently adhered to the required structure" (Finding 8). This is a useful methodological contribution over prior work that either avoided the issue or used brittle single parsers.

3. **Empirical evidence challenging the assumption that larger models are better.** Figure 2 compares CodeLlama 7B, 13B, and 34B, showing "little difference in performance" despite the 34B model being nearly five times larger (Section 4.4, line 370). Findings 4–5 further show that DeepSeek-R1 underperforms Qwen2.5 (its base model), and CodeLlama outperforms Llama2, suggesting that training data quality matters more than raw scale.

4. **CodeWordNet ablation quantifying the need for semantic matching.** Figure 1 shows that removing CodeWordNet causes a sharp drop in performance (e.g., Qwen3 drops from ~0.25 to ~0.08 F1 at O0), empirically justifying the use of semantic similarity metrics for name recovery evaluation.

5. **Real-world firmware evaluation with dual decompilers.** Table 6 evaluates all models on real-world firmware using both Ghidra and IDA Pro, extending evaluation beyond synthetic benchmarks and revealing that decompiler quality affects LLM performance.

## Weaknesses

### Major

1. **Unexplained numerical discrepancy between Table 2 and Figure 1.** Both report F1 scores for function name recovery on x86-64 decompiled code, and the paper states that CodeWordNet is used for name recovery evaluation (Section 3.4). Yet Table 2 shows CodeLlama O0 = 0.04 and Qwen3 O0 = 0.05, while Figure 1 shows CodeLlama O0 w/CodeWordNet ≈ 0.15 and Qwen3 ≈ 0.25 — a 3–5× difference. If these use different test subsets or different task formulations (e.g., Figure 1 predicts only the enclosing function's name while Table 2 predicts all callee names as described in Section 2), the paper must explain this discrepancy. As written, readers cannot reconcile the two sets of numbers.

2. **Unsupported F1 = 0.37 claim for DeepSeek-R1 in the introduction (line 19).** The introduction states that "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." This number does not appear in any main results table for DeepSeek-R1 — the highest visible fine-tuned score for DeepSeek-R1 is 0.17 (Table 3, variable name recovery, O0). Three other models (Qwen2.5, WizardCoder, Phi4) reach 0.33 in Table 3, yet the introduction singles out DeepSeek-R1 with a higher unsupported value. Even if the 0.37 appears in the appendix, the introduction must qualify it. As presented, this is a factual error that erodes trust in the paper's accuracy.

### Minor

3. **No variance estimates or confidence intervals.** The reproducibility statement (line 428) acknowledges "randomness of LLMs," yet all results are reported as single point estimates with no standard deviations or statistical tests. For a benchmarking paper making comparative claims (e.g., CodeLlama 0.04 vs. Llama2 0.01), readers cannot assess whether observed differences reflect genuine capability gaps or random variation. Adding at least 3 runs with standard deviations for the central comparisons would significantly strengthen the claims.

4. **Auxiliary LLM used for post-processing is not named or validated.** The paper uses an auxiliary LLM to extract structured outputs from heterogeneous model responses (Section 3.2) but never identifies which model was used, nor does it validate extraction accuracy. Errors in the extraction pipeline propagate directly into reported F1 scores and are attributed to the target model. A human evaluation of extraction accuracy on a sample of responses is needed to rule out systematic bias.

5. **The "training data quality" conclusions (Findings 4–5) overstate what the evidence supports.** The paper concludes that "training data quality is more important than parameter count" and "training data quality significantly impacts performance." However, CodeLlama vs. Llama2 differ not just in training data but in additional training phases (code-specific fine-tuning). DeepSeek-R1 vs. Qwen2.5 differ in RLHF training procedure. The experimental design does not isolate "training data quality" as a controlled variable.

6. **Assembly code task (Finding 3): 0.00 F1 across all models without discussing whether the task is information-theoretically feasible.** Even a human reverse engineer would struggle to recover names like `stack_chk_fail` from raw assembly without debug symbols or broader context. The paper presents this purely as an LLM limitation without acknowledging that the representation itself may be the bottleneck.

7. **Finding 7 (prompt template impact on training time) is based on a single observation** — changing CodeLlama's prompt template (line 396) — and is extrapolated as a general finding without sufficient evidence.

### Trivial

8. **DeepSeek-V2's F1 = 0.10 under O1** (Table 3, variable name recovery original) is noted without discussion of why O1 specifically helps this model while other optimization levels do not.

## Nice-to-Haves

- A non-LLM baseline (e.g., decompiler default naming, frequency-based prediction, or a simple n-gram model) to contextualize absolute F1 scores — currently the reader has no reference point for whether 0.33 is surprisingly good or still poor.
- Error analysis categorizing whether LLMs produce plausible-but-wrong names vs. completely unrelated tokens.
- The prompt template (referenced as "Figure 4a") should be included in the paper or appendix.
- More detailed dataset construction description (which GNU projects, function selection criteria, deduplication process).

## Removed Points

*These points were flagged for removal from the final review but are documented for transparency:*

- **ChatGPT-derived prompt as a confound (Harsh Critic point 4):** REMOVED. Using the same prompt across all models is a defensible methodological choice for fair comparison. Optimizing prompts per-model would introduce a different, arguably worse, confound. The paper explicitly acknowledges this design choice ("Rather than optimizing prompts, we adopt an established…prompt").
- **"No non-LLM baseline" as a major weakness:** DEMOTED to Nice-to-Have. While informative, its absence does not undermine the paper's claims about relative LLM performance. The paper's scope is LLM evaluation, not establishing absolute baselines.
- **Missing related works:** REMOVED per instructions (no external sources to confirm existence).
- **Formatting/style nitpicks, typos, missing appendix sections:** REMOVED as parser artifacts or out-of-scope.
- **Strength Finder's generic strengths ("importance of problem"):** REMOVED as lacking specific evidence or being generic.

## Novel Insights

None beyond the paper's own contributions. The most notable observation from combining the reviews is that the paper's core empirical contribution — showing that all evaluated LLMs perform poorly on these tasks across diverse conditions — is robust and well-supported despite the presentation issues. The criticisms surface real problems (inconsistencies, unsupported claims) that need fixing but do not undermine the central finding.

## Suggestions

1. **Resolve the Table 2 / Figure 1 discrepancy:** clarify whether they use different test subsets, different task formulations (all callee names vs. only the function name), or different aggregation methods. Add a note in the Figure 1 caption.
2. **Correct or qualify the F1 = 0.37 claim** in the introduction: either show the supporting data or replace it with the best observed result (0.33) attributed to the correct models.
3. **Add variance estimates** (at least 3 runs with std. dev.) for the central comparisons in Tables 2–4.
4. **Name the auxiliary LLM** and report a sample-based validation of extraction accuracy.
5. **Caveat the causal claims about training data quality** (Findings 4–5) as correlational observations.
