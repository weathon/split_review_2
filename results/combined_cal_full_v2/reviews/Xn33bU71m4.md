## Summary

This paper conducts a systematic evaluation of nine open-source mid-sized LLMs (7B–34B) on two core reverse engineering tasks — name recovery (function and variable names) and type inference — across four architectures (x86-64, x86-32, ARM, MIPS), four optimization levels (O0–O3), and two input representations (decompiled code and assembly). The authors develop an automated pipeline using placeholder normalization and an auxiliary LLM for response extraction, and evaluate both zero-shot and LoRA-fine-tuned models. The central finding is that LLMs perform poorly (F1 < 0.10 on most settings), with the brightest spot being variable name recovery at O0 after fine-tuning (F1 ~0.22–0.33). The paper correctly identifies an important gap in the reverse engineering literature where models are selected without rationale.

## Strengths

- **Addresses a genuine gap in research practice.** The observation that existing reverse engineering papers (SYMGEN using CodeLlama-34B, RESYM using StarCoder-3B) select LLMs without rationale is well-taken, and the field does lack systematic benchmarking (§2). [weight=6.30]

- **Multi-faceted evaluation scope.** The study spans four architectures, four optimization levels, two input representations, two decompilers (Ghidra and IDA Pro) for a real-world firmware test, and both name recovery and type inference. This breadth is appropriate for a benchmarking study (§4.1, §4.3). [weight=7.28]

- **The CodeWordNet ablation is informative.** Figure 1 cleanly demonstrates that removing CodeWordNet drops F1 scores sharply (e.g., Qwen3 from ~0.25 to ~0.08), confirming that models produce semantically related names even when exact matches fail. This provides positive evidence about what LLMs can do. [weight=8.77]

- **Honest negative framing.** The title "Not Yet on Types and Names" and the paper's candid reporting of near-zero scores avoid overclaiming. [weight=6.64]

## Weaknesses

### Fatal
None.

### Major

- **Abstract claims an F1 of 0.37 that cannot be verified from the main body.** Line 19 states: "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." In the main tables, the highest F1 for DeepSeek-R1 is 0.17 (Table 3, variable name recovery at O0); all other fine-tuned scores for this model are ≤0.05. The abstract presents 0.37 as a headline result without specifying the task, setting, or architecture, and no main-text table or passage explains this number. If the result appears in the appendix, the abstract and main text should reference it. This is an inconsistency between the paper's headline claim and the evidence presented in the main body.

- **The zero-shot vs. fine-tuned comparison is confounded by different test sets.** The zero-shot evaluation uses a 40,000-sample set (2,500 × 4 architectures × 4 optimization levels). The fine-tuning experiment uses a separate pool of 160,000 functions split 80/20 into 128k train and 32k test, explicitly "independent of the original 2,500 sample test set" (§4.3). Because "Orig" and "Fine" scores are measured on different samples, the improvement attributed to fine-tuning cannot be cleanly separated from differences in sample difficulty. The tables present them side-by-side as if directly comparable.

- **The auxiliary LLM for response extraction is a black box.** The evaluation pipeline depends on an unspecified auxiliary LLM to normalize heterogeneous model outputs into a consistent schema (§3.2, line 107). The paper does not identify which LLM was used for this purpose, does not validate its extraction accuracy on a manually annotated sample, and does not analyze whether its errors systematically bias F1 scores up or down. Given that all models score near zero, even small post-processing biases could alter rank order or mask genuine capabilities.

- **Internal discrepancy between Table 2 and Figure 1.** Both report F1 scores for function name recovery on x86-64 using CodeWordNet. Table 2 shows CodeLlama O0 at 0.04, Llama2 O0 at 0.01, DeepSeek-V2 O0 at 0.01, and Qwen3 O0 at 0.05. Figure 1's "w CodeWordNet" bars show ~0.15, ~0.18, ~0.20, and ~0.25 respectively — roughly 3–18× higher. The paper does not explain this discrepancy, which undermines the internal consistency of the main quantitative results.

### Minor

- **No statistical significance or variance reporting.** All tables report single F1 point estimates without standard deviations, confidence intervals, or any measure of variance. This is especially problematic when most values are near zero (0.00–0.10), making it impossible to assess whether small differences between models reflect meaningful variation or noise.

- **The central results are floor-effect scores, limiting informativeness.** Most settings yield F1 scores of 0.00–0.10, yet the paper draws comparative findings (Finding 4: larger size does not guarantee performance; Finding 5: training quality is a more decisive factor) from the narrow band of near-zero variation. Differences of 0.02–0.04 F1 at the floor are uninformative for model selection. The one regime with meaningful signal (variable name recovery at O0 after fine-tuning, F1 ~0.22–0.33) is under-analyzed — the paper does not explore why O0 specifically enables better performance or what the variation across models at O0 reveals.

- **The dataset specification is vague.** The paper says the dataset is "mostly from GNU software" (§4.1, line 139) without listing specific projects, versions, compilation configurations, or the sampling strategy (uniform across projects? stratified by function size?). This limits reproducibility.

- **Finding 4 ("larger model size does not guarantee better performance") rests on a narrow comparison.** It is drawn from only three size variants (7B, 13B, 34B) of a single model family (CodeLlama), with the 70B variant excluded due to GPU limits (§4.3, line 178). This is a thin basis for a general claim about model size.
