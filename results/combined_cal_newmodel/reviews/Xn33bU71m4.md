## Summary

This paper presents a systematic evaluation of 9 open-source LLMs (12–16B parameters) on two reverse engineering tasks — name recovery (function and variable) and type inference from stripped binaries — in both zero-shot and fine-tuned settings. The core findings are that current models perform poorly across all tasks (most F1 scores < 0.1) and that fine-tuning yields inconsistent improvements. The paper's motivation — that prior work selects LLMs arbitrarily — is well-founded, and the experimental scope (9 models across 4 architectures, 4 optimization levels, 2 decompilers) is broad.

## Strengths

- **Clearly motivated problem.** The paper correctly identifies that prior work selects LLMs for reverse engineering arbitrarily without justification (Section 2). A systematic comparison fills a genuine gap, and the framing is the paper's strongest element.

- **Broad experimental scope.** The evaluation spans 9 models, 4 architectures, 4 optimization levels, and two decompilers — more comprehensive than any single prior study on this topic. The automated pipeline for handling heterogeneous model outputs (Section 3.2) is a practical contribution.

- **Honest negative findings.** The paper consistently reports poor performance without overselling. This is a legitimate scientific contribution if the results are reliable — negative results can guide resource allocation away from unpromising directions.

## Weaknesses

### Major

1. **Internal inconsistency between Table 2 and Figure 1.** Table 2 reports F1 scores of 0.01–0.06 for function name recovery (original models, x86-64), while Figure 1 shows the same metric for the same task and models at 0.08–0.25 with CodeWordNet — a 3–20× discrepancy depending on model and optimization level (e.g., Llama2 O0: 0.01 in Table 2 vs. ~0.18 in Figure 1). The paper states that name recovery uses CodeWordNet (Section 3.4), yet Table 2 values align with the "wo CodeWordNet" column of Figure 1, not the "w CodeWordNet" column. This inconsistency is not acknowledged or explained, and it directly undermines confidence in Findings 1, 4, 5, and 6, which depend on these numbers.

2. **Unsupported headline quantitative claim in the abstract and introduction.** The abstract (line 9) and introduction (line 19) state that *"after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37."* However, this number does not appear in any reported result. The highest F1 score for fine-tuned DeepSeek-R1 across all tables is 0.17 (Table 3, variable name recovery at O0). All other fine-tuned scores are ≤0.05. A headline quantitative claim that cannot be traced to any experiment in the paper is a serious presentation error that misrepresents the findings.

3. **Unvalidated and unspecified auxiliary LLM for response extraction.** The evaluation pipeline depends on an auxiliary LLM that converts heterogeneous model responses into a uniform format (Section 3.2). The paper never identifies which LLM serves this role, never reports its extraction accuracy, and never accounts for the possibility that extraction errors vary systematically across target models (which produce very different output styles — see Section 4.5 on chain-of-thought, refusals, etc.). For a benchmarking paper whose entire evidence base passes through this pipeline, this is a critical methodological gap that makes it impossible to separate model failure from extraction failure.

### Minor

4. **No statistical measures for a comparison paper.** The paper reports no confidence intervals, standard deviations, or significance tests. Many comparisons involve tiny differences (e.g., 0.03 vs. 0.04 F1). The paper acknowledges LLM randomness ("The number will be similar, but not identical, due to randomness of LLMs and random data selection") but does not quantify it. Without variance estimates, readers cannot assess whether observed differences are meaningful.

5. **Dataset description is underspecified for a benchmarking paper.** The paper only states "diverse open-source projects, mostly from GNU software" (Section 4.1) without naming specific packages. The distribution of the 40,000 test functions across architectures is not reported, and the selection process for the 2,500 samples per (architecture, optimization) pair is not detailed. Independent replication is not feasible from the current description.

6. **Strict exact matching for type inference conflates metric strictness with model capability.** The paper uses exact matching for C types including user-defined types (Section 3.4), so semantically equivalent representations (e.g., `unsigned int` vs. `uint32_t`) count as mismatches. While the paper acknowledges this difficulty (Section 4.4), it does not address the extent to which the near-zero Table 4 scores reflect the metric's rigidity rather than model limitations, limiting the informativeness of the type inference results.

### Trivial

7. **No code or data release link is provided.** For a reproducibility-critical benchmarking paper, the statement that results "can be reproducible by executing the identical scripts" (Section 5) is empty without access to those scripts or the dataset.

## Nice-to-Haves

- Increase the fine-tuning budget beyond 200 steps (Table 7) and report convergence behavior; this would strengthen the conclusions about fine-tuning's limitations.
- Include non-LLM baselines (e.g., SYMLM, VARBERT, Debin) to contextualize how much LLMs add over existing solutions.
- Report which GNU packages compose the dataset.
- Disclose the identity of the auxiliary LLM used for response extraction.

## Suggestions

1. **Resolve the Table 2 vs. Figure 1 discrepancy.** Clarify whether Table 2 uses CodeWordNet or a different metric; if Table 2 values are correct, explain why they differ from Figure 1's "w CodeWordNet" values for the same models and task.
2. **Either provide evidence for the 0.37 F1 claim or remove it from the abstract and introduction.** If this number comes from an experiment in the appendix, cite it explicitly. Otherwise, correct the claim.
3. **Identify the auxiliary LLM and validate its extraction accuracy** on a manually labeled subset of at least 200 responses across different target models, reporting per-model accuracy.
4. **Add confidence intervals or error bars** for key comparisons to help readers assess whether model-to-model differences are meaningful.
5. **Release the dataset and evaluation scripts** to enable independent replication, as is standard for benchmarking papers.
6. **Provide more detailed dataset documentation**, including the specific GNU packages used and the distribution of functions across architectures.
