## Summary
This paper systematically benchmarks 9 mid-sized open-source LLMs (12B–16B) on two reverse engineering tasks—name recovery (function and variable) and type inference—from stripped binaries, using 40,000 functions across 4 architectures and multiple optimization levels. The main finding is that all models achieve very low F1 scores (mostly < 0.1) even after LoRA fine-tuning, suggesting current LLMs are not ready for production reverse engineering.

## Strengths
- **Broad systematic evaluation scope**: 9 LLMs across 4 architectures (x86-64, x86-32, ARM32, MIPS), multiple optimization levels (O0–O3), and 40,000 unique function samples (Section 4.1, Tables 2–6). This is genuinely broader than prior work that focused on narrow aspects.
- **CodeWordNet ablation demonstrates evaluation methodology matters**: Figure 1 shows removing CodeWordNet causes sharp F1 drops (e.g., Qwen3 O0 drops from ~0.25 to ~0.08), demonstrating that strict string matching unfairly penalizes semantically correct predictions. This is a useful contribution to the evaluation methodology discourse.
- **Real-world firmware evaluation with dual decompilers**: Table 6 evaluates on real firmware with Ghidra and IDA Pro, showing models perform slightly better on IDA Pro outputs — a practical insight absent in prior work.
- **Honest negative findings with broad implications**: The consistent near-zero performance across all models, tasks, and input formats (Tables 2–6) is a valuable corrective in a field where positive results dominate.

## Weaknesses

### Fatal
None

### Major
- **Unsupported headline numerical claim**: The introduction (line 19) states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." This number appears nowhere in the paper's result tables. Table 2 shows DeepSeek-R1 fine-tuned scores of 0.04–0.05; Table 3 shows 0.05–0.17; Table 4 shows 0.00–0.01. Even the best fine-tuned score across all models is 0.33 (Qwen2.5/WizardCoder/Phi4 for variable name recovery at O0). The 0.37 figure either does not exist, is misattributed, or comes from an unreferenced appendix condition. This is the central motivating claim in the abstract and introduction and it is directly contradicted by the presented results — a serious credibility problem.

- **Auxiliary LLM for output normalization is completely unspecified**: The entire evaluation depends on an "auxiliary LLM" (Section 3.2, lines 95–108) that post-processes raw model outputs into standardized schema. The paper never identifies this model — not its name, size, provider, or any validation of its accuracy. Since this model determines what counts as a "correct" prediction for every evaluated LLM, systematic biases or parsing errors propagate into all reported numbers. No examples of normalization accuracy are provided and no human evaluation validates the pipeline.

- **No comparison with specialized reverse engineering baselines**: The paper evaluates LLMs in isolation but never benchmarks against dedicated ML approaches for the same tasks — Debin (He et al., 2018), SymIm (Jin et al., 2022), VARBERT (Pal et al., 2024), and ReSYM (Xie et al., 2024) are all cited but never quantitatively compared. The conclusion that "LLMs perform poorly" is much less informative without context: if specialized models achieve F1 of 0.5–0.7, the story is about LLMs being the wrong tool; if they also struggle, the story is about task difficulty. The benchmarking contribution cannot be properly interpreted without this context.

### Minor
- **LoRA fine-tuning hyperparameters are absent**: Section 3.3 mentions using LoRA but provides no details — rank, alpha, target modules, learning rate, batch size, number of epochs, or dropout are all missing. Given LoRA's known sensitivity to these choices, the claim that fine-tuning provides limited benefit could change with different settings.
- **No variance or confidence intervals reported**: Despite acknowledging stochasticity (line 428: "The number will be similar, but not identical, due to randomness of LLMs and random data selection"), no repeated experiments or variance measures are provided.
- **Analysis is largely descriptive with limited insight into failure modes**: The results section catalogs model scores but offers limited analysis of *why* performance is so low. The 8 "Findings" are mostly unsurprising (larger models don't guarantee better performance, training quality matters).
- **Single arbitrary prompt template**: All 9 models are evaluated with one prompt adopted from a Notion page about GPT-3.5 (line 103), with no adaptation or optimization.

## Novel Insights
The CodeWordNet ablation (Figure 1) provides a genuinely useful insight for the RE-ML community: evaluation methodology choice significantly affects conclusions about LLM capability, with semantic matching vs. strict string matching producing order-of-magnitude differences in apparent performance. Combined with the consistent near-zero results across all models and tasks, this establishes a clear baseline that current LLMs are fundamentally limited for binary reverse engineering.

## Suggestions
- Resolve the 0.37 F1 score discrepancy — either fix the number in the abstract/introduction to match the actual results, or clearly identify where this number comes from
- Identify and validate the auxiliary LLM: report its name, show examples of parsing accuracy, ideally run a small human evaluation
- Add comparison with at least one specialized ML baseline (e.g., ReSYM or VARBERT) on a subset of the same data
- Report LoRA hyperparameters in full for reproducibility
