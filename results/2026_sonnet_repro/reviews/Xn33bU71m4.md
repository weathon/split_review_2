## Summary

This paper presents a systematic empirical evaluation of nine open-source mid-sized LLMs (CodeLlama, Llama2, WizardCoder, DeepSeek variants, Qwen variants, Phi4, Gemma3) on two binary reverse engineering tasks—function/variable name recovery and type inference—across four ISA architectures, four compiler optimization levels, and both decompiled and assembly code inputs, using 40,000 unique functions. An automated pipeline normalizes heterogeneous LLM outputs via an auxiliary LLM extractor. Results show near-zero F1 on most tasks before and after LoRA fine-tuning, supporting the conclusion that current LLMs are not yet reliable reverse engineers.

---

## Strengths

- **Multi-axis coverage eliminating single-configuration confounds.** Nine models × four architectures × four optimization levels × two input representations × 40,000 functions (Section 4.1/4.3) makes the universally poor performance (most F1 < 0.1) attributable to LLM capability limits, not a single narrow setup.

- **Fine-tuning instability is empirically demonstrated.** Table 3 shows that fine-tuning can improve variable name recovery significantly for some models (WizardCoder 0.01 → 0.33, Qwen2.5 0.01 → 0.33) but degrades others (DeepSeek-V2 O1: 0.10 → 0.05), directly supporting the claim that fine-tuning gains are inconsistent and not guaranteed.

- **Model size vs. training quality finding is grounded.** Figure 2 shows CodeLlama 7B, 13B, 34B achieve essentially identical F1 on all tasks, providing within-family evidence that scale alone does not improve performance on this domain.

- **Real-firmware evaluation extends conclusions to practice.** Table 6 confirms near-zero F1 on stripped firmware under both Ghidra and IDA Pro, validating that lab findings transfer to realistic scenarios.

---

## Weaknesses

### Fatal

- **Headline quantitative claim in the introduction is inconsistent with the paper's own results.** Section 1 (Introduction) explicitly states: "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." Table 3 (Variable Name Recovery) shows DeepSeek-R1's maximum fine-tuned F1 is **0.17** (O0, x86-64). No entry in any table—Tables 2, 3, 4, 5, or 6—reports 0.37 for DeepSeek-R1. The value 0.33 belongs to Qwen2.5, WizardCoder, and Phi4. This is the primary quantitative claim highlighted in the abstract/introduction to justify the importance of fine-tuning, and it is wrong relative to the paper's own evidence. This is not a parser artifact; it is a factual mismatch between the introduction's summary and the result tables.

### Major

- **Potential metric inconsistency between Figure 1 and Table 2.** Section 3.4 states that CodeWordNet is used for all name recovery evaluation. Table 2 reports CodeLlama function name recovery (x86-64, O0, original) as 0.04. Figure 1, which specifically shows function name recovery *with* CodeWordNet vs. without (same architecture, same model), shows a bar for "w CodeWordNet" that is substantially higher than the "wo CodeWordNet" bar—and visually appears to be roughly 3× higher than the Table 2 values for the same model/condition. If Table 2 already applies CodeWordNet, the Figure 1 "with" bars should match Table 2; if Table 2 does not use CodeWordNet, the paper is presenting its primary results under a metric it explicitly abandoned as inadequate. The paper never reconciles this, leaving the metric governing the primary result tables ambiguous.

- **No comparison to specialized reverse engineering systems undermines the paper's central interpretive claim.** The paper concludes that "current LLMs are not yet capable reverse engineers," but it cites VARBERT (Pal et al., 2024), ReSYM (Xie et al., 2024), SYMGEN (Jiang et al.), and SYMLM (Jin et al., 2022)—all of which produce quantitative results on analogous tasks—without including any of them as reference points. Without knowing whether a fine-tuned LLM at F1 = 0.33 (the paper's best variable-name result) is close to or far below VARBERT or ReSYM on overlapping data, the "not yet ready" conclusion cannot be assessed in context. The evaluation tells us LLMs score poorly in absolute terms but not what "poorly" means relative to the state of the art.

### Minor

- **200 fine-tuning steps with no rationale or ablation.** Section 3.3 adopts 200 steps for all models without justification or any learning-curve validation. This is especially consequential for the conclusion in §4.4 that "fine-tuning fails to produce meaningful gains" for type inference—if training has not converged, the conclusion conflates insufficient training with a fundamental LLM limitation.

- **Cross-family training-quality inference is not isolatable.** Findings 4 and 5 conclude that training data quality is more important than parameter count by comparing CodeLlama vs. Llama2 and Qwen2.5 vs. DeepSeek-R1. These pairs differ simultaneously in architecture, instruction-tuning pipeline, and training corpora; the conclusion about data quality specifically is conjecture. The within-family CodeLlama size experiment (Figure 2) is legitimate; the cross-family inference is not.

- **Near-zero results compared without statistical treatment.** Most model comparisons occur in the range F1 = 0.01–0.06. Conclusions such as "Qwen3 achieves the best function name recovery" (F1 = 0.06 vs. nearest competitor at 0.05) are not credible without variance estimates, given acknowledged stochasticity in LLM outputs and formatting failures.

### Trivial

- None beyond the 0.37/table discrepancy already elevated to Fatal.

## Nice-to-Haves

- A comparison to one specialized system (even approximate, using publicly available test data from VARBERT or SYMLM) would transform the finding from "absolute F1 is low" into an actionable statement for practitioners selecting tools.
- Reporting results with and without CodeWordNet consistently in the main tables (not only in a separate figure) would resolve the ambiguity about what metric drives the primary results.
- An ablation of fine-tuning steps (e.g., 100, 200, 500) would strengthen or weaken the conclusion that fine-tuning is insufficient for type inference.
- A brief contamination analysis (checking whether the test functions appear in common pretraining corpora) would clarify whether zero-shot scores reflect genuine generalization.

## Novel Insights

The paper's most genuinely novel observation is that prompt template design for LoRA fine-tuning can inflate training time by ~4× (Finding 7, Table 7), as evidenced by DeepSeek-V2 requiring 186,720 seconds vs. ~50,000 for similar models, a difference traced to its prompt template rather than model complexity. This is practically relevant for researchers running similar benchmarking studies and is not widely documented. Beyond this, the paper confirms what domain experience would predict (LLMs are poor zero-shot reverse engineers) without providing enough context—via comparison to specialized tools—to quantify how poor "poor" is.
