## Summary

This paper proposes Autoformalizer with Tool Feedback (ATF), a framework that integrates Lean 4 compiler feedback (syntax) and multi-LLM consistency judgments as external tools into an iterative autoformalization process. The training pipeline has three stages: cold-start on synthetic tool-calling data, expert iteration, and DPO to reduce ineffective revisions. Experiments show ATF substantially outperforms single-pass baselines (e.g., +29.13% consistency on CombiBench), and human evaluation confirms the trend. The authors also release a 750K-statement dataset.

## Strengths

1. **The core idea is well-motivated and concretely realized.** The paper correctly identifies that single-pass formalizers cannot detect or correct their own errors, and provides a clean, modular solution: separate tools for syntax (Lean 4 compiler) and consistency (multi-LLM ensemble), integrated via iterative refinement. This is a principled design that addresses a real bottleneck.

2. **The ablation study (Table 4) cleanly isolates the contribution of each component.** The "NO TOOLS" row shows the most dramatic evidence: consistency Pass@1 on CombiBench drops from 65.38% to 23.69% without tool feedback. The row-level separation of syntax-only vs. full tools further quantifies the value of consistency checking beyond syntactic correctness (e.g., ProverBench consistency rises from 75.68% to 89.78%). This is the strongest evidence in the paper for the method's core thesis.

3. **Human evaluation provides independent validation.** The 0.746 Pearson correlation between the automated consistency check and human judgments (Section 4.2) lends credibility to the evaluation tool. The human evaluation results in Table 3 (bottom section) confirm the same trend as automated results — ATF-32B leads on all three benchmarks — which is the best available evidence that the reported gains are real and not artifacts.

4. **The scaling analysis (Section 5.1) offers non-trivial insight.** ATF continues to improve beyond its training limit of 8 revisions (Figure 4a), suggesting the model learns a generalizable refinement strategy rather than memorizing correction patterns from training. This supports the claim that the tool-integrated approach is structurally beneficial.

5. **Open-source release of 750K formal statements** is a practical contribution that will benefit the community regardless of whether every detail of the method holds up.

## Weaknesses

### Fatal
None.

### Major

1. **The consistency evaluation judge and the ATF model share a base architecture (Qwen3-32B), and the same judge is used in training and evaluation.** The consistency check tool is an ensemble of QWQ-32B and **Qwen3-32B** (Section 3.1.2, Table 1). The ATF model is fine-tuned from **Qwen3-32B** (Section 3.2: "implement the training pipeline for ATF using Qwen3-32B"). During training, ATF's outputs are judged by a system that includes Qwen3-32B, and the model is explicitly optimized to satisfy this specific judge. During evaluation (Table 3), **the same ensemble judge evaluates ATF and all baselines**. If ATF has learned patterns that align with Qwen3-32B's idiosyncratic notion of "consistency" — not just correct formalizations — then the automated evaluation is biased in ATF's favor. The baselines have not been trained to satisfy this judge.

   The human evaluation partially mitigates this (100 samples per benchmark for 32B models), and the human-evaluated margins are still large (e.g., CombiBench consistency: ATF-32B 49% vs. Goedel-V2-32B 22%), but the automated results in Table 3 — which form the primary quantitative evidence — likely overstate the true gap. The paper should foreground the human evaluation as primary evidence and clearly caveat the automated metrics.

### Minor

2. **The comparison against baselines is structurally asymmetric.** ATF is an iterative system that receives compiler feedback and LLM consistency judgments in multiple forward passes, while all baselines are single-pass formalizers. The paper's justification ("output lengths roughly equivalent" — Section 4.1) addresses token count but not the fundamental difference in access to external signals or inference cost (multiple forward passes + tool invocations). The comparison is still informative — the method's contribution **is** the tool feedback — but the framing (e.g., "29.13% improvement" in the introduction) conflates the tool-feedback innovation with the additional compute and external information ATF receives. A controlled experiment giving baselines multiple sampling attempts without tools would help disentangle these factors.

3. **The consistency check benchmark (Section 3.1.2) is synthetic and lacks human-validated ground truth.** The 800 negative statements are generated by Gemini-2.5-Pro as "perturbations" and filtered by similarity >0.95 and syntactic validity, but no human verification is reported. If some perturbations are actually semantically consistent (a plausible failure mode), the reported FPR of 5.79% (Table 1) would be an underestimate — the judge might be correctly calling some things consistent that the synthetic label marks as inconsistent. The human evaluation (0.746 Pearson) provides some downstream validation, but the benchmark itself is not independently verified.

4. **Inference cost is not reported.** ATF's per-query cost includes: (a) multiple forward passes (up to 4 in main experiments, more in scaling analysis), (b) Lean 4 compilation per revision attempt, and (c) multi-LLM consistency check per revision. For a method whose contribution is adding inference-time tool use, omitting any discussion of computational overhead (total forward passes, wall-clock time, API costs) is a significant gap.

5. **Statistical significance is not reported.** The Pass@k results in Table 3 are point estimates without confidence intervals or standard errors. Given stochastic sampling (temperature=0.6, 16 samples), reporting variance would help assess whether the margins are reliable.

6. **The pre-check stage in the syntax tool (Section 3.1.1) is described but not evaluated.** The paper mentions a pre-check that filters obvious errors before Lean 4 compilation but provides no ablation or statistics on how many statements are caught at this stage vs. passing through. This is relevant for understanding the tool's efficiency and reliability.

7. **The decreasing consistency success rate across revision attempts (Figure 5c, from 69.5% to 8.8%) has a plausible alternative explanation.** The paper attributes this to the model "exhausting its most confident revision strategies," but it could equally be survivor bias — remaining unsolved problems after each round are genuinely harder, so the decreasing rate reflects dataset difficulty rather than model degradation. The paper should discuss this confound.

8. **The DPO design (Section 3.2) selects trajectories with fewer revisions as positive and more revisions as negative.** This conflates "fewer revisions" with "better formalization" — but a trajectory with fewer revisions could simply be one that succeeded on an easier problem. The scaling analysis (Figure 4a) partially addresses this by showing the model still improves given more revisions at test time, but the concern is not directly discussed.

### Trivial

None.

## Nice-to-Haves

- Validate the consistency check benchmark's ground truth with human annotations on a random subset of the 800 pairs, reporting inter-annotator agreement.
- Add a controlled experiment where baselines are allowed to re-sample K times without tool feedback, to separate "tool guidance" from "having more attempts."
- Report the Pearson correlation sample size and computation details for the 0.746 value.
- Discuss why Claude-4-Sonnet was chosen for cold-start synthesis and address reproducibility implications.
- Provide decontamination details (threshold, embedding vs. string-based) in the main text since they are critical for trust in the results.

## Novel Insights

The review process surfaced an important evaluation subtlety beyond the paper's own analysis: the shared architecture between the LLM-as-judge (Qwen3-32B) and the method being evaluated (ATF, fine-tuned from Qwen3-32B) creates a potential bias amplification loop. The judge is validated on a synthetic benchmark (FPR 5.79%) and then used to evaluate models — including one fine-tuned from the same base model the judge relies on. While the human evaluation provides a sanity check, the gap between automated and human margins on CombiBench (65.38% automated vs. 49% human for ATF-32B consistency) suggests the automated evaluation may systematically favor ATF. This is a methodological lesson for the broader field of LLM-as-judge evaluation in autoformalization: when the judge and the evaluated model share base architecture, and the model is trained to satisfy that judge, the evaluation risks becoming circular. Future work should either use an architecturally disjoint judge or rely primarily on human evaluation for headline claims.

## Suggestions

1. **Foreground the human evaluation** as the primary evidence for the main results, with the automated evaluation presented as a scalable but imperfect proxy (given the judge overlap concern).
2. **Add a multi-pass baseline**: run the strongest baseline (Goedel-V2-Formalizer-32B) in a mode where it can re-sample K times without tool feedback, then compare to ATF with similar forward-pass budgets. This would distinguish "tool guidance" from "additional sampling."
3. **Report inference cost** (total forward passes, tool invocations per query, wall-clock time or token overhead) to allow readers to assess the practical trade-off.
4. **Add confidence intervals** to the Pass@k results in Table 3.
5. **Acknowledge the alternative survivor-bias explanation** for Figure 5c and discuss why the "exhausting strategies" interpretation is preferred.
