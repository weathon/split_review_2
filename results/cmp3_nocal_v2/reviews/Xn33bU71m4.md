## Summary

This paper systematically evaluates nine open-source LLMs (13B–16B parameter range) on two reverse engineering tasks — name recovery (function and variable) and type inference — using 40K function samples from GNU software compiled across four CPU architectures and multiple optimization levels. The main finding is that all models perform poorly (most F1 < 0.1), with fine-tuning providing modest but inconsistent gains. The paper contributes a standardized benchmarking framework and reports honest negative results that could guide future work.

## Strengths

- **Broad and systematic evaluation scope.** The study covers 9 models, 4 CPU architectures (x86-64, x86-32, ARM, MIPS), multiple compiler optimization levels, and 2 decompilers (Ghidra and IDA Pro), making it substantially more comprehensive than prior work in this specific sub-area of reverse engineering.

- **Honest reporting of consistently poor results.** The paper does not oversell or spin negative findings. Nearly all models score F1 < 0.1 on type inference, and even the best fine-tuned variable name recovery reaches only 0.33 — a ceiling that the paper does not disguise. This kind of calibrated negative result can save the community effort.

- **Practical automated evaluation pipeline.** Using an auxiliary LLM to standardize heterogeneous model outputs (Section 3.2) is a practical solution to a real challenge in evaluating diverse LLMs whose response formats vary widely.

- **Consistent fine-tuning comparison.** Applying LoRA fine-tuning with the same 80/20 train/test split across all models (Section 4.3) enables a fairer comparison of fine-tuning gains than prior work where each paper selects a different model and training setup.

## Weaknesses

### Fatal
None.

### Major

- **Auxiliary LLM not identified or validated (methodological confound).** The evaluation pipeline relies on an unspecified auxiliary LLM to normalize outputs (Section 3.2, lines 107–108), but the paper never identifies which model is used, quantifies its parsing error rate, or validates that it treats all target models fairly. This creates a confound: measured F1 differences between target models could partly reflect the auxiliary LLM's parsing bias (e.g., handling DeepSeek-R1's chain-of-thought differently from CodeLlama's output) rather than pure reverse engineering capability. The paper acknowledges formatting difficulties (lines 412–414) but does not bound the auxiliary model's impact on comparative results. Without this validation, fine-grained cross-model comparisons (e.g., "Qwen3 achieves the best function name recovery with an F1 of 0.06") carry unknown reliability.

- **No statistical characterization of results.** The paper reports point estimates of F1 scores without confidence intervals, standard deviations, or any discussion of LLM generation parameters (temperature, top-p, sampling strategy). The reproducibility statement (line 428) acknowledges randomness but does not bound it. Given that differences between models are often ≤0.01 (Tables 2, 4) and that the CodeWordNet F1 values in Figure 1 are reported as approximate (~0.15, ~0.12, etc.), it is impossible to assess which observations are meaningful vs. noise. This limits the actionable value of the reported comparisons.

### Minor

- **Unqualified headline result in introduction.** The introduction (line 19) states that "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." However, no such value appears in the main results tables (the highest deepseek-R1 value observed is 0.17 for variable name recovery at O0 in Table 3). Results for other architectures are in the appendix (which is stripped by the parser — see line 217), so the value may exist there, but presenting it in the introduction without specifying which task, architecture, or optimization level it applies to is unclear and leaves the reader unable to evaluate the claim from the main body.

- **No non-LLM baselines.** The paper evaluates LLMs in isolation and concludes they are "fundamentally limited," but it does not compare against any non-LLM approach — not even the decompiler's own heuristic output (e.g., Ghidra's or IDA Pro's placeholder names evaluated with the same metric). Without such calibration, interpreting what F1=0.33 means is difficult: it could be impressive for a notoriously hard task or poor compared to a simple baseline. This is outside the paper's stated scope of *LLM* benchmarking, but the title's "Not Yet" claim implicitly makes a judgment about absolute capability that requires a reference point.

- **No qualitative error analysis.** The paper reports extensive quantitative results but provides almost no analysis of failure modes. Table 8 shows four success examples; there is no systematic error taxonomy, no analysis of whether errors stem from wrong names, missing outputs, format violations, or hallucinated types. The discussion in Section 4.5 focuses on formatting issues rather than functional failure modes, which limits the actionable guidance for future work.

### Trivial

- **Inconsistent model count.** Line 19 and the conclusion (line 426) say "nine prominent LLMs," but Section 4.2 (line 143) says "eight mainstream code LLMs" while Table 1 actually lists nine entries. This is a copy-editing error.

## Nice-to-Haves

- **Ablate the auxiliary LLM confound.** Manually spot-check 200–300 normalized outputs per model to quantify the auxiliary LLM's parsing error rate, or compare results with a rule-based fallback parser for at least one model.
- **Add one traditional baseline.** Evaluating the decompiler's own placeholder-normalized output with the same CodeWordNet metric would immediately calibrate whether the LLM scores are encouraging or discouraging.
- **Report generation parameters and run variance.** State the temperature/sampling settings used and report results averaged over 2–3 runs (or at minimum provide a single-run characterization).
- **Expand error analysis.** Categorize errors (wrong name vs. missing output vs. format failure vs. hallucination) to make the results more actionable.

## Suggestions

1. Identify the auxiliary LLM and validate its parsing accuracy per target model, or replace it with a rule-based extraction fallback.
2. Qualify the 0.37 claim in the introduction by specifying the task, architecture, and setting. If the value is genuinely anomalous, explain why it differs from the x86-64 results.
3. Report generation parameters (temperature, sampling) and consider adding confidence intervals or multi-run variance estimates, at least for key comparisons.
4. Add a small error analysis section categorizing model failures to make the negative results more actionable.
5. Resolve the "eight vs. nine" count inconsistency.

## Score and Decision

The paper addresses a genuine gap and its systematic evaluation across diverse conditions is a real contribution. However, the reliance on an unvalidated auxiliary LLM for output normalization introduces unknown bias into all comparative results, and the lack of any variance reporting means the fine-grained model comparisons cannot be evaluated for reliability. These are methodological gaps that affect the confidence in the paper's central claims. The core benchmarking effort is valuable and could be strengthened with relatively focused revisions.
