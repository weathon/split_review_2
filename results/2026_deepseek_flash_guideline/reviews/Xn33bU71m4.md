## Summary
This paper systematically evaluates nine mid-sized open-source LLMs on two reverse engineering tasks (name recovery and type inference) across four architectures (x86-64, x86-32, ARM, MIPS), four optimization levels (O0-O3), and two input representations (decompiled code and assembly code), both with and without LoRA fine-tuning. The experimental scope is substantial (40K test functions, 160K training functions), and the paper documents generally low performance across all models and settings.

## Strengths
1. **Multi-dimensional controlled experimental design**: The paper evaluates 9 LLMs across 4 architectures, 4 optimization levels, and 2 input formats with 40,000 unique deduplicated function samples (Section 4.1). This breadth of controlled variables goes beyond prior work in LLM-based reverse engineering evaluation.

2. **Quantified negative result on type inference across all models**: Table 4 shows that every evaluated model — both original and fine-tuned — achieves F1 scores at or below 0.06 for type inference on x86-64, with most entries at 0.00-0.03. This is systematic evidence that current LLMs are fundamentally limited on this task.

3. **Cross-decompiler evaluation on real-world firmware**: Table 6 compares LLM performance on real firmware decompiled by both Ghidra and IDA Pro, providing practical evidence about how decompiler choice affects LLM performance — a dimension absent from most prior work.

4. **Documentation that fine-tuning can degrade performance**: Finding 1 and Tables 3-4 document cases where fine-tuning reduces F1 scores (e.g., DeepSeek-V2 drops from 0.10 to 0.05 on variable name recovery under O1; most models go to 0.00 on type inference after fine-tuning). This nuanced observation is worth reporting.

5. **Quantification of CodeWordNet's role**: Figure 1 directly compares F1 scores with and without CodeWordNet across four models, showing that removing the semantic-similarity metric causes a sharp drop (e.g., Qwen3 drops from ~0.25 to ~0.08 at O0). This demonstrates concretely why strict string matching would understate LLM capabilities.

## Weaknesses

### Fatal
None.

### Major
1. **Unexplained discrepancy between Table 2 and Figure 1**: Both Table 2 and Figure 1 report F1 scores for function name recovery on x86-64 via decompiled code. Yet the values differ by 3–5×. For example, CodeLlama at O0: 0.04 (Table 2) vs. ~0.15 (Figure 1, with CodeWordNet); Llama2 at O0: 0.01 (Table 2) vs. ~0.18 (Figure 1, with CodeWordNet). The paper provides no explanation for these differences — whether they stem from different dataset subsets, metric computation variants, prompt configurations, or something else. Since both purport to measure the same quantity, these systematically divergent numbers cannot both be correct without clarification, which undermines confidence in the experimental corpus of a measurement paper.

2. **Claims about "training data quality" exceed what the evidence supports**: Finding 4 states "training data quality is a more decisive factor" than model size, and Finding 5 claims training data quality significantly impacts performance even among models with the same architecture. However, the paper does not directly measure or control training data quality — it infers it post-hoc from performance differences between models that differ along many uncontrolled dimensions (tokenization, pre-training data distribution, instruction-tuning protocol, etc.). The evidence supports correlations, not the causal claims about "data quality" that the findings assert.

3. **No variance or confidence-interval reporting**: The paper reports single-point F1 estimates for all experiments. Given the stochastic nature of LLM generation and the random data sampling, providing error bars or variance estimates is standard practice for an empirical benchmarking paper. Without them, it is impossible to assess whether reported differences between models or conditions are meaningful above noise.

### Minor
1. **Abstract's headline claim (F1=0.37 for DeepSeek-R1) lacks traceability in the presented tables**: The abstract states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." The highest F1 for DeepSeek-R1 in the presented tables is 0.17 (Table 3, variable name recovery, O0). This value may come from results for other architectures in the appendix (stripped by the parser), but the abstract presents it without qualification, creating an appearance of inconsistency that harms trust.

2. **Auxiliary LLM extraction pipeline is unvalidated**: Section 3.2 describes using an auxiliary LLM to normalize heterogeneous model outputs. The reported F1 scores reflect a convolution of (a) the target model's actual capability, (b) the auxiliary LLM's extraction accuracy, and (c) their interaction. The paper provides no validation of this step — no precision/recall on a labeled set, no discussion of failure cases, no comparison to an alternative extraction method. For a measurement paper, an unvalidated instrument weakens trust in the reported numbers.

3. **Type inference metric is overly strict**: The metric requires exact equality including user-defined types (Section 3.4). A model that correctly identifies a type but formats it differently (e.g., `unsigned int` vs. `uint32_t`) would be penalized. This likely deflates scores, making the conclusion that "LLMs fail at type inference" partly an artifact of the metric choice.

4. **Fine-tuning degradation to 0.00 on type inference is not analyzed**: Table 4 shows fine-tuning drives most models' type inference scores to 0.00, yet the paper describes this as "limited impact" (Finding 2). The fact that fine-tuning on task-specific data makes models *worse* is a more striking and potentially informative result than "limited impact" suggests, and it merits dedicated analysis rather than a single sentence.

5. **Single prompt template may systematically disadvantage some models**: The paper uses one prompt template adopted from prior ChatGPT work (Section 3.1). Different instruction-tuned models may respond differently to the same prompt format, and no prompt-sensitivity analysis is conducted.

## Nice-to-Haves
- Adding non-LLM baselines (traditional decompiler output, prior ML approaches like SYMNN, DIRTY) would contextualize the negative results.
- Analyzing the assembly-code failures (Table 5: all 0.00 F1) — why models fail (tokenization? context length? instruction semantics?) would be informative.
- The CodeLlama size comparison (7B vs 13B vs 34B) is underpowered because all scores are near floor (0.02–0.06 F1), making conclusions about size invariance fragile.

## Novel Insights
The observation that fine-tuning *degrades* type inference performance to 0.00 for most models (Table 4) — rather than simply yielding "limited improvement" — is more striking than the paper acknowledges. This suggests a fundamental misalignment between the LoRA fine-tuning objective and the type inference task (e.g., the model may overfit to formatting patterns in the training data that do not generalize, or the task signal may be too sparse for LoRA to capture). This finding, if properly analyzed, could be a genuine insight about the limits of fine-tuning for structured prediction tasks in decompiled code.

## Suggestions
1. **Reconcile the Table 2 vs. Figure 1 discrepancy**. Explain whether these use different subsets, metrics, or prompt settings. If they differ by experimental condition (e.g., Table 2 uses one scoring variant and Figure 1 another), state this explicitly.
2. **Validate the auxiliary LLM extraction pipeline** on a labeled sample (100–200 responses) and report extraction precision/recall.
3. **Add confidence intervals or error bars** for the main result tables.
4. **Analyze the fine-tuning degradation on type inference** (Table 4) rather than describing it as "limited impact" — the degradation to 0.00 is the more interesting result.
5. **Tone down causal claims about "training data quality"** (Findings 4–5) to match correlational evidence.
