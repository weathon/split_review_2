## Summary
EditBench is a new benchmark for evaluating LLMs on instructed code editing tasks, constructed from real-world data collected via a purpose-built VSCode extension used by ~500 developers. It comprises 540 problems (109 core unique problems translated into 5 natural languages) spanning Python and JavaScript, encompassing four task categories: feature addition, feature modification, bug fixing, and optimization. The authors evaluate 40 diverse LLMs and report findings on the importance of contextual information (highlighted code, cursor position) and category-level performance.

## Strengths
- **In-the-wild data collection methodology is genuinely novel for code editing benchmarks.** Recruiting ~500 real developers who used the extension for their actual workflows (as opposed to paid annotators on artificial tasks) produces instruction diversity that is empirically demonstrated in Table 2 — real instructions are terse, context-dependent, and often include raw error traces rather than clean NL descriptions.
- **The context ablation study (Table 3) is insightful and actionable.** Demonstrating up to 8 percentage points of performance swing based on whether highlighted code/cursor position is provided, and showing that the *direction* of the effect is model-dependent (o3-mini and qwen3-coder are hurt by highlighted context), reveals non-trivial differences in how models use IDE context — this has real implications for tooling.
- **Breadth of model evaluation (40 models across families, sizes, and training regimes) is commendable** for a benchmark paper and makes comparisons robust. The gap between closed and open models, and the category-specific performance differences (Figure 5), provide concrete empirical signals.
- **The low correlation with Aider Polyglot (r=0.24, not significant) and Chatbot Arena (r=0.11)** empirically substantiates the claim that EditBench captures a distinct evaluation dimension not measured by existing tools. This is a positive finding, not a weakness.
- **IRB-approved data collection and explicit PII removal** reflect good practice for a dataset built from user data.

## Weaknesses

### Fatal
None.

### Major
- **The 540-problem count is misleading.** The benchmark's actual unique content is 109 core problems; the other 431 entries are GPT-4o translations of these problems into four other languages. The translation is validated only on a "subset" (Section 3.2), primarily in Chinese and Spanish. This means the claimed multilingual diversity is largely synthetic and generated by the same model family used as a top-performing baseline. The benchmark presents itself as having 5 natural languages collected in-the-wild, but only English problems were naturally sourced — the others are model-generated derivatives. This conflation should be made explicit up front.

- **The test harness creation process may introduce systematic bias toward particular solution styles.** Section 3.3 acknowledges annotators were given example solutions from GPT-4o and Sonnet-3.7 "to give insight into possible solutions." This risks annotators inadvertently encoding assumptions matching those models' solution patterns into the test cases, which would inflate those models' scores and penalize different-but-correct implementations. The paper does not investigate or rule out this confounder.

### Minor
- **Restricting to Python and JavaScript** while the collected data covers PHP (18%), HTML (7%), and other languages means the benchmark does not fully represent the diversity of real-world coding (a limitation the paper acknowledges, but it is worth noting that the claimed comprehensiveness over "real-world use cases" is somewhat diluted by this constraint).
- **The finding that `gpt-5` with default reasoning underperforms `gpt-5-mini`** (Section 5.1) is reported with an informal qualitative explanation (struggles with indentation, edge cases) rather than any systematic analysis. This is an interesting anomaly that deserves more rigorous examination (e.g., examining error types quantitatively across difficulty bins).
- **The weak correlation with Polyglot (r=0.24, p=0.06)** is also consistent with the hypothesis that EditBench is noisy rather than measuring a distinct construct. The paper offers explanations rooted in task design but does not present evidence that rules out the alternative.

### Trivial
- The bar chart descriptions in the figure captions repeat essentially the same content as the alt-text; this could be streamlined.

## Nice-to-Haves
- A test of inter-annotator agreement on the test harnesses across the 5 annotators would significantly strengthen confidence in benchmark reliability.
- Reporting model-level statistics on *how many test cases* each problem has (or variance in the number of tests) would help understand whether performance differences might be driven by heterogeneous problem difficulty encoding.
- Including an analysis of whether translated problems show different per-model performance distributions than original English problems would either validate or raise concerns about the translation quality for evaluation purposes.

## Novel Insights
The most genuinely novel insight is the empirically demonstrated model-specificity of contextual sensitivity: some models (o3-mini, qwen3-coder) actively *hurt* performance when given highlighted code context, while others benefit. This suggests that different pretraining/fine-tuning regimes lead to qualitatively different strategies for integrating IDE context, which is not captured by existing benchmarks and has direct implications for how these models should be deployed in coding assistants. The complementary finding that "hard" problems have shorter instructions but longer highlighted code — forcing multi-source reasoning rather than instruction-following — provides a useful diagnostic for what makes instructed code editing difficult.

## Suggestions
- Clearly distinguish EditBench-core (109 problems, all English, in-the-wild) from EditBench-complete (540 problems, multilingual via translation) in all result tables, and report primary results on EditBench-core to avoid inflating problem count.
- Conduct a contamination audit by checking whether any collected code snippets appear in training data of the top-ranked models (e.g., via substring matching on public code corpora) — given that problems come from real projects, this is a legitimate concern.
- Provide ablation showing how correlated English vs. translated-language performance is per model, to verify that multilingual expansion is evaluating language handling rather than identical problems.

## Score and Decision
EditBench is a well-motivated benchmark paper targeting an underserved but practically important evaluation niche. The in-the-wild data collection methodology is the paper's principal contribution and is executed with appropriate rigor (IRB, privacy controls, human annotators with double-review). The 40-model evaluation is thorough and the contextual information ablation is a concrete novel finding. The primary weakness — that the claimed 540-problem multilingual benchmark is largely 109 unique problems padded via synthetic translation — is significant but does not invalidate the core contribution, especially since the paper acknowledges it. The test harness quality concern is mitigated by the double-review annotation process. Overall this is a solid, useful benchmark contribution that the community would benefit from.
