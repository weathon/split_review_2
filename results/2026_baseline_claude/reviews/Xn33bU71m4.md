## Summary

The paper systematically evaluates nine mid-sized open-source LLMs (CodeLlama, Llama2, WizardCoder, DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, Phi4, Gemma3) on two binary reverse engineering tasks: name recovery (function and variable names) and type inference. Using 40,000 decompiled functions from GNU binaries spanning four ISAs and four compiler optimization levels, and augmented with real-world firmware evaluation, the paper concludes that all tested LLMs perform poorly (F1 < 0.1 without fine-tuning), and that LoRA fine-tuning yields modest and inconsistent gains.

---

## Strengths

- **Scale**: Evaluating nine models across four architectures, four optimization levels, two decompilers, and two tasks (name recovery + type inference) constitutes one of the more comprehensive empirical studies on LLMs for binary RE. The decision to cover both decompiled-code and assembly-code input representations is principled.
- **Automated post-processing pipeline**: Using an auxiliary LLM to normalize heterogeneous outputs across models is a practical engineering contribution that others in the community can adopt for future benchmarking.
- **Useful secondary findings**: Finding 7 (fine-tuning time is highly sensitive to prompt template design, with up to 4× overhead) and the IDA Pro vs. Ghidra quality comparison are concrete, actionable observations not widely documented elsewhere.

---

## Weaknesses

### Fatal

None that fully invalidates the contribution, but two severe issues together nearly rise to this level.

### Major

1. **Numerical inconsistency between abstract/introduction and experimental tables.** The abstract and Introduction both state: *"after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37."* However, Table 3 (variable name recovery, fine-tuned, x86-64) shows DeepSeek-R1 at F1 = 0.17 (O0), 0.05 (O1, O2), and 0.05 (O3) — the best fine-tuned variable name recovery numbers (0.33) belong to Qwen2.5, WizardCoder, and Phi4, not DeepSeek-R1. No table in the main paper shows DeepSeek-R1 reaching 0.37 on any task. Even if this figure originates from an appendix result on a different architecture, prominently citing it in the abstract while the main tables contradict it is misleading and erodes trust in the reported numbers.

2. **Evaluation metric inconsistency between main tables and Figure 1.** The paper characterises CodeWordNet as *"essential for fair evaluation"* of name recovery and integrates it into the SYMLM-based metric. Yet Table 2 reports function name recovery F1 for CodeLlama (original, O0, x86-64) as 0.04, while Figure 1's accompanying data shows CodeLlama "with CodeWordNet" achieving ~0.15 on the same setting. The discrepancy — roughly 3-4× — suggests that Tables 2–3 do not actually apply CodeWordNet, whereas Figure 1 does. The paper never clarifies which metric governs which table. If the main tables use strict string matching, then (a) the paper's claim that CodeWordNet is the fairness-enabling metric is undermined by its own experimental protocol, and (b) all cross-table comparisons are internally inconsistent.

3. **No comparison to specialized baselines.** The paper's central thesis is that "LLMs are not yet effective for reverse engineering," but this is evaluated in an absolute vacuum. SYMGEN, ReSYM, VARBERT, SymLM, and other methods are mentioned in Related Work, yet their performance figures are never cited alongside the LLM results. Without knowing whether these specialized systems achieve 0.4, 0.6, or 0.8 on the same tasks, it is impossible to contextualize the LLMs' 0.03–0.33 range — whether it represents a large gap or near parity with the state of the art.

4. **Uniform 0.00 assembly results warrant investigation.** Table 5 reports exactly 0.00 for all nine models across all optimization levels on assembly-based function name recovery, both original and fine-tuned. Across 40,000 functions, not a single correct prediction is credited to any model. The paper briefly explains "predictions are too sparse to register," but this is suspicious: even common libc functions (e.g., `main`, `printf`, `malloc`) should occasionally be predicted correctly by models trained on code. No diagnostic is provided to confirm this is a real capability gap and not an artifact of the evaluation pipeline (e.g., format extraction failure before scoring).

### Minor

1. **Type inference fine-tuning degradation is unexplained.** For most models (DeepSeek-V2, DeepSeek-R1, Qwen3, Phi4, Gemma3), fine-tuning drives type inference F1 to 0.00 — worse than the original models. The paper attributes this to strict exact-match evaluation criteria, but this criterion applies equally to original and fine-tuned models; it cannot explain why fine-tuning is actively harmful. Whether fine-tuned models are generating wrong answers with higher confidence, over-producing user-defined type tokens, or formatting outputs in ways the post-processor cannot parse is not analyzed.

2. **Prompt engineering is treated as fixed.** The paper adopts a single existing ChatGPT prompt template without any prompt optimization. Given that Finding 7 shows prompt templates can change fine-tuning time by 4×, prompt choice is clearly impactful. Interpreting results as a capability ceiling for LLMs, when the ceiling may reflect a fixed suboptimal prompt, weakens the conclusion's strength.

3. **Hardware and reproducibility details are incomplete.** Table 7 reports fine-tuning times but omits GPU model, VRAM, batch size, and precision settings — information necessary for others to reproduce or situate these numbers.

### Trivial

- Table numbering appears out of order in the paper (Table 6 appears before Table 5 in the rendered document), likely a parser artifact.

---

## Nice-to-Haves

- A precision/recall decomposition to accompany F1, especially for type inference (e.g., whether models are generating primitive types correctly but failing only on user-defined types).
- Error analysis on assembly: confirm (even for a small sample) that the 0.00 result reflects genuine semantic failure, not pipeline failure.

---

## Novel Insights

The most actionable observation beyond the paper's stated contributions is that training data distribution (code-specialization) matters more than parameter count *and* more than architecture across this narrow-range size band (~12B–16B). CodeLlama (13B) outperforms the same-architecture Llama2 (13B), and Qwen2.5 (14B) outperforms DeepSeek-R1 (14B, fine-tuned on Qwen2.5 for reasoning). This suggests that even modest domain alignment during pre-training can outweigh substantial post-hoc RLHF-style training in specialized low-resource binary analysis tasks — a moderately interesting observation for practitioners choosing base models for fine-tuning. However, the scope is limited and the evidence is correlational, so this remains a suggestive empirical finding rather than a controlled insight.

---

## Suggestions

- Reconcile the DeepSeek-R1 0.37 claim with the table data; if this comes from an appendix architecture, state so explicitly and report results for all models on that architecture.
- Clearly define which tables use CodeWordNet-based scoring and which use strict string matching; use a single consistent metric throughout.
- Include at least one specialized baseline (e.g., VARBERT or ReSYM) on a comparable subset of the dataset to contextualize the LLM numbers.
- Investigate the assembly 0.00 result with a manual sample to confirm it is a genuine model failure.
- Provide a breakdown of type inference errors by category (primitive vs. composite vs. user-defined types) to clarify where fine-tuning fails.

---

## Score and Decision

The paper addresses a genuine need — systematic, model-agnostic benchmarking of LLMs for binary reverse engineering — and the experimental scale is commendable. However, two major issues significantly undermine confidence in the reported findings: (1) the abstract/introduction's DeepSeek-R1 F1=0.37 claim contradicts the experimental tables, and (2) the CodeWordNet evaluation metric is apparently applied inconsistently between Figure 1 and Tables 2–3, making it unclear what the main tables actually measure. These are not presentation issues; they concern the correctness and internal consistency of the primary empirical contribution. Combined with the absence of specialized-method comparisons (which would be essential for interpreting whether these numbers are "low" or "competitive"), the paper requires substantial revision before it meets ICLR standards.
