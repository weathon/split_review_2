## Summary

This paper presents a systematic evaluation of nine mid-sized open-source LLMs (CodeLlama, Llama2, DeepSeek-R1, Qwen2.5, Qwen3, WizardCoder, Phi4, Gemma3, DeepSeek-V2) on two binary reverse engineering tasks: name recovery (function and variable names) and type inference. The evaluation spans four architectures (x86-64, x86-32, ARM, MIPS), four optimization levels (O0–O3), two input representations (decompiled code and assembly code), and two decompilers (Ghidra, IDA Pro) on real-world firmware. Both zero-shot and fine-tuned (LoRA) settings are tested. The main finding is that all evaluated models perform poorly across nearly all settings, with most F1 scores below 0.10 in zero-shot and only modest improvements after fine-tuning.

## Strengths

- **Substantial evaluation breadth.** The paper tests 9 LLMs across 4 architectures (x86-64, x86-32, ARM, MIPS), 4 optimization levels (O0–O3), 2 input representations (decompiled/assembly), and 2 decompilers (Ghidra, IDA Pro) on real-world firmware — exceeding the scope of most individual RE studies. [favorability=10.86]

- **Fine-tuning experiments with LoRA across all 9 models** provide a consistent comparison of fine-tuning benefits, revealing interesting patterns such as large O0-specific variable-name recovery gains (e.g., Qwen2.5 from 0.01→0.33, WizardCoder from 0.01→0.33) that collapse at O1–O3. [favorability=10.75]

- **The automated evaluation pipeline using an auxiliary LLM for output normalization** addresses a genuine practical challenge in comparing heterogeneous model outputs, even though its accuracy is not separately validated. [favorability=7.98]

- **Identifies a genuine gap in the literature.** Prior RE work selects LLMs without clear rationale (e.g., SYMGEN picks CodeLlama-34B, RESYM picks StarCoder-3B for unstated reasons), motivating the need for systematic benchmarking. [favorability=6.61]

## Weaknesses

### Fatal
None.

### Major

- **Abstract makes an unsupported quantitative claim.** The abstract states that "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37" (line 19). This number does not appear in any main-paper table — Table 2 (function name recovery, best fine-tuned = 0.05), Table 3 (variable name recovery, best fine-tuned = 0.17), Table 4 (type inference, best fine-tuned = 0.06), Table 5 (assembly, all 0.00), or Table 6 (firmware, which has no fine-tuned column). The paper states that results for other architectures are in the appendix, but the abstract presents this as a headline finding without any table reference or disambiguation, making it unverifiable from the main paper. [favorability=0.22]

- **Metric ambiguity between Tables 2–4 and Figure 1.** Section 3.4 describes CodeWordNet (semantic similarity with partial credit) as the name recovery evaluation method. However, Table 2's function name recovery F1 scores (0.00–0.07) are roughly 3–4× lower than Figure 1's "w CodeWordNet" values (~0.08–0.25) and align much better with Figure 1's "wo CodeWordNet" values (~0.02–0.08). The paper never states whether Tables 2–4 use CodeWordNet or exact matching. A reader cannot determine what the reported F1 scores actually measure. [favorability=1.74]

- **No statistical analysis.** The paper reports point estimates without confidence intervals, standard deviations, or significance tests. Since most zero-shot F1 scores cluster between 0.00–0.07, differences like 0.03 vs. 0.05 may not be meaningful. The paper's stated goal is to help researchers "make informed model selections" (line 89), but without statistical characterization, the benchmark cannot reliably differentiate between models at these low values. [favorability=-1.54]

### Minor

- **Data contamination not discussed.** The dataset is GNU software (open-source, widely distributed). All evaluated LLMs were pretrained on code from the internet almost certainly including GNU code. The paper does not address how contamination might affect the reported scores. [favorability=4.80]

- **Fine-tuning generalization concern.** The paper does not specify whether training and test functions come from different projects (line 186 only guarantees non-overlap at the sample level). If the same projects appear in both, fine-tuning gains (e.g., Qwen2.5 from 0.01→0.33 at O0) could partly reflect memorization rather than general capability. This suspicion is reinforced by the extreme variability across optimization levels — the same model that jumps to 0.33 at O0 collapses to 0.05–0.10 at O1–O3. [favorability=6.03]

- **Auxiliary LLM pipeline not validated.** The output normalization uses an auxiliary LLM, but its error rate and potential biases toward certain output formats are not measured, introducing an unquantified source of noise. [favorability=5.94]

- **Prompt inconsistency for DeepSeek-R1.** The paper modified DeepSeek-R1's prompt to suppress chain-of-thought reasoning (line 412), while other models used a different template. This breaks prompt uniformity and could affect relative performance. [favorability=6.67]

- **CodeWordNet ablation limited in scope.** The analysis (Figure 1) is restricted to x86-64 and only 4 models, yet the paper presents it as demonstrating that "CodeWordNet is essential for fair evaluation" without evidence that the pattern generalizes. [favorability=0.75]

## Suggestions

- Add a table reference in the abstract for the 0.37 DeepSeek-R1 result (or correct it if it is an error).
- Explicitly state whether Tables 2–4 use CodeWordNet or exact matching; report both if feasible.
- Add bootstrapped confidence intervals or standard deviations to help interpret small differences between models.
- Discuss data contamination risks from the GNU dataset.
- Validate the auxiliary LLM normalization pipeline.
- Use the same prompt template for all models or provide a controlled justification for any deviation.

### Score Determination

**Round 1 bracket:** 3.5–5.0

The paper's breadth (9 models × 4 architectures × 4 opt levels × 2 representations) and clear problem motivation place it above the 3.5–3.75 anchors, which had more fundamental novelty/contribution questions. However, the paper is below "To Err is Machine" (5.00) because that paper provided deeper error analysis and diagnostic breakdowns despite a narrower scope, while this paper has two unresolved structural issues that directly affect result interpretability.

**Narrowing:** Comparing favorability-rated items, this paper's most damaging weaknesses (abstract claim at 0.22, metric ambiguity at 1.74, no statistical analysis at -1.54) are collectively more negative than "To Err is Machine"'s worst items (-0.69, 0.61). The structural issues are fixable but currently prevent a reader from fully trusting the reported numbers. The CodeWordNet ablation restriction (0.75) further limits confidence in the metric's deployment in main results.

The paper's strengths (10.86, 10.75) are genuinely high and reflect real engineering effort and scope. This creates a split: substantial work undermined by presentation and methodological gaps that can be repaired.

**Final score:** 4.0 — Borderline reject. The paper addresses a real gap and puts in substantial evaluation effort, but the combination of an unsupported headline quantitative claim, unresolved metric ambiguity, and absent statistical analysis prevents the benchmark from providing reliable guidance for model selection — its stated purpose. With the metric ambiguity resolved, the abstract claim substantiated, and appropriate statistical characterization added, this could become a solid 5–6 paper.
