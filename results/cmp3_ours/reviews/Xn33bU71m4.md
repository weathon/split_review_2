## Summary

This paper evaluates nine open-source mid-sized LLMs (12B–16B) on two core reverse engineering tasks — name recovery (function and variable) and type inference from stripped binaries — across four architectures (x86-64, x86-32, ARM, MIPS) and four optimization levels (O0–O3), using both decompiled code and assembly input. The main finding is that all models perform poorly in the zero-shot setting (F1 < 0.1), with fine-tuning yielding only inconsistent and generally modest improvements. The paper's contribution is a systematic benchmarking framework and a body of honest empirical evidence to inform model selection in the reverse engineering community.

## Strengths

- **Well-motivated problem.** Section 2 convincingly identifies that prior work (e.g., SYMGEN's CodeLlama-34B, RESYM's StarCoder-3B) selects models for fine-tuning without explicit rationale, and that the field lacks a systematic comparison. This gap is real and worth filling.

- **Broad and systematic coverage.** Nine models spanning three years (2023–2025), multiple families (CodeLlama, Llama, DeepSeek, Qwen, Phi, Gemma, WizardCoder), four architectures, four optimization levels, two input representations (decompiled code and assembly), and two decompilers (Ghidra and IDA Pro for real-world firmware). Table 1 and the experiment design reflect substantial effort.

- **Honest reporting with no result inflation.** The paper consistently presents low F1 scores across all tables and explicitly states that current LLMs are not yet effective for these tasks. The negative result is clearly documented, which is valuable for the community.

- **Real-world validation.** Table 6 evaluates models on actual firmware using two different decompilers, adding ecological validity to the benchmark.

## Weaknesses

### Major

**1. The auxiliary LLM used for output extraction is neither identified nor validated.** The evaluation pipeline (Section 3.2, lines 107–108) relies on an unnamed auxiliary LLM to parse heterogeneous model outputs into a standardized format. The paper provides no accuracy evaluation of this extraction step, no discussion of how extraction errors propagate into precision/recall/F1, and does not identify which model serves this role. Since the paper itself states that model outputs "often deviate from the requested format, include extraneous explanations, or vary between short tokens and full sentences" (line 105) — precisely the conditions where an extraction LLM would be most error-prone — this is a critical gap. Without validation of the extraction pipeline, the numerical precision of all reported scores carries unknown error bars. This is the most significant methodological concern in the paper.

### Minor

**2. The introduction's headline F1 score of 0.37 for DeepSeek-R1 (line 19) is not traceable in the main result tables.** The highest F1 score for DeepSeek-R1 in any main table is 0.17 (Table 3, variable name recovery, O0, fine-tuned). The paper does state that additional architecture results are in the Appendix (line 217), which was stripped by the parser, so supporting data may exist there. However, a headline quantitative claim should be clearly anchored in the presented results. As written, a reader comparing the introduction against the tables will find this claim unverifiable.

**3. A single fixed prompt template is used across all models without per-model optimization (Section 3.2, line 103).** The paper adopts a prompt adapted from a GPT-3.5 study without optimizing for each model. Finding 7 (Section 4.5) shows that prompt template design can change fine-tuning time by 4×, and the paper had to modify the template for DeepSeek-R1 to suppress chain-of-thought reasoning (line 412), acknowledging that one template does not fit all. Models with different pretraining distributions are at an inherent disadvantage, confounding model-to-model comparisons.

**4. The assembly-code experiment (Table 5) reports 0.00 F1 for all models without failure-mode analysis.** The paper does not investigate why — whether inputs exceed context windows, assembly tokenization is poor, the prompt is mismatched, or the extraction pipeline fails on assembly outputs. A null result with no analysis of *why* is substantially less informative than it could be.

**5. Reproducibility is insufficiently supported for a benchmark paper.** The reproducibility statement (line 428) is a single sentence ("The result can be reproducible by executing the identical scripts") with no repository link, dataset URL, or code release. For a paper whose main contribution is a benchmark and empirical findings, this makes it difficult for the community to build on the results.

## Suggestions

1. **Validate the extraction pipeline.** Identify the auxiliary LLM and measure its extraction accuracy on a labeled sample of 100–200 responses. Report the error rate and discuss how it affects the reported F1 scores.
2. **Anchoring the 0.37 claim.** Either cite the specific appendix table that supports it, or correct the number to match what the main tables show.
3. **Provide a repository link** with code, prompts, and at minimum a representative sample of the dataset to support reproducibility.
4. **Add per-model prompt sensitivity analysis** or, at minimum, discuss how the fixed template may bias the comparison.
5. **Analyze failure modes for assembly-code results** to turn the null result into an explanatory finding rather than a flat zero.
