## Summary
This paper presents a systematic benchmark evaluating nine open-source mid-sized LLMs (12B–16B parameters) on reverse engineering tasks: function name recovery, variable name recovery, and type inference from decompiled and assembly code. The evaluation spans four architectures, multiple optimization levels, and includes a real-world firmware test. The central finding is that current LLMs perform poorly on these tasks, with most F1 scores below 0.06 without fine-tuning and remaining largely below 0.10 even after fine-tuning, with assembly-code function name recovery yielding 0.00 F1 across all models.

## Strengths
- **Systematic multi-model comparison**: The paper evaluates nine distinct LLMs on the same dataset of 40,000 functions across four architectures and multiple optimization levels, providing the first standardized comparison of its kind for reverse engineering. Tables 1–6 present side-by-side F1 scores across all model × optimization-level combinations.

- **Multi-task, multi-representation experimental design**: Evaluates function name recovery, variable name recovery, and type inference using both decompiled code and assembly code, plus real-world firmware with two decompilers (Ghidra and IDA Pro). This breadth ensures the negative findings are not an artifact of a single narrow setting.

- **Honest reporting of negative results**: The assembly-code results (Table 5) show 0.00 F1 for every model — a stark, verifiable finding. The paper does not inflate or cherry-pick results to make performance look better than it is.

- **CodeWordNet ablation (Figure 1)**: Quantifies how much of measured name-recovery performance is attributable to the soft-matching metric versus strict string matching, providing transparency about evaluation sensitivity.

- **Qualitative examples (Table 8)**: Concrete side-by-side comparisons of original vs. fine-tuned model predictions against ground truth make the performance differences interpretable.

## Weaknesses

### Fatal
None.

### Major
- **Numerical discrepancy between Table 2 and Figure 1**: Both report function name recovery F1 on x86-64 using CodeWordNet-based evaluation, yet the numbers differ by 3–5× with no explanation. For example, Qwen3 at O0 scores 0.05 in Table 2 but ~0.25 in Figure 1; DeepSeek-V2 at O0 scores 0.01 in Table 2 but ~0.20 in Figure 1. The paper describes both as x86-64 experiments using CodeWordNet, but never acknowledges or explains why they differ so dramatically. Since the paper's primary output is these numerical comparisons, an unexplained 3–5× gap between two tables reporting the same task on the same architecture undermines trust in the quantitative results.

### Minor
- **Unverifiable headline claim**: The introduction (line 19) states that fine-tuned DeepSeek-R1 reaches an F1 score of 0.37, but the highest DeepSeek-R1 score anywhere in the body of the paper is 0.17 (Table 3, variable name recovery, O0). The claimed 0.37 may be reported in the appendix for a different architecture, but the body provides no evidence for the paper's central framing claim. This creates a disconnect between the paper's framing and its visible evidence.

- **No non-LLM baselines**: The paper claims LLMs perform "poorly," but whether an F1 of 0.05 is poor depends on task difficulty. A simple heuristic (e.g., majority-class prediction, frequency-based name matching) would contextualize the absolute scores. Without any baseline, the reader cannot distinguish "LLMs are unsuited to this task" from "this task is intrinsically very difficult."

- **Auxiliary LLM for post-processing is unidentified**: Section 3.2 describes using an auxiliary LLM to normalize heterogeneous model outputs into a consistent format. The identity of this auxiliary model is never disclosed, which affects reproducibility and introduces an unquantified confound.

- **Fine-tuning hyperparameters not reported**: The paper uses LoRA fine-tuning for 200 steps on 160,000 functions (Section 4.3). Key hyperparameters — learning rate, batch size, LoRA rank, LoRA alpha — are never specified. Without these, the fine-tuning results are not reproducible, and the conclusion that "fine-tuning has limited impact" could reflect insufficient training rather than a fundamental limitation.

- **Only F1 reported, no precision/recall**: The paper states (line 139) that models are evaluated using "precision, recall, and F1 score," but all tables report only F1. Without precision and recall, the reader cannot determine whether low F1 is driven by poor precision, poor recall, or both.

### Trivial
- Dataset drawn exclusively from GNU software projects; generalizability to other codebases (embedded systems, proprietary software) is not discussed.
- No measure of variance reported despite the reproducibility note acknowledging results will vary due to randomness.

## Nice-to-Haves
- Reporting fine-tuning results across all architectures (not just x86-64) would strengthen the paper's generalizability claims.
- A systematic failure-mode analysis beyond the four cherry-picked examples in Table 8 would add insight.
- Disclosing the auxiliary LLM used for post-processing and characterizing its error rate would improve reproducibility.

## Novel Insights
The paper's most interesting finding is not just that LLMs perform poorly, but the specific pattern of failure: fine-tuning on variable name recovery produces dramatic but brittle improvements (e.g., WizardCoder jumps from 0.01 to 0.33 at O0, but drops to 0.08 at O3), while type inference barely budges under any condition. This asymmetry — that name recovery is somewhat trainable while type inference is not — is not highlighted by the authors but emerges from the data and suggests a fundamental difference in how LLMs represent semantic identifiers versus structural type constraints in decompiled code.

## Suggestions
- Resolve and explain the Table 2 / Figure 1 discrepancy. If the experiments use different data subsets, models, or evaluation procedures, state this explicitly. If one set of numbers is incorrect, correct it before publication.
- Clarify where the 0.37 F1 claim comes from — which task, architecture, and optimization level — or remove it if it cannot be substantiated.
- Add at least one simple baseline (e.g., always predict `int` for type inference, frequency-based name heuristics for name recovery) to contextualize the absolute F1 scores.
- Report precision and recall alongside F1, or explain why only F1 is shown across all tables despite the claim that all three are computed.
- Disclose the auxiliary LLM used for post-processing and report fine-tuning hyperparameters for reproducibility.
