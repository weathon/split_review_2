## Summary
This paper evaluates nine open-source mid-sized LLMs on two binary reverse-engineering tasks — name recovery and type inference from stripped binaries — across four ISAs (x86-64, x86-32, ARM, MIPS), four optimization levels, and both zero-shot and LoRA fine-tuned settings. The central message is that current LLMs perform poorly on these tasks even after fine-tuning, with the goal of providing principled model selection guidance for the reverse-engineering community.

## Strengths
- **Large-scale cross-architecture evaluation**: 40,000 functions spanning x86-64, x86-32, ARM, and MIPS at four optimization levels provides genuine breadth uncommon in this niche area.
- **Real-world firmware experiment** (Table 6): Evaluating on actual stripped firmware using both Ghidra and IDA Pro outputs distinguishes this work from purely synthetic evaluations. The consistent IDA Pro > Ghidra gap across most models and tasks is a practically useful finding.
- **Zero-shot + fine-tuned comparison across nine models**: Fine-tuning all models with LoRA enables distinguishing pre-training capability from task-adaptable potential, which is more informative than zero-shot-only work.

## Weaknesses

### Fatal
- **The headline claim in the abstract is directly contradicted by the reported data.** The introduction states: *"after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37."* Table 3 (Variable Name Recovery, x86-64) shows DeepSeek-R1's best fine-tuned score is **0.17** (at O0). The 0.33 scores are achieved by Qwen2.5, WizardCoder, and Phi4 — not DeepSeek-R1. No table in the paper shows DeepSeek-R1 at 0.37. For a benchmarking paper whose core contribution is accurate comparative measurement, having the single most prominently stated empirical result be contradicted by the tables is a fundamental validity problem.

### Major
- **Fine-tuning runs for only 200 gradient steps with no convergence evidence.** Table 7 confirms all fine-tuning results are from 200 steps. With 160,000 training functions and 12–16B parameter models (LoRA), 200 steps is a tiny fraction of one epoch. No learning curves, validation loss plots, or ablation on step count are provided. The paper's central conclusion — *"fine-tuning has limited impact"* and *"gains are inconsistent"* — is drawn from potentially severely undertrained models. Anomalies such as DeepSeek-V2 variable name recovery dropping by 50% under O1 after fine-tuning (Table 3), and six models reaching 0.00 type inference after fine-tuning (Table 4), are precisely what undertraining artifacts look like. Without evidence of convergence, the fine-tuning conclusions cannot be trusted.

- **Figure 1 vs. Table 2 inconsistency is unexplained.** Figure 1 compares "w CodeWordNet" vs. "wo CodeWordNet" for function name recovery. The bar chart (as described in the paper) shows CodeLlama "w CodeWordNet" at approximately 0.15 at O0 on x86-64. But Table 2 reports CodeLlama function name recovery on x86-64 at O0 as 0.04 (Orig). Since Section 3.4 establishes CodeWordNet as the default name evaluation method, Table 2 should already incorporate it. These two numbers cannot both be correct for the same model, task, and architecture. The paper provides no reconciliation.

### Minor
- **Type inference degrades to 0.00 for fine-tuned models across the board** (Table 4: DeepSeek-V2, DeepSeek-R1, Qwen2.5, Qwen3, WizardCoder, Phi4, Gemma3 all reach 0.00 after fine-tuning). This striking result receives only a one-sentence acknowledgment. Given the 200-step constraint, it likely reflects undertraining, but the paper doesn't investigate.
- **No prompt ablation for the benchmarking comparisons.** Section 3.2 adopts a prompt from a Notion page designed for ChatGPT without conducting ablations across models. Cross-model comparisons partly reflect prompt-model compatibility differences rather than intrinsic capability, particularly for instruction-following format variation.
- **Finding 5 is asserted without evidence.** The claim that DeepSeek-R1 underperforms Qwen2.5 due to its reinforcement-learning training ("training optimization") is stated as a finding but has no supporting quantitative analysis.

### Trivial
- Dataset homogeneity not acknowledged: results derive entirely from GNU software, and generalization to commercial or obfuscated binaries is unaddressed.

## Nice-to-Haves
- Learning curves showing when/whether fine-tuned validation performance plateaus — this would make the fine-tuning analysis interpretable.
- Separate reporting of type inference for primitive vs. user-defined types; near-zero scores on strict user-defined type matching conflates evaluation difficulty with model capability.
- A concrete model selection recommendation table (given a fixed compute budget, which model + decompiler is best for each task?) — this would deliver on the stated goal of "principled model selection."

## Novel Insights
The consistently higher performance of IDA Pro over Ghidra as input representation across models and tasks (Table 6) is a practically useful finding that practitioners can act on immediately, independent of the fine-tuning analysis. The uniformly zero assembly-code performance (Table 5) across all nine models quantifies a practitioner intuition at larger scale than previous work.

## Suggestions
1. **Fix or explain the DeepSeek-R1 = 0.37 claim** — this is the most urgent correction before any resubmission; it is impossible to trust the rest of the numbers without resolving it.
2. **Train to convergence or provide learning curves** — even extending to 2,000 steps with a validation curve would substantially change the interpretation of all fine-tuning results.
3. **Reconcile Figure 1 with Table 2** — explain what experiment Figure 1 actually depicts and whether it uses the same conditions as the main tables.
4. **Decompose type inference by primitive vs. user-defined types** — this would make the near-zero results informative rather than just indicating evaluation difficulty.
