## Summary
This paper evaluates nine open-source mid-sized LLMs (e.g., CodeLlama, Llama2, DeepSeek-R1) on two reverse engineering tasks—name recovery and type inference from stripped binaries across multiple architectures and optimization levels. The authors show that zero-shot performance is very low (F1 ≈ 0.01–0.06) and that fine-tuning with LoRA provides measurable but still modest improvements (best F1 ≈ 0.33 for variable names). They conclude that current LLMs are not yet capable of performing these reverse engineering tasks reliably.

## Strengths
- **First systematic multi-model evaluation for these RE tasks:** The paper addresses an important gap in the literature by comparing nine LLMs on the same benchmark, covering name recovery and type inference simultaneously.
- **Covers multiple architectures and optimization levels:** The dataset is built from binaries compiled for x86-64, x86-32, ARM, and MIPS, with O0–O3 optimization, providing a more thorough assessment than prior work.
- **Automated evaluation pipeline:** The use of an auxiliary LLM to normalize responses and the CodeWordNet-based metric for name recovery addresses the variance in LLM output formats, making the comparison more consistent.

## Weaknesses
### Fatal
The fine-tuning experiments are conducted for only **200 training steps** (as reported in Table 7). For a dataset of 160,000 function samples, this is far below the amount of training typically required for convergence—even with LoRA. The authors provide no justification that 200 steps is sufficient (e.g., loss curves, learning rate schedule, evidence of convergence). This invalidates any conclusions drawn about the efficacy (or lack thereof) of fine-tuning for these tasks. The claim that “fine-tuning provides limited gains” is not supported by the experimental design.

### Major
- **Lack of comparison to non-LLM baselines:** The paper measures absolute F1 scores but does not compare LLM performance against traditional machine learning methods (e.g., SYMLM, Debin, or other specialized neural models) or even rule-based decompiler output. Without such context, it is unclear whether the near-zero scores reflect a weakness of LLMs specifically or the intrinsic difficulty of the tasks.
- **No prompt tuning or ablation:** Only a single prompt template (taken from a prior ChatGPT study) is used for all models. Given that LLMs are highly sensitive to prompt design, the poor performance may be partially an artifact of suboptimal prompting. The paper does not explore how prompting affects the results, nor does it attempt to optimize prompts per model.
- **Auxiliary LLM for output parsing is not validated:** The paper relies on another LLM to normalize responses but provides no evaluation of that parser’s accuracy or failure cases. Errors in the parsing stage could systematically lower or inflate the reported F1 scores.
- **Dataset composition and generalizability:** The primary dataset is constructed from GNU software projects. While the authors include a small real-world firmware test (again with near-zero scores), the overall evaluation may not represent the variety of code found in real reverse engineering scenarios (e.g., obfuscated code, proprietary binaries). The negative conclusion might be valid only for this specific source.

### Minor
- **Incomplete reporting of experimental details:** The paper does not specify batch size, number of epochs, LoRA rank/alpha, learning rate, or hardware configuration for fine-tuning. This makes reproducibility uncertain.
- **Table 5 is ambiguous:** It reports only a single column for assembly-based function name recovery across all optimization levels (O0–O3). The authors should clarify whether results are averaged or if each optimization level was tested separately but returned identical zero values.
- **The CodeWordNet impact analysis (Figure 1) shows values (e.g., ~0.15 for CodeLlama) that are much higher than the zero-shot scores in Table 2 (which are ≤0.06).** This discrepancy is not discussed; the figure seems to report on a different experimental condition (perhaps using a different metric or subset), confusing the reader.

### Trivial
- The paper states it evaluates nine models, but Table 1 lists nine names, while some sections (e.g., the abstract) mention three families. This inconsistency is cosmetic.

## Nice-to-Haves
- It would be informative to include human expert performance or the performance of state-of-the-art non-LLM tools (e.g., Debin, SYMLM) on the same dataset to calibrate the difficulty.
- An analysis of why fine-tuning helps for variable name recovery (e.g., O0) but hurts type inference would strengthen the paper’s contribution.
- The authors could explore whether chain-of-thought prompting or providing contextual hints (e.g., calling convention clues) improves results.

## Novel Insights
None beyond the paper’s own contributions—mainly a confirmation that today’s mid-sized LLMs, even after a short fine-tuning, perform poorly on named entity recovery and type inference from stripped binaries.

## Suggestions
- **Redo the fine-tuning experiments with a proper training setup:** Use more steps, monitor convergence, report training curves, and justify the stopping point. Without that, the fine-tuning results are uninterpretable.
- **Add baselines:** Include at least one traditional ML method (e.g., a simple classifier using assembly n-grams) or a specialized neural model from the RE literature to give context to the near-zero scores.
- **Validate the auxiliary parser:** Compare the parsed outputs against manual ground truth for a random subset to ensure the evaluation metric itself is not noisy.
- **Perform prompt search:** Try different prompt formulations (e.g., explicit format requirements, few-shot examples) to see whether performance can be improved without changing the model.

## Score and Decision
The core flaw—insufficient fine-tuning—undermines the paper’s main claims about the limited effectiveness of fine-tuning. Together with missing baselines and unvalidated evaluation components, the contribution is not sufficiently supported for acceptance at ICLR.
