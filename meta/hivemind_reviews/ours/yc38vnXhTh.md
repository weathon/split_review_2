## Summary

This paper presents ACTOR, an LLM-powered agent for human behavior simulation in 3D scenes that operates via a perceive-plan-act cycle with value-driven tree search (MCTS), hierarchical activity priors, and customizable value functions. It also introduces BehaviorHub, a large-scale automatically generated dataset of 10k scene-conditioned human behavior samples across 1.5k scenes. The agent is evaluated on behavior planning and simulation metrics, with ablations and downstream task experiments demonstrating the utility of both the architecture and the dataset.

## Strengths

1. **Value-driven planning with dual evaluation types**: The agent combines real-valued functions (e.g., shortest path) with language-based value prompts (e.g., "neat person" description) to evaluate candidate behaviors (§4.2). This design is well-motivated and the ablations (Table 3a) show it provides the largest performance gain — GSR jumps substantially when the value function is added (row 3→4), directly confirming that environment-grounded evaluation is the key differentiator over ungrounded LLM planning.

2. **Large-scale, automatically generated behavior dataset**: BehaviorHub contains 10k behavior samples covering 2k activities across 1.5k scenes with 8.6M motion frames (§5.3) — an order of magnitude larger than the human-authored ActivityPrograms. The dataset's utility is independently validated via downstream tasks (Table 4): pre-training on BehaviorHub improves FID on PROX scene-aware motion generation (11.36→10.02) and HumanML3D language-conditioned motion generation (0.65→0.54), demonstrating concrete value beyond the paper's own evaluation.

3. **Human evaluation confirms automatic metric trends**: Five human raters (Table 2) consistently rank ACTOR above LLMaP and HuggingGPT on completeness (3.05 vs. 2.23, 2.71), rationality (3.47 vs. 2.48, 2.89), and motion quality (3.75 vs. n/a, 3.18). This provides subjective evidence that the automatic evaluation framework is reliable and that ACTOR produces more plausible behavior simulations.

4. **Thorough ablation and diagnostic experiments**: The paper systematically ablates each component (Table 3a: bare baseline → active tree search → hierarchical prior → value function), compares search algorithms (Table 3b), and tests modular scalability across LLM cores (Table 3c). This gives a clear picture of which design choices drive performance.

## Weaknesses

### Fatal

None.

### Major

1. **Evaluation circularity for text-based planning metrics**: The ground-truth linguistic plans in BehaviorHub's main set are generated by an LLM (the paper states it "distill[s] the tree-structured linguistic plans of human daily behaviors from LLM using in-context learning" in §1, and seeds from ActivityPrograms are augmented with LLM-generated samples in §5.1). The text-based evaluation metrics (Sentence-BLEU, BERTScore in Table 1) measure alignment with these LLM-generated plans, and ACTOR itself uses a GPT-4-family LLM as its core. This creates a circular validation loop: the metric rewards ACTOR for reproducing outputs similar to those of its own underlying model family.  
   **Mitigation**: The simulation metrics (GSR, SSR) are based on physical task completion via contact distance thresholds (§5.4), which is not circular. The dynamic subset (300 manually configured samples) partially addresses this, though the paper does not state whether the ground-truth plans for these 300 samples are human-authored or LLM-generated. The human evaluation (Table 2) provides independent evidence. However, the headline claim of "nearly doubling the overall success rate" rests partly on metrics that are weakened by this concern. This is the single most impactful weakness.

2. **Baseline selection is not strong for this task**: LLMaP is a text-only procedural planning model (the paper acknowledges it "lacks the capability to perform behavior simulation" in §6.1). HuggingGPT is a general tool agent not designed for 3D behavior simulation. Neither baseline incorporates environment dynamics, hierarchical decomposition, or motion execution — precisely the innovations ACTOR introduces. The comparison therefore conflates the advantage of having a purpose-built system with the advantage of the specific architectural choices. The paper's own ablation (Table 3a, row 1: bare baseline one-pass LLM planner, GSR 24.3) would have been a more informative competitor in Table 1. While the ablations partially fill this gap, including a more purpose-built baseline (e.g., an LLM planner with hierarchical decomposition but without tree search and value functions) would better isolate the contribution of the active planning loop.

### Minor

1. **Dynamic subset ground-truth provenance unclear**: The paper states that the 300 dynamic samples are "manually create[d]" with "state-aware triggers" (§6.1), but it does not state whether the ground-truth *plans* for these samples are human-authored or LLM-generated. If they are LLM-generated, the circularity concern persists even on this subset. The authors should clarify this explicitly.

2. **Value function probability conversion is ad-hoc**: The language-based command outputs ("sure/more-likely/less-likely/impossible") are converted to fixed probabilities 1.0/0.7/0.3/0.01 with no sensitivity analysis or justification (§4.2). While this is a reasonable starting point, the paper does not test whether results are robust to these specific values.

3. **MCTS vs. beam search margin is small**: In the search algorithm comparison, the difference between MCTS and beam search is small (exact values depend on which subset; the diagnostic results in Table 3b show moderate gaps on the Dynamic subset). The paper's claim that "MCTS shows optimal results" is correct, but the advantage is not clearly decisive, and no statistical significance or variance is reported. This weakens the claim that the choice of search algorithm is critical.

4. **Motion generation models are fine-tuned on BehaviorHub asymmetrically**: The action stage uses off-the-shelf models that are fine-tuned on BehaviorHub (§4.3), while the baselines (LLMaP, HuggingGPT) do not have access to BehaviorHub for motion generation. The paper compares ACTOR's full pipeline (with BehaviorHub-fine-tuned motion models) against baselines that lack this advantage. This asymmetry should be acknowledged and the downstream task experiments (Table 4) partially address this concern by demonstrating BehaviorHub's standalone value.

### Trivial

- The probability values 1.0/0.7/0.3/0.01 for language-based value commands are mentioned without any reference or empirical basis.
- Minor: The paper refers to Table numbers inconsistently in one place (the text refers to "Table 4b" when discussing key component analysis, but the table is labeled "Table 3 (a)").

## Nice-to-Haves

- A human evaluation of plan *correctness* on a random sample of BehaviorHub linguistic plans (not just ACTOR's plans) would strengthen the dataset's credibility as ground truth.
- Reporting variance or confidence intervals for key comparisons (especially MCTS vs. beam search) would clarify whether observed differences are meaningful.
- An ablation varying the language command probability values (1.0/0.7/0.3/0.01) would demonstrate robustness.

## Suggestions

1. **Address the circularity concern directly**: State clearly whether the ground-truth plans for the Dynamic subset are human-authored. If they are, highlight this prominently. If they are not, commission a small human-annotated held-out set (even 50 samples) for the text-based planning metrics to provide an independent anchor for those numbers.

2. **Include the bare baseline (one-pass LLM planner) in Table 1**: The ablation baseline from Table 3a (GSR 24.3 on Dynamic) would be a more meaningful reference point than LLMaP or HuggingGPT for understanding ACTOR's improvement. Consider adding this as a row or noting it in the discussion.

3. **Clarify the GSR definition**: Explicitly state whether GSR measures completion of the agent's own plan or the ground-truth plan, and whether the metric depends on matching ground-truth step labels or only on physical completion via contact thresholds. This would directly address the circularity concern.

4. **Add sensitivity analysis for value function probabilities**: Briefly test whether varying the language command probability values (1.0/0.7/0.3/0.01) materially changes results, even as a single ablation in the appendix.

5. **Acknowledge the fine-tuning asymmetry**: Explicitly note that ACTOR's motion generation models are fine-tuned on BehaviorHub while baselines are not, and clarify how this affects the comparison.

## Score and Decision

The paper tackles a genuinely difficult and important problem with a well-motivated architecture and a large-scale dataset that demonstrably benefits downstream tasks. The weaknesses — primarily the evaluation circularity for text-based planning metrics and the weak baselines — are real but not fatal: the simulation metrics (GSR, SSR) rely on physical task completion in the simulator, the human evaluation provides independent validation, and the downstream task experiments (Table 4) prove BehaviorHub's value on entirely independent tasks. The ablations effectively isolate the contribution of each component. With clarifications on these points, the paper constitutes a solid contribution.
