## Summary

The paper evaluates nine open-source large language models (CodeLlama, Llama2, DeepSeek variants, Qwen variants, WizardCoder, Phi4, Gemma3) on two binary reverse engineering tasks—name recovery (function and variable names) and type inference—using both decompiled and assembly code. The authors develop an automated evaluation pipeline and test models in zero-shot and fine-tuned (LoRA) settings across four architectures and multiple optimization levels. The main finding is that current LLMs perform poorly on these tasks (F1 scores mostly below 0.1 for zero-shot, and only modest improvements after fine-tuning, with the best fine-tuned variable name recovery reaching F1 ~0.33). The paper also reports that model size does not correlate with performance and that training data quality is more important.

## Strengths

- **Addresses an important gap**: The paper systematically benchmarks LLMs for two core reverse engineering tasks where model selection has been arbitrary. This is the first large-scale comparative evaluation of this scope in the domain.
- **Comprehensive experimental design**: The evaluation covers 9 models, 4 CPU architectures, multiple optimization levels, both decompiled and assembly input formats, and includes real-world firmware. The use of LoRA for efficient fine-tuning and CodeWordNet for semantic name matching is methodologically sound.
- **Transparent negative results**: The paper honestly reports that all models perform poorly, even after fine-tuning, and documents inconsistent improvements. This negative finding is valuable to prevent the community from overestimating LLM capabilities in this area.

## Weaknesses

### Fatal

- **Unsubstantiated claim about DeepSeek-R1 F1 score**: The abstract and introduction state that "DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." However, the experimental tables (Table 3, Table 2, Table 4) show the highest F1 for DeepSeek-R1 is 0.05 (function name recovery), 0.17 (variable name recovery), and 0.03 (type inference)—none reaching 0.37. This claim is not supported by any presented result and appears to contradict the paper's own data. Such a discrepancy undermines the credibility of the core message.

### Major

- **Unexamined auxiliary LLM bias**: The evaluation pipeline uses an auxiliary LLM to normalize model outputs into a consistent format. The paper does not validate the accuracy of this auxiliary model, nor does it discuss how errors in normalization could propagate into the final metrics. This introduces an uncontrolled source of measurement error that could affect all reported scores.
- **Overly strict type inference metric**: The evaluation requires exact matches for primitive and user-defined types. Given that user-defined types are often arbitrary and context-specific, and that LLMs may infer semantically equivalent but differently named types, this metric is likely too harsh and may understate true capability. No sensitivity analysis or softer matching is provided.
- **Limited investigation of fine-tuning failure**: Fine-tuning sometimes _decreases_ performance (e.g., DeepSeek-V2 variable name recovery at O1: 0.10 → 0.05). The paper acknowledges this but provides no analysis of why, leaving the practical utility of fine-tuning unclear. The use of only 200 fine-tuning steps without convergence checks is also a concern.
- **Dataset representativeness**: The dataset is drawn primarily from GNU software. These projects are well-represented in LLM training data, yet performance is still near zero. This raises questions about the generalizability of the results to commercial or proprietary firmware (the real-world firmware evaluation shows similarly poor results, but details on that dataset are sparse).

### Minor

- **The paper claims to extend name recovery to all functions within a function body** (calling functions), but the results do not separately analyze this aspect, making it unclear whether the task formulation affects performance compared to prior work.
- **The "Findings" in Section 4.4 are presented as summaries of the data but some are not fully supported** (e.g., Finding 1 states "gains are inconsistent and not guaranteed"—this is accurate, but the discussion does not quantify how often fine-tuning helps vs. hurts across all settings).

### Trivial

- The prompt template and fine-tuning time are highly model-dependent, but the paper does not provide the exact templates used, making reproducibility harder.

## Nice-to-Haves

- **Validate the auxiliary LLM**: Run a small human evaluation on a subset of outputs to measure normalization accuracy.
- **Report type inference with partial matching**: Show results when exact match is relaxed to include category-level correctness (e.g., "integer" vs. "int").
- **Analyze error cases**: Categorize why models fail (e.g., wrong names vs. missing predictions vs. format errors).
- **Provide fine-tuning loss curves** to confirm convergence at 200 steps.

## Novel Insights

None beyond the paper's own contributions. The core observation that current LLMs are ineffective for these reverse engineering tasks is consistent with the poor reported scores, but this is a negative result that the community already suspected. The finding that training quality matters more than model size and that fine-tuning can be detrimental in some cases is modestly novel but insufficiently explored.

## Suggestions

- **Retract or clarify the DeepSeek-R1 0.37 claim**: If this number comes from a different experiment (e.g., a different metric or task), explicitly state it. Otherwise, remove the claim, as it directly contradicts the presented data.
- **Acknowledge the limitations of strict type matching** and report a secondary analysis using a softer metric (e.g., matching base types, ignoring user-defined sub-names).
- **Validate the output normalization pipeline** either by human inspection or by comparing results with a hand-crafted parser for a subset of models.

## Score and Decision

**Score**: 3  
**Decision**: Reject

**Reasoning**: The paper tackles a relevant and underexplored evaluation problem, and the experimental effort is commendable. However, the fatal inconsistency between the claimed DeepSeek-R1 F1 of 0.37 and the actual results in the tables invalidates a core motivation and erodes trust in the reported numbers. Additionally, the unvalidated auxiliary LLM pipeline and the overly strict type metric raise concerns about measurement validity. The negative findings are useful, but they are not presented with sufficient rigor to outweigh these flaws. With corrections and additional validation, a revised version could be suitable for a future venue.
