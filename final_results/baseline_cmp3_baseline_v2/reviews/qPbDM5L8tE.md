## Summary

CoRAL is a modular neuro-symbolic framework for contact-rich robotic manipulation that decouples high-level reasoning from low-level control. It integrates FoundationPose for 6-DoF tracking, a VLM (GPT-4o) for physical parameter estimation, an LLM for generating cost functions and contact strategies for a Model Predictive Path Integral (MPPI) controller, and a memory unit for experience reuse. Evaluated in a simulated MuJoCo environment on six challenging tasks, the paper shows advantages over end-to-end VLA baselines and demonstrates that each component (separated vision/LLM roles, online refinement, memory, dedicated pose estimation) is necessary for robust performance.

## Strengths

- **Modular neuro-symbolic design** that clearly separates perceptual grounding (vision+VLM) from strategic reasoning (LLM+MPPI cost function), enabling zero-shot execution without task-specific training data.
- **Comprehensive ablation studies** that convincingly demonstrate the necessity of each architectural component: separated VLM/LLM roles, online LLM-driven refinement, experience memory, and dedicated pose estimation.
- **Challenging task suite** including multi-stage reasoning (push-then-pick), force control, and contact-rich tool-use (flip with wall) that are genuinely difficult for end-to-end models.
- **Explainability potential** shown through natural language failure diagnosis and adaptive parameter correction, which is a practical advantage over black-box policies.

## Weaknesses

### Fatal
None.

### Major
1. **Simulation-only evaluation severely limits the strength of the empirical claims.** All experiments are conducted in MuJoCo simulation with idealized physics, perfect state information from the simulator, and no hardware noise. For a framework claiming *“robust execution”* and *“adaptive manipulation”* in real-world contact-rich scenarios, the absence of any real-robot validation leaves the core claims untested. The simple reactive feedback augmentation (Eq. 7) may not compensate for the sim-to-real gap in friction, compliance, or sensing.
2. **Excessive execution time makes the system impractical.** CoRAL takes 45–212 seconds per successful trial (Table 1), while end-to-end baselines complete tasks in 5–13 seconds. Even taking into account that CoRAL is doing more online planning, the paper does not analyze the time budget per component (perception, MPPI sampling, LLM API calls, etc.) or discuss how latency could be reduced. This is a critical practical concern for dynamic manipulation.
3. **Unfair baseline comparison.** The end-to-end VLA baselines (OpenVLA, π0.5) are evaluated zero-shot on custom tasks that differ substantially from their LIBERO training distribution. A more informative comparison would include fine-tuning these models on the same tasks or comparing on a shared benchmark. The human-expert baselines partially address this, but the paper overstates its advantage by claiming it “significantly outperforms” baselines on tasks where the baselines were never trained. The human-expert FSM baseline actually outperforms CoRAL on several tasks (e.g., T1: 8/10 vs 4/10), showing the LLM-based cost generation is not yet at expert level.
4. **Lack of reliability analysis for LLM-generated outputs.** The LLM produces cost functions (Eq. 2) and contact strategies (Eq. 3) that directly determine controller behavior. The paper does not report how often the LLM produces a syntactically valid cost function, how many retries are needed, or the variance in output quality across runs. This makes it difficult to assess the reproducibility or robustness of the approach.

### Minor
- Only 10 trials per condition, which is low for statistical significance; confidence intervals are absent.
- Memory unit implementation is vague (retrieval mechanism, indexing, capacity). The improvement from memory is modest (2/10→4/10 on T1), and the paper does not characterize retrieval failures.
- The actual cost functions generated by the LLM for each task are not shown, only an illustrative example.

### Trivial
- The framework uses pre-trained foundation models; “zero-shot” is a reasonable term here but could be more carefully scoped to the specific tasks.
- Figure 2 has small text that is hard to read.

## Nice-to-Haves
- A real robot experiment on at least one or two tasks (e.g., push and pick) to validate sim-to-real transfer.
- Wall-clock time breakdown: perception latency, MPPI sampling time, LLM API call duration, total planning vs execution time.
- Error analysis: frequency and severity of LLM failures (invalid cost functions, hallucinated parameters) and their impact on success rate.

## Novel Insights

The key insight is the two-level feedback architecture: a high-frequency inner loop (MPPI re-planning) and a low-frequency outer loop (LLM-driven re-strategizing). This allows the LLM to not only set initial cost function weights and contact priors but also to diagnose failures and correct the internal world model (mass, friction) mid-execution. This goes beyond prior work where LLMs only provide high-level task decomposition or static cost maps. The demonstration that separating VLM (perception) from LLM (reasoning) is critical for performance, and that a unified VLM fails catastrophically, is a concrete architectural lesson.

## Suggestions

1. Add at least one real-robot experiment, even on a simplified subset of tasks, to substantiate the robustness claims.
2. Provide per-component latency analysis and discuss how the pipeline could be accelerated (e.g., smaller LLM, fewer MPPI samples, GPU parallelization).
3. Improve baseline fairness by fine-tuning VLA models on the same tasks or by comparing on a standard benchmark (e.g., LIBERO tasks) where both approaches can be evaluated fair.
4. Increase the number of trials and report confidence intervals (e.g., via bootstrapping) to quantify uncertainty in success rates.
5. Show example LLM outputs (cost functions, contact strategies) for one or two tasks to give readers a concrete sense of how the LLM performs.

## Score and Decision

The paper proposes a reasonably novel modular architecture with careful ablations. However, the simulation-only evaluation, excessive runtime, and unfair baseline comparisons significantly weaken the empirical support for the claimed advantages. While the ideas are interesting, the evidence is insufficient to recommend acceptance at ICLR.
