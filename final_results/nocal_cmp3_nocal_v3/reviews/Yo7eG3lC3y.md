## Summary

This paper introduces LEGO-EVAL, a tool-augmented evaluation framework for assessing fine-grained text-to-3D-scene alignment, and LEGO-BENCH, a benchmark of 130 instructions with 1,250 fine-grained constraints covering floor layout, material selection, object selection, and object placement. LEGO-EVAL decomposes evaluation into constraint identification, tool execution planning, argument selection, and validation, using 21 tools across three types (Environment Interaction, Textual Reasoning, Multimodal Reasoning). The method achieves 0.81 holistic F1 and 0.63 Cohen's κ against human judgments, substantially outperforming VLM-as-a-judge baselines (0.40 F1, 0.05 κ). Benchmarking existing scene generation methods reveals success rates ≤10%.

## Strengths

- **Well-motivated problem with concrete failure evidence.** The paper demonstrates specific failure modes of CLIPScore and VLM-as-a-judge (e.g., hallucinating objects, misidentifying components, failing at multi-hop spatial reasoning) through clear examples in Figures 1 and 8. The need for fine-grained evaluation of text-to-3D alignment is convincingly established.

- **Principled tool-augmented architecture.** Rather than asking a monolithic VLM to reason holistically from renderings, LEGO-EVAL decomposes evaluation into modular steps—constraint identification, tool planning, argument selection, and validation—with 21 tools that explicitly ground scene components via object lists, coordinate checks, color verification, and spatial relation queries. This directly addresses known VLM limitations on 3D spatial understanding.

- **Strong quantitative headline results.** LEGO-EVAL with GPT-4.1 achieves 0.81 holistic F1 and 0.63 Cohen's κ vs. 0.40 and 0.05 for the best VLM-as-a-judge baseline (Table 1). The ablation study (Table 2) confirms that all three tool types contribute, with Environment Interaction being the largest contributor (24.9% drop when disabled). These gaps are large enough to be meaningful even accounting for evaluation-design considerations.

- **LEGO-BENCH fills a genuine gap.** The benchmark provides 130 fine-grained instructions averaging 9.6 constraints each, spanning architectural components (39%), object selection (23.3%), floor layout (21.8%), and material selection (15.4%), with manually curated ground-truth scenes. This is more diagnostic than existing coarse-description benchmarks for 3D scene synthesis.

## Weaknesses

### Fatal

None.

### Major

- **Case study reveals a contradictory judgment (Figure 8).** LEGO-EVAL outputs "Valid ✓" alongside the reasoning: "Since neither object is present, there is no way to assess whether the flashlight and the laptop are facing the same way. This means the constraint cannot be satisfied." If the constraint cannot be satisfied, the correct judgment is "Invalid ✗" (as the paper's own framework defines: "A scene is deemed valid only if it fulfills all constraints"—§3.1 Step 4). The paper's text then describes LEGO-EVAL as "accurately recognizing the absence of both objects and determining the constraint cannot be satisfied." This is a direct contradiction between the output label and both the stated reasoning and the paper's own description. Two possibilities exist: either LEGO-EVAL has a logical error that would produce false positives on any constraint where required objects are absent (systematically inflating its reported accuracy), or this is a figure formatting error. Either way, the paper must transparently address this before its core claims can be properly evaluated.

### Minor

- **Refinement experiment (§5) underspecifies the feedback mechanism.** The paper states: "we use LEGO-EVAL to evaluate scenes generated by Holodeck, then provide feedback to refine invalid scenes. We iterate this refinement process 3 times." It does not specify who or what performs the refinement—is an LLM prompted to modify the scene based on LEGO-EVAL's explanations? Is it the original generation method with added constraints? Without this detail, the comparison between LEGO-EVAL and VLM-as-a-judge as feedback signals is hard to interpret or reproduce.

- **Ground-truth provenance for the component analysis (Table 5) is unspecified.** The analysis of tool planning and argument selection uses "ground-truth" execution plans and "human-annotated tool execution plan[s]," but no details are provided on how these annotations were created, by whom, or how consistency was ensured. This makes the reported GED and F1 correlations difficult to assess.

- **No error analysis of LEGO-EVAL's own failures.** The paper never discusses where LEGO-EVAL itself makes mistakes—what constraint types produce false positives or false negatives, or how its per-category performance varies. Without this, the reader cannot judge whether LEGO-EVAL is genuinely reliable or merely better than very weak baselines.

- **No variance reporting for main results.** LLM-based planning has inherent variance from API sampling, but the paper does not report standard deviations or confidence intervals for the F1 and κ scores in Table 1. It is unclear whether the reported values are stable across runs.

- **Sample sizes for complexity analysis (Figure 6) are unreported.** The paper splits 130 instructions into simple (2–7), moderate (8–12), and complex (13+) bins but does not report N per bin or confidence intervals. The extreme bins could be quite small, making the sharp decline in success rates less conclusive.

### Trivial

- The method description (§3.1) would benefit from at least one complete tool execution trace for a single constraint, showing all four steps with concrete inputs and outputs.

## Nice-to-Haves

- Runtime and cost analysis: LEGO-EVAL executes up to 21 tools with multiple LLM calls; the community would benefit from knowing the cost per evaluation relative to VLM-as-a-judge.
- Per-category F1 breakdown for LEGO-EVAL by constraint type (Floor Layout, Material Selection, etc.) beyond the aggregate Partial F1.
- Fully isolated ablation of Environment Interaction tools (the current "w/o E + M" condition conflates two tool types).

## Suggestions

1. **Resolve the Figure 8 contradiction immediately.** Either correct the output label if it is a formatting error, or document and fix the logical bug in LEGO-EVAL if "Valid ✓" is actually the system's output for this case. This is the highest-leverage fix.
2. **Document the refinement mechanism** used in the feedback experiment, even briefly (one sentence stating what model/pipeline performs the refinement).
3. **Add a brief note on annotation procedures** for the ground-truth scenes, constraints, and tool execution plans—at minimum, the number of annotators and how consistency was maintained.
4. **Include variance estimates** (e.g., standard deviations over multiple runs or bootstrap confidence intervals) for the main evaluation results in Table 1.
