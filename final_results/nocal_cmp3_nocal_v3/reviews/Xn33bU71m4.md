## Summary

This paper systematically evaluates nine open-source LLMs (12B–34B parameters) on two binary reverse engineering tasks — name recovery and type inference — across four architectures, four optimization levels, two input representations (decompiled code and assembly), and real-world firmware with two decompilers. Models are tested in both zero-shot and LoRA-fine-tuned settings. The paper finds that all models achieve low F1 scores without fine-tuning, and fine-tuning yields modest but inconsistent improvements.

## Strengths

1. **Fills a genuine gap in the literature.** Prior LLM-based reverse engineering work selects models arbitrarily (e.g., SYMGEN uses CodeLlama-34B, ReSYM uses StarCoder-3B) without justification. The paper correctly identifies that this lack of systematic comparison makes the field hard to interpret. The motivation (Section 2) is well-articulated.

2. **Evaluation is broad along meaningful dimensions.** Nine models, four architectures, four optimization levels, two input representations, and real-world firmware with Ghidra and IDA Pro. This is more comprehensive than any single prior study in this space.

3. **Practical post-processing pipeline (Section 3.2).** LLMs produce wildly inconsistent output formats. The solution — using an auxiliary LLM to normalize responses — is sensible and practically useful for anyone running similar evaluations.

4. **Honest documentation of practical failure modes.** The observations about inconsistent output formatting (Finding 8), DeepSeek-R1's refusal responses and excessive chain-of-thought (Section 4.5), and the sensitivity of fine-tuning time to prompt templates (Finding 7) are genuinely useful and not typically reported.

### Major

1. **Unresolved inconsistency between Table 2 and Figure 1 for the same metric on the same data.** Table 2 reports F1 scores for function name recovery on x86-64 decompiled code (e.g., CodeLlama O0 Orig: 0.04; Llama2 O0 Orig: 0.01; Deepseek-V2 O0 Orig: 0.01; Qwen3 O0 Orig: 0.05). Figure 1 (tabular data below it) reports the same metric with CodeWordNet and yields values 3–10× higher (CodeLlama O0: ~0.15; Llama2 O0: ~0.18; Deepseek-V2 O0: ~0.20; Qwen3 O0: ~0.25). Section 3.4 defines the primary metric as using CodeWordNet, yet Table 2's values are closer to Figure 1's "without CodeWordNet" values — and even those do not match for two of the four models. The paper offers no explanation. This must be resolved for the core quantitative results to be trusted.

2. **Introduction claims "F1 score of 0.37" for fine-tuned DeepSeek-R1 without specifying provenance.** Line 19 states "after fine-tuning, DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." No table in the main text reports this value. The x86-64 results show DeepSeek-R1 fine-tuned achieving at most 0.05 (function names, Table 2), 0.17 (variable names, Table 3), 0.01 (type inference, Table 4), and 0.07 (firmware, Table 6). The paper notes that results for other architectures are in the appendix (which was stripped by the parser), so the 0.37 may come from ARM/MIPS results. However, presenting this as a headline without specifying which task and architecture produced it is misleading. The reader cannot evaluate a central advertised result.

### Minor

3. **Single-prompt zero-shot evaluation without sensitivity analysis.** The paper uses one prompt (drawn from prior ChatGPT work) for all nine models (Section 3.2, "Rather than optimizing prompts, we adopt an established reverse engineering prompt"). LLMs are sensitive to prompt phrasing; a prompt designed for ChatGPT may disadvantage CodeLlama, Llama2, or DeepSeek-R1. The paper itself reports prompt sensitivity for training time (Finding 7) and modified the prompt for DeepSeek-R1. A small control experiment (2–3 prompt variants on a 500-sample subset) would substantially strengthen the claim that low scores reflect fundamental model limitations rather than prompt mismatch.

4. **Fine-tuning protocol lacks convergence validation.** Models are fine-tuned for a fixed 200 steps with no learning curves, no convergence analysis, and no hyperparameter details beyond "LoRA." Some models perform worse after fine-tuning (e.g., DeepSeek-V2 at O1 on variable name recovery drops from 0.10 to 0.05 in Table 3). Without convergence validation or basic hyperparameter sweeps, the modest gains (and occasional losses) may reflect a suboptimal training setup rather than fundamental limits of fine-tuning.

5. **Title is broader than the evidence.** The title evaluates "LLMs" generally, but the study covers only open-source models in a narrow size range (12B–34B), explicitly excluding ChatGPT, GPT-4, and Claude. While the exclusion is justified, the framing should match the scope.

6. **No variance or statistical significance reporting.** With F1 scores as low as 0.00–0.05 for zero-shot results, it is impossible to assess whether differences between models or conditions are meaningful or just noise. The paper does not state how many runs were performed.

## Novel Insights
Beyond the paper's own contributions, the most interesting meta-observation from the reviews is that the paper's strongest negative empirical finding (models are universally poor at reverse engineering) may be partially confounded by its evaluation design. The Table 2 / Figure 1 inconsistency and the single-prompt protocol both raise the possibility that the reported near-zero scores reflect evaluation artifacts (metric inconsistency, suboptimal prompt) rather than intrinsic model limitations. The paper would benefit from a controlled experiment isolating these confounders before drawing strong conclusions about LLM capability limits.
