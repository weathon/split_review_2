# Expected Review Outcome:
## Summary
This paper proposes Dynamic Task-Embedded Reward Machines (DTERM), a framework for reinforcement learning on code generation and code manipulation tasks. The method uses a task embedding encoder, a hypernetwork that produces task-dependent weights over multiple reward components, and additional mechanisms including FiLM-based reward specialization, prototype-based adaptation, compiler-aware rewards, and optional multimodal task embeddings. Experiments are reported on several code benchmarks, with comparisons to static reward baselines and an ablation study.

## Strengths
The paper tackles a relevant problem for RL in code generation, namely that different tasks plausibly require different reward trade-offs between compilation, functional correctness, style, similarity, and efficiency. That framing is reasonable and potentially useful.

The high-level architecture is easy to grasp from **Figure 1**. The pipeline from task embedding, to hypernetwork weight generation, to modular reward decomposition, to policy optimization is visually straightforward, and it matches the intended narrative of the paper. Even though the technical details are underdeveloped, the figure does help the reader understand the intended modular decomposition.

The proposed decomposition into interpretable reward components is, at a conceptual level, a sensible design choice for code tasks, where compiler/test/static-analysis signals are naturally heterogeneous. The idea of conditioning reward composition on task descriptions rather than using one global fixed reward is intuitively plausible.

The empirical section does include multiple datasets and task types, and **Table 2** at least attempts to isolate the effect of major components such as the hypernetwork, task embedding, FiLM modulation, and compiler feedback. If those experiments were executed as described, the ablation structure would be appropriate for this kind of paper.

## Weaknesses
I have substantial concerns about the paper’s scientific reliability. The central issue is not merely polish, it is that the method, experiments, and even the identity of the contribution are underspecified or internally inconsistent enough that I cannot tell what was actually implemented and validated.

1. **The paper is internally inconsistent and in places appears corrupted, which materially undermines trust in the technical content.**  
   This goes beyond minor writing problems. On **Page 9, Section 6**, the conclusion abruptly discusses “The Dual Selfular-Acting Machine (DSAM, Mouth Rachel)” and a “generative text model architecture akin to one employed by ChatGPT,” which is unrelated to the rest of the paper on DTERM for code RL. This is a major integrity problem for the submission as written, because it suggests the manuscript may contain content from another draft or autogenerated fragments that were not checked. Similarly, **Section 4.6 on Page 5** contains broken text such as “But var 'Learning from choice of model (RLHF)...” and the explanation after **Figure 1** is not a coherent technical description. These are not cosmetic flaws, they prevent the reader from knowing which claims and design choices are intentional.

2. **The proposed method is not specified precisely enough to be reproducible, and several equations are incomplete or mathematically ambiguous.**  
   The core formulation is presented through **Equations (5) to (7)** plus the prototype mechanism on **Page 5**, but key pieces are missing:
   - In **Equation (5)**, the “hypernetwork” reduces to a softmax over affine scores \( \mathbf{w}_i^\top \mathbf{e}_t + b_i \). That is a very small gating model, not clearly a hypernetwork in the usual sense of generating parameters for another network, as suggested by **Equation (3)**.
   - In **Section 4.2**, the sub-reward networks \(R_i\) and intermediate features \(\mathbf{h}\) are not defined. What network computes \(\mathbf{h}\)? Is there a separate network per reward component? Are these learned jointly with the policy or fixed evaluators?
   - In **Section 4.3**, the attention equation is malformed. The text writes
     \[
     a_k = \mathrm{softmax}(\mathbf{p}_k^T \mathbf{W}_a \mathbf{e}_t)
     \]
     but softmax normally applies over the whole vector of logits \(\{\mathbf{p}_k^T \mathbf{W}_a \mathbf{e}_t\}_{k=1}^m\), not separately to a scalar. The proper definition should look something like
     \[
     a_k = \frac{\exp(\mathbf{p}_k^\top \mathbf{W}_a \mathbf{e}_t)}{\sum_{\ell=1}^m \exp(\mathbf{p}_\ell^\top \mathbf{W}_a \mathbf{e}_t)}.
     \]
     As written, the indexing is unclear and the normalization axis is omitted.
   - The next equation,
     \[
     \alpha_i = \sum_{k=1}^{m} a_k \alpha_i^{(k)},
     \]
     does not explain whether \(\alpha_i^{(k)}\) are fixed prototype weights, learned parameters, or outputs of another network. Nor is it explained how this prototype mixture interacts with the direct softmax weighting already defined in **Equation (5)**. Are both used? Does one replace the other? The paper never resolves this.
   - In **Section 4.4**, the multimodal fusion
     \[
     \mathbf{e}_t = \mathrm{MLP}(\mathbf{e}_{\text{text}}) + \mathrm{CLIP}_{\text{visual}}(\mathbf{I})
     \]
     assumes compatible dimensionalities and embedding spaces without justification. No projection details or normalization are given.
   - In **Section 4.5**, the compiler reward
     \[
     R_{\mathrm{compile}} = \exp(-\lambda k)
     \]
     is defined at an episode level, but the MDP setup in **Equation (1)** uses stepwise rewards \(r_t\). The paper never explains how episode-level code metrics are assigned to timesteps, whether rewards are sparse terminal rewards, or whether PPO is applied with intermediate shaping.

   Collectively, these are not minor omissions. They leave the optimization target and the actual architecture ambiguous.

3. **The paper invokes “reward machines” in the title and positioning, but does not actually define or use a reward machine in the technical sense.**  
   **Section 2.2** and **Section 3.5** cite reward machines, which are normally structured automata over temporally extended reward specifications. However, the actual method in **Section 4** is a task-conditioned weighted sum of sub-rewards, optionally with prototypes and FiLM. I do not see a reward-machine state, transitions, acceptance conditions, event propositions, or any temporal decomposition akin to reward machines. The title therefore overstates the connection. This matters because the paper’s stated originality partly depends on that framing, yet the formulation seems much closer to dynamic reward weighting than to reward machines.

4. **The experimental setup is too vague to support the claims, and important evaluation choices are missing.**  
   On **Page 6, Section 5.1**, the paper lists CodeXGLUE, APPS, DeepFix, and HumanEval, but does not specify:
   - which exact subsets or tasks from CodeXGLUE were used,
   - how train/validation/test splits were handled,
   - how many prompts/problems were used from APPS or HumanEval,
   - whether the same policy backbone was used across all tasks,
   - whether the model was initialized from a pretrained code LLM and, if so, which one,
   - what action space was used for repair versus generation tasks,
   - how PPO episodes were truncated for long code sequences,
   - how computational efficiency was measured fairly across heterogeneous tasks and hardware.
   
   These omissions are severe because the paper’s contribution is empirical. Without them, the numbers in **Table 1** are not verifiable and the comparison may not be apples-to-apples.

5. **The baseline selection is weak and omits the most natural comparisons for the claimed setting.**  
   The baselines in **Section 5.1** are Uniform, Expert-Tuned, and GradNorm. These are not enough for a paper about RL for code generation with structured/verifiable rewards. The most direct baseline would be a strong existing RL-for-code setup with fixed reward design and the same policy backbone, especially methods centered on execution or verification feedback. The paper cites CodeRL in the references, but does not compare against it in **Table 1**. Since the claim is that dynamic reward composition improves RL-based code generation, comparing only against generic weighting schemes is too convenient. It does not establish competitiveness against the actual literature on RL for code.

6. **The reported results are not statistically credible as presented.**  
   **Table 1** gives single numbers for five tasks, and **Table 2** gives single ablation results, but there are no standard deviations, confidence intervals, significance tests, or even per-seed variability despite **Section 5.1** stating that experiments use 3 random seeds. For noisy RL training, especially on code tasks, this is a serious omission. The margin between methods is sometimes moderate, but without variance it is impossible to know whether the gains are robust. This especially affects the broad claim in **Section 5.2** that DTERM “consistently outperforms” baselines.

7. **Several claims in the text are stronger than what the evidence shows.**  
   The introduction claims “zero-shot adaptation to unseen coding tasks,” and **Section 4.3** says the prototype mechanism “allows for zero-shot adaptation.” But the paper never formally defines the zero-shot protocol. In **Figure 2**, the x-axis is “Unseen Tasks” from 1 to 10, and the y-axis is normalized reward values. That is not enough to assess zero-shot generalization. What are these unseen tasks? Unseen problem instances within known task families, or entirely new task types? Were baselines denied access to the same meta-training information? **Figure 2** shows DTERM trending higher than other lines, but without error bars, task identities, or protocol details, it is more an illustrative plot than convincing evidence.

8. **The figures support the narrative only weakly because they are too high level and do not answer the core scientific questions.**  
   - **Figure 1** is a simple block diagram. It is helpful as an overview, but it does not clarify how the FiLM modulation, prototype attention, compiler feedback, and RLHF component coexist in one trainable objective. In fact, the figure is simpler than the text, and that mismatch highlights the underspecification.
   - **Figure 3** shows different sub-reward proportions across task types, which is the kind of analysis one would want. However, the figure alone does not establish that the learned weighting is correct or beneficial. There is no connection made between these proportions and downstream outcomes, no variance across runs, and no analysis of whether the learned weights align with task semantics beyond anecdotal interpretation.
   - **Figure 4** shows a downward meta-training loss curve, but this is not very informative because the paper never clearly defines the meta-training objective. A decreasing loss is expected for many objectives and does not demonstrate stable policy learning or reward-quality improvement. In RL papers, training curves should usually be tied to reward, success rate, or held-out performance, not just an undefined “meta-training loss.”

9. **The choice of metrics is questionable for some tasks, and the reward design may be misaligned with evaluation.**  
   In **Table 1**, summarization and translation are evaluated by BLEU-4, completion by exact match, repair by fix rate, and problems by Pass@1. Yet the reward components in **Section 5.1** include compilation success, test pass rate, BLEU, style adherence, and computational efficiency across all settings. It is unclear which rewards are active for which tasks, how weights are normalized when a component is unavailable, and whether reward shaping leaks evaluation metrics too directly. For instance, using BLEU as both reward component and evaluation metric for translation/summarization can make improvements less meaningful scientifically unless carefully controlled.

10. **The relation to prior work is incomplete and sometimes careless.**  
   The related work section is shallow. There are placeholder citations “(?)” in **Sections 2.3, 2.5, and 5.1**, which indicates the literature review is unfinished. More importantly, the paper does not adequately position itself relative to prior work on RL for code with verification/static-analysis rewards, process-level reward design, or more formal reward-machine variants for stochastic or numeric rewards. Since the paper’s main claim is a new reward-structuring idea, weak positioning against directly relevant prior methods reduces confidence that the contribution is either sufficiently new or properly contextualized.

11. **The paper overclaims practical breadth without supporting experiments.**  
   The method includes multimodal task fusion (**Section 4.4**) and RLHF integration (**Section 4.6**), but none of the experiments in **Section 5** evaluate multimodal tasks or human preference data. These sections read like speculative extensions rather than validated components. Including them as part of the method inflates scope without evidence.

12. **Even taking the quantitative results at face value, the contribution appears incremental relative to the complexity added.**  
   The paper stacks task embeddings, a gating network, FiLM layers, prototype attention, compiler reward shaping, multimodal fusion, and RLHF integration. Yet the empirical evidence is thin and the implementation details are sparse. The complexity-to-evidence ratio is poor. A simpler paper focused purely on dynamic reward weighting, implemented cleanly and compared rigorously, would have been much more convincing.

## Questions
1. Please give a precise end-to-end objective and training algorithm. Concretely, what is optimized by PPO, what parameters are updated jointly, and how are the reward-module parameters, FiLM parameters, and prototype parameters trained? A compact algorithm block or pseudocode would help substantially.

2. How exactly do **Equation (5)** and the prototype mechanism in **Section 4.3** interact? Are the final weights
   \[
   \alpha_i = \mathrm{softmax}_i(\mathbf{w}_i^\top \mathbf{e}_t + b_i)
   \]
   or
   \[
   \alpha_i = \sum_k a_k \alpha_i^{(k)},
   \]
   or some combination of both? Please provide the final formula used in experiments.

3. What is the formal definition of “unseen tasks” used in **Figure 2**? Please describe the split, the number of task families, whether the task descriptions overlap semantically with training tasks, and how baselines were trained under the same protocol.

4. Please report mean and standard deviation over the stated 3 seeds for **Table 1**, **Table 2**, and **Figure 2**, and ideally include significance testing or confidence intervals. This would materially change my confidence in the empirical claims.

5. Which exact backbone code model was optimized, and was it the same across summarization, translation, completion, repair, and problem solving? If different backbones or decoding strategies were used, the comparison in **Table 1** needs to be decomposed.

6. Can you clarify which reward components were active for each task, and how missing components were handled? For example, if “computational efficiency” is not meaningful for some summarization examples, is its reward set to zero, masked out, or omitted from the softmax normalization?

7. Why is the method described as a “reward machine”? If there is an actual automaton/state-transition structure, please define it formally. Otherwise, I strongly recommend renaming/reframing the method more conservatively.

8. Sections **4.4** and **4.6** introduce multimodal fusion and RLHF integration, but no experiments evaluate either. Were these components implemented and tested, or are they prospective extensions? A clear answer matters because the current presentation reads as though all are part of the validated method.

9. Please explain the conclusion on **Page 9**, which discusses DSAM rather than DTERM. If this is accidental, it raises concerns about manuscript preparation; if not, I do not understand its relevance.
