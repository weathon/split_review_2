## Summary

This paper presents a systematic benchmark of nine open-source mid-sized LLMs (7B–16B) on two reverse engineering tasks: function/variable name recovery and type inference from stripped binaries. The evaluation covers four architectures (x86-64, x86-32, ARM, MIPS), four optimization levels (O0–O3), two input representations (decompiled code and assembly), and two decompilers (Ghidra and IDA Pro), with both zero-shot and LoRA fine-tuned settings. The main finding is that current LLMs perform poorly on these tasks (most F1 scores below 0.1), though fine-tuning yields notable improvements on variable name recovery at optimization level O0.

## Strengths

- **Broad evaluation scope.** The paper evaluates 9 models across 4 architectures, 4 optimization levels, 2 input representations, and 2 decompilers. This represents a significant experimental effort covering a design space that prior work has not systematically explored. Tables 2–6 and the accompanying figures document this breadth concretely.

- **The O0 vs. O1–O3 fine-tuning gap is striking and potentially important.** Table 3 shows fine-tuned variable name recovery at O0 reaching 0.22–0.33 F1 across models, while O1–O3 stay below 0.10 for most models. This asymmetry could point to meaningful differences in how compiler optimization transforms variable semantics, and it is the kind of observation that could drive future work.

- **Honest documentation of limitations in the body.** The paper acknowledges that LLMs struggle with output formatting (Finding 8), that fine-tuning gains are inconsistent and not guaranteed (Finding 1), and that type inference is near-floor even after fine-tuning (Finding 2). The body does not oversell what the evidence shows.

## Weaknesses

### Major

- **Abstract makes an unsupported numerical claim.** The abstract states that after fine-tuning "DeepSeek-R1 demonstrates a notable improvement, reaching an F1 score of 0.37." However, in every presented result table (Tables 2–4, x86-64), DeepSeek-R1's best fine-tuned score is 0.17 (variable name recovery, O0 in Table 3). Its function name recovery peaks at 0.05 and type inference at 0.01. The value 0.37 appears nowhere in the reported results. The body text (line 265) highlights WizardCoder reaching 0.33 as the best result, not DeepSeek-R1. Results for non-x86-64 architectures are deferred to the appendix (stripped from this submission), but the abstract presents this claim as a general finding without qualification. This is a factual mismatch between what the paper advertises and what it demonstrates, and it undermines the paper's credibility.

- **Model-comparison claims rest on tiny F1 differences with no statistical grounding.** Most zero-shot F1 scores are between 0.00 and 0.06, and fine-tuned function name recovery scores hover between 0.02 and 0.07. The paper presents findings like "Qwen3 achieves the best function name recovery with an F1 score of 0.06" — a difference of 0.01–0.02 from the next-best models. No confidence intervals, standard deviations, or significance tests are reported anywhere. At this scale, measured differences could easily be noise from random sampling, auxiliary LLM parsing errors, or prompt template variations. The paper's stated goal of "guiding model selection" (line 91) is not supported by measurements at this resolution.

- **Potential data leakage in train/test split.** The training set is described as "independent" of the test set and drawn "from the same pool" of open-source projects (line 186). The paper does not specify whether functions from the same source file or project can appear in both splits, and no deduplication procedure beyond removing identical decompiled/assembly code pairs is described. If functions from the same binary straddle the split, fine-tuning results — especially the elevated O0 scores — could reflect learning dataset-specific patterns rather than generalizable name recovery.

### Minor

- **Auxiliary LLM confound is not validated.** The paper uses an auxiliary LLM to normalize heterogeneous model outputs into a consistent format (Section 3.2), but does not report this model's parsing accuracy, validate its outputs against a gold-standard manual parse, or analyze whether parsing error rates differ across source models. Since the paper's central contribution is comparative benchmarking, systematic parsing bias could confound model rankings.

- **The O0 vs. O1–O3 gap is identified but not analyzed.** The finding that fine-tuning yields dramatically better variable name recovery at O0 (0.22–0.33) than at O1–O3 (≤0.10) is the most striking result in the paper, but no analysis is offered to explain why. The paper notes it in passing and moves on. Investigating whether this reflects fewer recoverable variables at O0, different naming patterns, or compiler-induced distortions would substantially strengthen the contribution.

- **Finding 4 ("training data quality is more decisive") overclaims on the evidence.** The paper compares CodeLlama 7B/13B/34B and finds little size-related improvement, then compares across model families and attributes differences to "training data quality." The within-family scaling result is consistent with known scaling laws (diminishing returns at fixed data scale), and the cross-family attribution is speculative since model architecture, training recipe, and data composition all differ simultaneously.

## Nice-to-Haves

- Report fine-tuning hyperparameters (LoRA rank, alpha, learning rate, batch size) to improve reproducibility.
- Run experiments with multiple random seeds and report standard deviations to establish a noise floor for the tiny F1 differences.

## Suggestions

1. **Fix the abstract.** Either remove the unsupported 0.37 claim or qualify it with the exact task, architecture, and optimization level it refers to (if it appears for a non-x86-64 architecture in the appendix).
2. **Add statistical characterization.** At minimum, run multiple seeds and report standard deviations so readers can assess whether the 0.01–0.03 differences that drive model comparisons exceed the noise floor.
3. **Clarify the train/test separation methodology.** Specify whether cross-project enforcement was applied; if not, quantify the potential leakage.
4. **Validate the auxiliary LLM.** Report parsing accuracy on a manually-audited sample, broken down by source model.
5. **Analyze the O0 gap.** This is the paper's most interesting finding, and it deserves dedicated analysis rather than a passing mention.
