\title{Coding Reliable LLM-based Integrated Task and Knowledge Agents with GenieWorksheets}

\begin{abstract}
Large Language Models (LLMs) present an opportunity to create automated assistants that can help users navigate complex tasks.
However, existing approaches have limitations in handling conditional logic, integrating knowledge sources, and consistently following instructions.
Researchers and industry professionals often employ ad hoc pipelines to construct conversational agents. 
These pipelines aim to maintain context, address failure cases, and minimize hallucinations, yet frequently fail to achieve these objectives.
To this end, we present \system{} – a programmable framework for creating task-oriented conversational agents that are designed to handle complex user interactions and knowledge queries.
Unlike LLMs, \system{} provides reliable grounded responses, with controllable agent policies through its expressive specification, \worksheet{}. 
In contrast to dialog trees, it is resilient to diverse user queries, helpful with knowledge sources, and offers ease of programming policies through its declarative paradigm.
The agents built using \system{} outperforms the state-of-the-art method on complex logic domains in STARV2 dataset by up to 20.5\%.
Additionally, through a real-user study involving 62 participants, we show that \system{} beats the GPT-4 with function calling baseline by 21.1\%,  20.1\%, and 61\% on execution accuracy, dialogue act accuracy, and goal completion rate, respectively, on three diverse real-world domains.png}\hspace{0
\end{abstract}

\section{Introduction}



Researchers and industry practitioners have demonstrated significant interest in developing task-oriented dialogue agents. 
These agents are typically designed with a transactional focus, aiming to fill slot values based on user utterances to complete specific tasks~\citep{budzianowski-etal-2018-multiwoz, SMDataflow2020, rastogi2020towards}.
However, natural conversations between users and call agents cannot be adequately modeled solely as slot-filling tasks.
Users often require external information to progress through the steps necessary for task completion.
For example, when attempting to make a restaurant reservation, users frequently seek to identify a venue that best aligns with their preferences. 
Additionally, users may interrupt the agent at any point during the conversation to pose new inquiries.
Traditional dialogue tree-based approaches often struggle to handle such unexpected user questions or deviations, leading to a suboptimal user experience~\citep{rasa2017, converse2022, AmazonLex, BotPress, GoogleDialogueFlow}.

The advent of Large Language Models (LLMs) offers a promising opportunity to create more natural dialogue agents. 
These LLM-based agents can effectively navigate ``unhappy paths," where the system adeptly manages unforeseen user inquiries at any stage of the conversation.
Furthermore, LLMs have enabled the development of knowledge assistants capable of querying structured data by generating query languages such as SQL~\citep{pourreza2023dinsqldecomposedincontextlearning} and SPARQL~\citep{liu2024spinachsparqlbasedinformationnavigation} and retrieving text for unstructured knowledge~\citep{khattab2023demonstratesearchpredictcomposingretrievallanguage}. 
However, LLMs can be unreliable, posing challenges for developers aiming to deploy them in real-world applications, primarily due to a lack of control over conversations and inaccurate contextualization of information.

{\bf Challenge 1: Creation of effective, informative, and responsive informative agents, while letting developers exercise control without onerous efforts.} Developers desire to
maintain control over critical aspects of the agent's operation, including the flow of conversations, the timing of actions, and the information elicited from users.
For example, if a user declines an agent's offer to book a restaurant, developers should be able to program the agent to suggest alternative options, such as offering discounts.
With the in-context learning capabilities of LLMs, researchers have begun incorporating agent policies as instructions in model prompts~\citep{zhang2023sgp, liu2024llm}.
However, LLMs often fail to adhere strictly to these instructions, resulting in inconsistent and unreliable agent behavior~\citep{liu2024lost}.
Recent libraries, such as those offered by LangChain and Guidance, provide abstractions for developing LLM-based agents but still require developers to manually craft prompts and create reliable pipelines.
{\bf Challenge 2. Support users' queries for information, which may be embedded in a task request.} Semantic parsing, which maps natural language to logical forms, has been applied to API invocations~\citep{patil2023gorilla} and database queries~\citep{pourreza2023dinsql, liu2023suql}. To create task agents that can answer questions, 
\citet{kim2020beyond} proposes using intent classification to generate a query or an API invocation. However, in practice, a single user statement can combine a query with an API invocation. For example, ``I want to book a romantic restaurant in London on Valentine's day'', translates into a query to produce a restaurant to be used as input to a reservation API invocation. How do we express and support arbitrary compositions of queries and API calls?

{\bf Challenge 3: Dialogue systems need to remember pertinent facts from the dialogue history.}
Current methods based on LLMs typically rely on including in the prompt a complete dialogue history~\citep{ulmer2024bootstrapping, liu2024llm} or a summary of the conversation~\citep{packer2023memgpt, li2024hello}.
However, full dialogue histories can cause LLMs to overlook critical details in extended interactions;  
summarization may omit essential information, leading to repetitive questioning or generating inaccurate responses, often referred to as ``hallucinations"~\citep{bang2023multitask}.



{\bf Our proposed method}. This paper proposes a method 
that let developers easily create dependable and effective task-oriented agents that can carry out accurate, fluid, and informative conversations with users. We address the above challenges with a novel {\em high-level}, {\em expressive} and {\em declarative} specification representation we have created called a Genie Worksheet. 
The core concept is to ask the developer to directly declare variables to represent information that is pertinent to the conversation and to describe the actions to perform according to the input information. For answering user questions, the developer only have to supply the knowledge bases, which may be structured or unstructured. In other words, the developer is only declaring the {\em necessary} specification, and we show that the specification is {\em sufficient} to create effective knowledge and task-oriented agents.

From the Genie Worksheet, the Genie framework derives a conversational agent that fills in the variables in the Worksheet as the conversation continues. {\em The actively updated Worksheets double up as a succinct representation of the dialogue state}, designed carefully to 
address the complexity in semantic parsing and agent policies. As shown in Figure~\ref{fig:intro_fig}, an agent processes each turn of the conversation in four steps: a contextual neural semantic parser to interpret the input, an execution module performs the queries and actions, an algorithmic agent policy module decides on the agent actions, and a neural response generator generates the response governed by the agent policy.
Contributions of this paper include:
\begin{enumerate}[leftmargin=*]

\item 
Genie Worksheet is the first high-level specification language for effective integrated knowledge and task-oriented agents. 
\begin{itemize}[leftmargin=*]
    \item 
It is the first representation that supports {\em full integration} of knowledge and task-oriented agents. Unlike previous slot-based task-oriented dialogues (ToD), the agent can handle utterances and conversations that translate into formal queries for hybrid knowledge bases and whose results are used in API calls (Challenge 2).
\item
It is a high-level {\em declarative} language that lets the developer {\em control the agent policy} easily. Developers only need to specify (1) spreadsheets for tasks that associate actions with the requested information from the user and task completion, (2) schemas of structured databases and free-text repositories (Challenge 1).
\item 
Unlike traditional ToD agents which support only a fixed set of parameters, Genie WorkSheet is {\em expressive}, as it supports full dialogues where the information to request is {\em dependent on users' answers}. Such behavior, typical of call agents, has previously been supported only in dialogue-tree specifications.
\item
Genie Worksheet facilitates the derivation of an effective agent, as it is instrumental in the creation of an accurate semantic parser and a flexible agent policy.
It is the representation used as {\em the context and target for the contextual semantic parser}, allowing the parser to remember pertinent information in a long conversation (Challenge 3). It is also interpreted by the agent policy module, which can handle the complexity of {\em mixed-initiative} dialogues easily by first servicing the user's initiatives before the agent's initiatives as recorded in the worksheets (Challenge 1), as shown in the second to last turn of the agent in Figure~\ref{fig:intro_fig}.
\end{itemize}
\item Using a fully functional prototype of \worksheet{}, \system{} agents outperform the SOTA on StarV2~\citep{zhao2022anytod} by up to 20.5\% points across the complex logic domains.

\item Via a user study of 62 participants across 3 different real-life dialogue-oriented tasks, we show that \system{} agents are significantly better than the previous SOTA. The results show an impressive 86.5\% execution accuracy, 89.2\% dialog act accuracy, and an 82.8\% goal completion rate, surpassing the GPT-4 function-calling baseline by 21.1, 20.1, and 61 percentage points, respectively.

\end{enumerate}


\section{Design and Rationale of the \worksheet}



The objective in the design of the worksheet is to provide developers a high-level, concise, expressive specification of the task at hand. Our worksheet design is inspired by the versatility of webforms. Modern websites contain multiple fields which can be optional, tabs for selection of task, and pop-up windows that depend on previous user responses. 
There are two kinds of worksheets: a {\em task} worksheet and a {\em} knowledge base worksheet, described below. 

\paragraph{Task Worksheet} A worksheet, as illustrated in \autoref{fig:worksheet}, has a {\em WS Name}, a {\em WS Predicate} which indicates when it is activated, a {\em WS Kind} which is set to Task,
and a {\em WS Actions}, which are executed when all its required parameters for this task are assigned. 
The WS Predicate of a top-level worksheet is always true, whereas the rest are activated only if their related predicates are true. 
\begin{figure*}[ht!]
    \centering
    \includegraphics[width=\textwidth]{images/worksheets.pdf}
    \caption{The \worksheet{} specification for the support ticket submission assistant in \autoref{fig:intro_fig}.}
    
    \label{fig:worksheet}
\end{figure*}
Each worksheet contains a set of fields. A field has a {\em Predicate} which indicates when it is to be executed. It has a {\em Kind}, which can be input, output, or internal, and a {\em Description}. It has a {\em Type}, where all conventional types are allowed. If it is an enum {\em Type} (e.g. student\_task in \autoref{fig:worksheet}), a set of {\em Enum Values} and their {\em Description}s are specified in the succeeding lines. The boolean {\em DontAsk} will record the information if the user offers it, but the agent will not ask for it. If DontAsk is false, the agent will ask for the field if it is not assigned, but user can refuse to answer if it is not {\em Required}.
Whenever a field is assigned, the supplied {\em Actions} should be executed either if the {\em Confirmation} boolean is set to false, or if the user has confirmed with the agent.

For both the worksheet action and field action, the developer can write code using the variables defined in the worksheet (in Python). Several built-in actions are provided to the developer: 
(1) {\tt say (str)} responds to the user with the given string {\tt str}. 
(2) {\tt propose (ws, [fld,val]*)} instantiates a new worksheet {\tt ws} with the given field value pairs. For instance, developers can code in a \texttt{propose} action in the {\em WS Actions} field of a flight booking worksheet to propose a hotel booking worksheet at the same destination of the flight.
(3) {\tt exitws()} marks the worksheet as abandoned and closes it. For instance, the {\em Actions} field of the ``confirm'' field in the ``Main'' worksheet in \autoref{fig:worksheet} contains a {\tt exitws()} call if user does not want to submit the ticket anymore. 

\paragraph{Knowledge Access} In Genie Worksheet, knowledge access is treated as a first-class object. Real-life queries often involve both structured and unstructured accesses. For instance, queries ``what's the best rated restaurant with a romantic atmosphere'' require accesses to both the structured ``ratings'' column and the free text ``reviews'' column. To handle hybrid knowledge bases, Genie adopts the SUQL query language, an SQL extension that integrates search of unstructured data~\citep{liu2023suql}. For each knowledge base to be included, the developer must create a worksheet with {\em Kind} set to KB. The fields in the KB Worksheet define the schema of the KB.




\section{\system: Reliable LLM-based Dialogue Agents}

\subsection{Formal Representation}

Current LLM-based dialogue agents contextualize the conversation by providing the complete dialogue history or summarizing it.  
However, despite their impressive natural understanding capabilities, they often struggle with maintaining relevant contextual information across longer conversations. 
Additionally, summarizing conversations can cause a loss of key information in the conversation.
This leads to hallucinated or fabricated values and repeating questions. 
Therefore, to mitigate these issues, \system tracks the dialogue state with a formal dialogue state. 
A dialogue
consists of a set of alternating user and agent turns, $\{u_1,a_1, \cdots, u_{t-1}, a_{t-1}, u_{t}\}$, where $u_i \in \mathcal{U}$, $a_i \in \mathcal{A}$ denoting user and agent utterances.

The parser outputs the current worksheets, which are used by the Agent Policy to generate the Agent Dialogue Acts. These Acts along with the latest worksheet value and the latest user utterance are used to generate the response. }

\paragraph{Dialogue State}
As an agent runs, it assigns values to the fields in task work sheets, executes actions,  and performs queries. 
A dialogue at each turn $t$, $d_t \in D$, is  a sequence of records, $r \in R$, each of which can be a completed or partially specified task or a KB query. A record has a {\em kind} of either task or KB query, an {\em initiator}, which can be agent or user. A task record has two additional attributes: 
(1) {\em name}, the name of a worksheet, 
(2) {\em assignment}, which maps one or more fields in the worksheet to its value. 
A KB query record has four additional attributes: (1) {\em names}, the set of names of knowledge bases mentioned in the query, (2) {\em NL query}: a string of the form {\tt answer(s)}, where {\tt s} is the de-contextualized (i.e. self-contained) query in natural language, (3) {\em KB query}: the formal query associated with the NL query, (4) {\em result}: the result of executing the formal query. 

Two examples of formal dialogue state are shown in \autoref{fig:methodology} (Formal Dialogue State $d_{t-1}$ and $d_t$).
In $d_{t-1}$, there are three records, two of task kind and one KB. 
The compositions of queries and APIs are supported by passing the result of an instance of a worksheet in as a field of another worksheet. 
The assignment of \texttt{course\_id} in record $r_2$ is $r_1$, which is of kind KB.

\textbf{Agent Acts} Agent utterances have a formal representation ($\bar{a} \in \bar{\mathcal{A}}$) consisting of 
5 agent acts:
\begin{itemize}
    \item \Report(record): Report the result obtained by executing the task or query in the record.
    \item \Confirm(record, fld name): Confirm the value mapped to a field name in a record. 
        \item \Say(utterance): Explicitly say the given utterance.
    \item \Propose(record): Propose to the user a new task or query, with possibly partially pre-filled values, in the given record.
        \item \Ask(record, fld name): Ask for the value of a field in a record.
\end{itemize}

\subsection{Architecture of the Genie Agent}
The Genie agent has three components: 
\begin{itemize}
\item  $\text{P}(u_t, a_{t-1}, \bar{a}_{t-1}, d_{t-1}, w): \mathcal{U} \times \mathcal{A} \times \mathcal{P}(\bar{\mathcal{A}}) \times \mathcal{D} \times \mathcal{W} \rightarrow \mathcal{D}$: A parser $P$ 
 accepts the current user utterance $u_t$ and contextualizes the utterance using the last agent utterance $a_{t-1}$, the previous-turn agent acts $\bar{a}_{t-1}$, the formal dialogue state from the last turn $d_{t-1}$, worksheet $w$, and generate a new dialogue state $d$. 

\item AP$(d, d', w): \mathcal{D} \times \mathcal{D} \times \mathcal{W} \rightarrow \mathcal{P}(\bar{\mathcal{A}}) \times \D$: an agent policy that accepts the dialogue state from the previous turn $d$, the new dialogue state after parsing $d'$, and the worksheet $w$ and produces a set of agent dialogue acts $\bar{a}$, along with a new dialogue state. 

\item $\RG(d_t, \bar{a}_t, u_t, a_{t-1}): \D \times \mathcal{P}(\bar{\A}) \times \mathcal{U} \times \A \rightarrow \A$: a response generator that accepts the formal dialogue state
$d_t$, an agent act set $\bar{a}_t$, the last user $u_t$ utterance and agent utterance $a_{t-1}$ to generate the agent response $a_t$.
\end{itemize}

Figure \ref{fig:methodology} shows the overview the \system system. At turn $t$ in the conversation, the system is given: (1) the conversation history $\{u_1,a_1, \cdots, u_{t-1}, a_{t-1}, u_{t}\}$, where $u_t \in \mathcal{U}$, $a_t \in \mathcal{A}$ denoting user and agent utterances; (2) the $t-1$-th turn formal agent act $\bar{a}_{t-1} \in \mathcal{P}(\bar{\mathcal{A}})$; (3) the $n-1$-th turn formal dialogue state $d_{t-1} \in \mathcal{D}$; and (4) the \worksheet{} $w \in \mathcal{W}$.

\textbf{The Parser} The parser consists of three modules. The
contextual semantic parsing (CSP) that translates the user utterance into a set of changes to be applied to the dialogue state.  
The context supplied to CSP is a compressed version of the dialogue state, where only the last KB record is included. 
The user may (1) \textit{supply values} to fields that are anticipated in existing worksheets;
(2) \textit{modify} a previously filled field or remove its value;
(3) \textit{initiate} new tasks or queries. 
If the user enters values into fields or modifies previously filled fields, the queries are update statements that modify an existing record, as illustrated in~\autoref{fig:worksheetquery}. 
If the user initiates a new task or query, a new record is created.
The CSP leaves queries to knowledge bases in natural language.

The second module, the knowledge parser (KP), translates natural language queries into formal queries. This decomposition of function allows for more advanced approaches for knowledge retrieval~\citep{yao2022react,yao2023treethoughtsdeliberateproblem} and abstracts knowledge integration away from CSP. 
The third module performs the updates on the dialogue state to create an updated dialogue state.
        \begin{algorithm}[t]
        \small
        \caption{\system{} Agent Policy}
        \label{alg:agent_policy}
        \begin{algorithmic}[1]
        
        \State \textbf{Input:} Previous dialogue state $d$, updated dialogue state from the parser $d'$, worksheet: $w$
        \State \textbf{Output: } New dialogue state $d'$, Agent Act $\bar{a}$
        \State Initialize a new Agent Acts set $\bar{a} \gets \text{empty set}$
        \If {KB record $r$ exists in \texttt{Diff}($d'$, $d$)}
            \If {required parameter $p$ associated with $r$ is unfilled}
                \State $\bar{a} \gets \bar{a} \cup \{\Ask(r, p)\}$ \Comment{Ask for the first required parameter}
            \Else
            \State Execute the KB query in the KB record $r$
            \State $\bar{a} \gets \bar{a} \cup \{\Report(r)\}$ \Comment{Report the result of KB record to the user}
            \EndIf
        \EndIf
            \ForAll {assigned fields $f$ in worksheets present in  \texttt{Diff}($d',d$) }
                \If {$f$ requires confirmation}
                    \State $\bar{a} \gets \bar{a} \cup \{$\Confirm$(r, f)\}$ \Comment{Ask for confirmation}
                \Else
                    \State Execute the actions associated with the field $f$
                    \State Update the state $d'$ and add new agent acts to $\bar{a}$
                \EndIf
            \EndFor

            \ForAll {Task records $r$ that are complete but whose actions have not been executed}
                 \State Execute the actions associated with the worksheet for $r$
                    \State Update the state $d'$ and add new agent acts to $\bar{a}$
            \EndFor

            \ForAll {required fields $f$ in the records $r$ in  $d'$}
            \If {$f$ has not been assigned}
                \State $\bar{a} \gets \bar{a} \cup \{\Ask(r, f)\}$ \textbf{break} \Comment{Ask for the first unfilled field}
            \EndIf
            \EndFor
        \State \textbf{Return} updated dialogue state $d'$ and $\bar{a}$        \end{algorithmic}
        \end{algorithm}
        
\textbf{Agent Policy} As opposed to relying on LLM to directly generate agent response based on conversation so far, \system uses a symbolic module to compute the agent responses.
The rationale for this is twofold: (1) Providing agent acts causes the LLM to generate a deterministic response governed by the agent policy.
(2) LLMs struggle with under-represented developer-defined policies and cannot follow all the instructions. Using a symbolic module to compute the necessary actions improves the LLM's ability to follow instructions. 

The agent policy (AP) interprets the updated dialogue state $d' \in \mathcal{D}$ generated by the parser ($P$), previous dialogue state $d$ and the worksheet signature $w \in \mathcal{W}$ to inform its actions, resulting in an update of the dialogue state $d' \in \mathcal{D}$ and a set of new agent acts $\bar{a} \in \mathcal{P}(\bar{\mathcal{A}})$. 
The agent policy (AP) utilizes the \texttt{Diff($d', d$)} function that identifies any fields and worksheets that have been modified or initiated between two dialogue states $d'$ and $d$.

Algorithm~\ref{alg:agent_policy} outlines the agent policy. The procedure initiates by assessing whether a new KB record exists within the updated dialogue state \(d'\) compared to $d$ (Line 4). 
If any required parameters $p$ are missing in the record, the agent prompts the user to provide the missing values (Line 6). Otherwise, the system reports the result of the KB query (Line 9).
Subsequently, the policy checks whether any new fields require confirmation and prompts users (Line 14). If no confirmation is needed, actions associated with the newly filled fields are executed (Line 16), and the dialogue state is updated accordingly (Line 17). Any agent acts based on developer defined actions are recorded (Line 18).
If all fields in any worksheet are filled and their corresponding actions have been completed, the policy executes the worksheet-related actions (Line 22) and updates the dialogue state (Line 23). Any agent acts based on developer defined actions are recorded (Line 24).
Finally, the policy identifies the first unfilled field in the dialogue state and generates an agent act corresponding to requesting the user to provide the necessary value (Line 28).
\subsection{Discussion}
Genie automatically handles the dialgoue flow based on a succinct declarative Worksheet specification. This is significantly different from dialogue trees which require the programmer to hand-code the policy for each turn. Another popular approach is to model the conversation as a finite state machine where user inputs are mapped to a small number of user dialogue acts and rules are used to map the user dialogue acts, together with results of API or DB queries, to agent dialogue acts. As we discussed, each turn can invoke multiple different agent dialogue acts, resulting in an exponentially many agent dialogue state, had a finite machine been used. Purely function calling in LLMs will also fail to handle the many details in a conversation.

Before we launch into the discussion of our real user study on real-life applications, we perform a comparison study on one of the more complex examples of a slot-based benchmark.

AnyTOD~\citep{zhao2022anytod} has the SOTA result on StarV2. 
With \system, the agent policy for the banking domain can be specified in 9 lines of code in \worksheet{}, as opposed to 31 lines in AnyTOD.
We only provide three examples to the LLM-based semantic parser\footnote{We use \texttt{gpt-4-turbo-2024-04-09} for this experiment.}, while AnyTOD finetunes T5 XXL (13B) model on all domains except the one tested (roughly 6000 data points). \system{} achieves an impressive weighted SaF1 of 82.5, 83.4, and 92.7 on each of the three domains, outperforming the best ToD model by 17.5, 20.5, and 6.4 percentage, respectively. Furthermore, our analysis indicates that most of our errors are caused by inconsistent dataset annotations.

\subsection{Applications}
We choose three diverse applications with varying complexities. Compared to the 3 StarV2 domains, these real-world applications are much more complicated, as shown in Table~\ref{table:stats}.

\noindent\textbf{Restaurant Reservation}
Making a restaurant reservation requires finding a suitable restaurant and providing booking information to complete a transaction. 
We use the real-life dataset containing restaurants from Yelp.com from ~\citet{liu2023suql}. 
  
\noindent\textbf{Ticket Submission}
In this study, we aim to replicate a subset of tasks found within a university's student services portal. University student services portals typically contain various tasks categorized under different sections and subsections, posing a navigational challenge for students seeking to locate the appropriate link.
Moreover, these portals often contain a vast corpus of free-text data, which students must peruse before submitting a ticket.
We evaluate agents' capability to handle nested webpages with predicates and subsequent actions.

\noindent\textbf{Course Enrollment}
Finally, we evaluate the performance of \system{} as a course enrollment assistant, which combines hybrid data sources to search for course details and fill out complicated nested forms.
The assistants allow students to ask questions about course requirements, student reviews, and ratings while filling out their enrollment forms.
We collect a real-life dataset containing courses from the Computer Science program, with 4 tables (courses, offerings, ratings, and programs).

\subsection{Baseline and Data Collection}

\noindent\textbf{Baselines:} We compare our system against GPT-4-turbo with functional calling, which we call GPT-4 (FC).
We provide the baseline system with the ability to use the same KB Parser for external knowledge access. 
This baseline closely follows ~\citet{li2024large}. We also experimented with Nemo-Guardrails~\citep{rebedea-etal-2023-nemo}, a recently-proposed development framework for LLM-based conversational agents, but found it fails miserably on basic task-oriented dialogues (refer to \autoref{sec:details-on-nemo} for details).

\noindent\textbf{Study Design:} We use Prolific to recruit 22 participants for Restaurant Reservations and 20 users who identified as students for Ticket Submission. 
We recruited 20 university students to evaluate the Course Enrollment assistant. 
We instructed them to attempt to book a reservation, submit an issue ticket, and enroll in two courses, respectively.
We randomly assigned users to one of the two visually identical systems. We collected 99, 81, and 127 turns with \system{}, and 90, 70, and 144 turns with With GPT 4 (FC), respectively.

\subsection{Evaluation Metrics}

\noindent\textbf{Semantic Parsing Accuracy}
For each user turn, we manually inspect the code generated by the semantic parser for correct APIs and Databases and filled fields.
We define the gold Semantic Parsing output ($SP$) as the set of correct API calls ($A$), Database calls ($D$), and fields to fill ($F$).
Then for each user utterance,  $SP = \{s_1, s_2, ..., s_m \}$, where $s_i \in \{A \cup D \cup F\}$ and $m$ is the total number of choices, such that $m= |A \cup D \cup F|$. 
The Semantic Parsing Accuracy (SP Acc) for a system is defined as the number of correct choices in the semantic parser's output divided by $m$.
\noindent\textbf{Execution Accuracy}
We manually inspect each turn to check whether the agent executes the correct API and databases. 
For each agent turn, let the executions be $E =\{e_1, e_2, ..., e_m\}$ where $e_i$ is an API or database call.
We evaluate whether each $e_i$ is a true positive or false positive. We calculate the Execution (Ex Acc)  as the number of true positives divided by the number of true and false positives for all the execution calls in a conversation.

\noindent\textbf{Agent Dialogue Act Accuracy}
For each turn, we manually inspect whether the agent's dialogue act follows the policies provided by the developer
. Formally, for each turn, we define a list of gold acts $a_1, a_2, ..., a_m$ where $a_i \in A$, all the possible agent dialogue acts.
The Agent Dialogue Act Accuracy (DA Acc) for a system is defined as the number of correctly predicted actions divided by $m$. 
For GPT-4 (FC), we map its responses to the equivalent elements in the power set of agent acts.

\noindent\textbf{Goal Completion Rate}
We define Goal Completion Rate (Goal CR) as the user's ability to successfully complete the task with the system's assistance.

Goal Completion Rate is a binary metric for each conversation, where 1 denotes that the goal was completed, and 0 indicates that the goal was not achieved.

Table~\ref{table:main}
compares \system{} against GPT 4 (FC) across three metrics and finds that \system{} performs significantly better than GPT-4 (FC) on all three domains.
We observe that \system{} consistently demonstrates a high semantic parsing rate (exceeding $85\%$), indicating that \worksheet is simple to understand for LLMs with few shot examples.
The marginally lower SP Acc  ($85.8\%$) observed in the Ticket Submission application can be attributed to the application's complexity, featuring several worksheets (=$8$) and fields (=$28$), as shown in Table~\ref{table:stats}.

Additionally, the higher Ex Acc can be attributed to providing compressed context as the formal dialogue state, enabling the LLM to invoke the correct API and execute the suitable knowledge query.
The superior performance on DA Acc can be ascribed to our agent's capability to provide turn-by-turn instructions rather than presenting all the instructions at once, as is the case with GPT-4 (FC). 
\textbf{The results validate the benefit of programmable policies in delivering a reliable assistant}.

In terms of the final Goal Completion Rate, we observe that GPT-4 (FC) scores relatively higher in restaurant reservations, the domain it is most familiar with and well represented in existing dialogue datasets~\citep{ye-etal-2022-multiwoz,rastogi2020towards}.
Similar results are also observed by \citet{zhang2023sgp} and \citet{hudecek-dusek-2023-large}.

In most cases, GPT-4 (FC) does not elicit all the required fields from the user, making incomplete API calls. 
Moreover,  despite having access to the KB Parser, \textbf{GPT-4 (FC) often hallucinates} non-existent courses and fails to enroll students.

\section{Related Work}


{\bf Dialogue Tree-based frameworks}. 
A wide variety of commercial and open-sourced products ~\citep{AmazonLex, BotPress, converse2022, GoogleDialogueFlow, MSBot, MSPowerVirtualAssistants, OneReach, rasa2017, WatsonAssistants} exist that help developers program a conversational virtual assistant using dialogue trees, with slight differences in design. For instance, \citet{BotPress,GoogleDialogueFlow,MSBot,OneReach,WatsonAssistants} allow users to interactively program a dialogue tree with a graphical user interface. Developers can manipulate various building blocks that classify user intents, sometimes with the help of built-in NLU (natural language understanding) modules. RASA allows developers to declare a list of global intents and program linear conversational paths accordingly ~\citep{rasa2017}. Converse allows developers to program a special kind of ``and-or'' trees ~\citep{converse2022}.
{\bf LLM and task-oriented dialogues}. A series of recent works attempts to integrate LLMs with TOD, showing its capability in dialogue state tracking~\citep{hu2022context, feng2023towards, hudecek-dusek-2023-large, li2024large, zhang-etal-2023-sgp}. In particular, \citet{li2024large} uses GPT's function calling capability for state tracking, which we compare against in Section \ref{sec:eval-with-real-users}. \citet{deng2024plugandplay} uses LLM for its dialogue policy planning module but does not support developer-defined actions through code. When building ToD agents with LLMs, existing works typically feed the entire set of instructions to the model for response generation~\citep{zhang-etal-2023-sgp}. While this works well on smaller domains, LLMs struggle to follow all instructions in real-life situations~\citep{liu2024lost}. Genie Worksheet instead uses formal agent acts to instruct LLMs on its response.



\section{Conclusion}


We introduce \system{}, a novel framework for building knowledge-integrated task assistants with LLMs, with \worksheet{}, a high-level specification that allows for detailed control over conversation flows.
The agents built using Genie outperforms the state-of-the-art method on complex logic domains in STARV2 dataset by up to 20.5\%.
Our real user studies with 62 participants demonstrate \system{} drastically outperforms traditional LLM-based systems and dialogue trees.
