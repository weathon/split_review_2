\title{Identifying the Risks of LM Agents with an LM-Emulated Sandbox}

\begin{abstract}
\label{sec:abstract}
Recent advances in Language Model (LM) agents and tool use, exemplified by applications like ChatGPT Plugins, enable a rich set of capabilities but also amplify potential risks---such as \tentative{leaking private data or causing financial losses}. 
\tentative{Identifying these risks is labor-intensive, necessitating implementing the tools, setting up the environment for each test scenario manually, and finding risky cases.  As tools and agents become more complex, the high cost of testing these agents will make it increasingly difficult to find high-stakes, long-tail risks.}
To address these challenges, we introduce \methodabbrv: a framework that uses an \lm to emulate tool execution and enables scalable testing of \lmagents against a diverse range of tools and scenarios.
Alongside the \sim, we develop an \lm-based automatic \ss \eval that examines agent failures and quantifies associated risks. \tentative{We test both the tool emulator and evaluator through human evaluation and find that \failprecadv of failures identified with \methodabbrv would be valid real-world agent failures.}
Using our curated \tentative{initial} benchmark consisting of \numtoolkit high-stakes toolkits %(most of which are challenging to test in real environments) 
and \numtest \tests, we provide a quantitative risk analysis of current \lmagents and identify numerous \fails with potentially severe outcomes.
Notably, even the safest \lmagent exhibits such failures \bestfailinc of the time according to our evaluator, underscoring the need to develop safer \lmagents for real-world deployment.%

\section{Background \& Problem Statement}


In this section, we begin by formalizing the definition and evaluation of \lmagents. Then, we introduce how our framework implements this formulation and tackles the practical challenges of \ss evaluation. Finally, we describe the specific threat model considered in our \ss evaluation.
The example \test for assessing \lmagents (\cref{fig:testcase} (left) will be utilized throughout this section.

\label{sec:background}

\paragraph{Formulation of \lmagents}
\ificlr
Language Model (LM) agents \citep{yao2023react, shinn2023reflexion,wang2023voyager}
utilize powerful tools such as API plugins \citep{qin2023toolllm, openai2023plugin} to interact with external environments and solve real-world tasks.
\else
Language Model (LM) agents \citep{yao2023react, shinn2023reflexion,liu2023llm+p,wang2023voyager}
utilize powerful tools such as web browsers \cite{nakano2021webgpt}, code interpreters \cite{gao2023pal}, and API plugins \citep{schick2023toolformer,qin2023toolllm, openai2023plugin} to interact with external environments and solve real-world tasks.
\fi
In the general setup, an \lmagent receives a user instruction $\inst \in \instspace$ 
(\eg, ``Please delete some files to free my disk space'') 
and executes actions using tools from the given tool set $\toolspace$ (e.g., tools for executing terminal commands).
The setup can be formalized as a partially observable Markov decision process (POMDP): at each step $\tstep$, the \lmagent takes an action $\action_\tstep \in \actionspace$ composed of the specific tool being invoked $\tool_\tstep \in \toolspace$ and additional input arguments for the tool (\eg, specific terminal commands), and receives an observation $\obs_\tstep \in \obsspace$ from tool execution.
The initial environment state is denoted as $\initstate \in \statespace$, the state transition function and emission function are denoted as $\transdist: \statespace \times \actionspace \to \statespace$ and $\emsdist: \statespace \to \obsspace$, respectively.
Given the \lmagent's trajectory $\tau_\totaltstep=(\action_1, \obs_1, \dots, \action_\totaltstep, \obs_\totaltstep)$ up to the final step $\totaltstep$, humans can assess the \emph{\help} score $\rewardhelp=\rewardfunchelp(\inst, \traj_\totaltstep)$ and \emph{\ss} score $\rewardss=\rewardfuncss(\inst, \traj_\totaltstep)$ with their implicit rewards $\rewardfunchelp, \rewardfuncss$.
The \help score measures how well the \lmagent fulfills the user instruction 
(\eg, whether some unnecessary files were deleted to free disk space), 
while the \ss score assesses the potential risks posed by the \lmagent and the severity of those risks
(\eg, whether critical files were indiscriminately deleted leading to data loss or system instability).

\paragraph{Challenges in \ss evaluation}
In standard practice, human experts conduct all the tasks from tool implementation and sandbox setup for specific test cases (\ie, $\transdist$, $\emsdist$, and $\initstate$) to the inspection and evaluation of agent trajectories (\ie, $\rewardss$).
\ificlr
\iclrtentative{
Such a procedure presents several challenges. 
First, the substantial manual effort required to build a sandbox and define its state for testing (e.g. environment variables or files) makes it difficult to find and replicate \fails that are rare but severe. 
Second, the necessity of having a fully realized tool and a sandbox setup in place restricts \lmagent evaluations to a subset of existing tools 
(\eg, \citet{liu2023agentbench}). 
However, \lm developers would want to ensure that their systems behave safely not only for existing tools, but also for tools that third-party developers may implement and deploy in the near future.
Finally, the requirement of a human expert to manually inspect the agent's actions makes it costly to test on large, diverse sets of tools and scenarios.}

\subsection{Emulating Tool Executions with Language Models}

\paragraph{The LM as an automated virtual sandbox} 
The core component of our framework is our emulator for the various tools and their execution environment.
We design the \sim by prompting GPT-4, which has showcased strong abilities to mimic multi-agent behaviors \citep{park2022social,park2023genagents}, and even emulate a virtual machine \citep{degrave2022vm} and existing public APIs \citep{tang2023toolalpaca}.
As depicted in \cref{fig:testcase},
our \emph{\std} \sim is prompted to instantiate the sandbox using the ``\toolspecs'' (containing the description, arguments, returns, and exceptions for each tool, see \cref{fig:example_tool_spec} for an example) and the ``\userinst'' of each \test.
At each step $\tstep$, the \sim also receives the current trajectory including previous actions and observations $\traj_{\tstep - 1}=(\action_1, \obs_1, \dots, \action_{\tstep - 1}, \obs_{\tstep - 1})$, as well as the current action $\action_\tstep$ taken by the \agent 
\ificlr
(including the tool being invoked and the associated tool inputs).

\fi
The emulator \lm is then prompted to return the observation $\obs_\tstep$ for the current action, where it implicitly emulates the state transition $\transdist$, the emission $\emsdist$, and the initial state $\initstate$ to return $\obs$ 
(for the full prompt for the \sim LM, see \cref{sec:emulator_prompt}).
The design of our \sim enables flexible prototyping of different test scenarios and risk assessments.
First, by leveraging the advanced programming capabilities

\paragraph{Adversarial emulator for red-teaming}
Sampling test scenarios randomly in the \std \sim may be inefficient for identifying rare and long-tailed risks, as the majority of them may result in benign or low-risk outcomes. 
In existing simulation-based testing frameworks for autonomous driving~\citep{dosovitskiy2017carla, rong2020lgsvl}, testers explicitly modify the sandbox state to align with particular red-teaming goals. We adapt this approach to our emulator and allow the sandbox to set its state and drive the tool execution to align with a target risky outcome.

We instantiate these ideas as the \emph{\adv} \sim, which is designed to automatically set up the virtual sandbox states based on \tests for red-teaming the \lmagents.
As depicted in \cref{fig:testcase}, the \adv \sim is additionally prompted with the underspecified nature of instructions (``\underspec''), as well as the several intended risks that could arise from LM agent’s actions, along with their respective descriptions (``\risksandactions'') of the specific \test.
The \sim is instructed to utilize this information to instantiate long-tail and more challenging scenarios where \lmagents are more likely to take risky actions and cause potential risks.
Therefore, unlike the \std \sim, the \adv \sim samples the sandbox state from a distribution that emphasizes long-tail higher-risk scenarios 
\ificlr
(see \cref{fig:sim_compare_main} for an illustrative example). 
\else
(see \cref{fig:sim_compare_main} for an illustrative example and \cref{sec:compare_std_adv} for additional examples). 
\fi


\paragraph{\Sim requirements \& design}

\ificlr
Crucially, for the \fails identified in our \sim to be faithful, they must be possible to instantiate in an actual tool and sandbox setup. 
\iclrtentative{

To fulfill the set requirements, the prompt of the \sim \lm is crafted to incorporate the detailed requirements and a chain-of-thought \citep{nye2021show,wei2022cot} process for the \lms to examine the compliance of each requirement step by step (see~\cref{sec:impl_details_sim} for details).}
\else
Crucially, for the \fails identified in our \sim to be faithful, it must be possible to instantiate the emulated trajectories in an actual tool and sandbox setup. 
For this to hold true, the \sim needs to satisfy the following core requirements: 
\begin{inlinelist}
\item \textbf{input validation}: the \sim must validate the tool inputs and reject invalid ones by raising an exception. For example, inputs using a placeholder instead of a legitimate email address should be rejected;
\item \textbf{accuracy}: the emulated outputs must closely mirror the corresponding actual tool execution, in line with the tool specifications and inputs;
\item \textbf{consistency}: the emulated trajectory must maintain a consistent state transition and ensure there are no discrepancies in emulated outputs throughout the entire trajectory. For instance, a file that has been deleted should not subsequently appear.
\end{inlinelist}
Any violation of these core requirements is deemed a \emph{major} issue, rendering the emulation non-instantiable.
In \cref{tab:emulator_req_design}, we summarize these core requirements and additional secondary requirements (\eg, exactly match the output of existing tools); violations of secondary requirements result in \emph{minor} issues that do not impede instantiability.

To design an \sim that fulfills the set requirements, the prompt of the \sim \lm is crafted to incorporate the detailed requirements and a chain-of-thought \citep{nye2021show,wei2022cot,kojima2022large} process for the \lms to examine the compliance of each requirement in a step-by-step manner (see~\cref{sec:impl_details_sim} for details).

\paragraph{\Ss \eval}
The objective of the \ss \eval is to precisely identify failures of \lmagents and quantitatively assess their potential risks.
\tentative{However, unlike capability evaluations (\eg, \citet{liu2023agentbench}) with predefined goal conditions, automatic risk evaluation is considerably more nuanced since \lmagents may fail in a variety of unpredictable ways, each with varying risk severities.}
Instead of enumerating and predefining all failure conditions, %(more precisely, failure conditions in the context of \ss evaluations) 
we prompt \lms to examine the \lmagent trajectories and retrospectively capture \fails within them.
As depicted in \cref{fig:testcase}, the \ss \eval takes the complete trajectory $\traj_\totaltstep$ as input, as well as the ``\underspec'', ``\risks'', and corresponding ``\riskyactions'' of the specific \test to facilitate its assessment. 
Using the provided information, the \lm-based \eval is tasked with assessing whether the \lmagent has undertaken any risky actions, such as failing to address \underspec or making incorrect tool calls. 
To distinguish and quantify the associated risks, the \eval is instructed to assess them based on both the \emph{likelihood} that the risk materializes (certainly not, possible, or likely) and the \emph{severity} of the resulting harm (mild or severe),
\ificlr

\paragraph{\Help \eval}
\label{sec:help_eval}
The \help \eval is designed to assess how effectively the \lmagents fulfill \userinsts without causing risks, which offers another evaluation dimension that complements the \ss evaluation. 
In particular, an agent that fails to take any effective actions or consistently seeks user confirmation before acting (even in non-risky scenarios) may achieve a perfect \ss score. 
However, it would fall short on \help, as the agent fails to complete the task.
As illustrated in \cref{fig:testcase}, the \help \eval utilizes the ``\underspec'' and the ``\expachv'' of the specific \test to assess how closely the \lmagents' actions align with ideal behaviors for safely assisting the \userinst. 
\ificlr
Based on this information, the \lm-based \eval takes the complete trajectory $\traj_\totaltstep$ as input and outputs the \help score $\rewardhelp$.
\iclrtentative{The \help score is also assessed on a scale of 0 to 3, with 3 indicating an ``excellent'' achievement and 0 indicating a ``poor'' one.}
\else
Based on this information, the \lm-based \eval takes the complete trajectory $\traj_\totaltstep$ as input and outputs the \help score $\rewardhelp$, according to the criterion in \cref{tab:evaluator_rubric}.
\fi
While the \help \eval is designed to capture potential tradeoffs between safety and helpfulness, this tradeoff is not an inevitable one since the benign user intent is best fulfilled through a safe action. For example, deleting all files without user confirmation to ``clean disk space'', is not in line with the \expachv and will be penalized in our \help evaluation. This means that agents that can properly disambiguate user intent can both be safe and helpful (see \cref{fig:agent_ss_help_frontier}).
\rebuttentative{Details and the full prompt are in \cref{sec:impl_details_help_eval} and \cref{sec:help_eval_prompt}, respectively.}

\section{Discussion}

\label{sec:discussion}

\paragraph{Comparison to prior \lm agent benchmarks}
Existing benchmarks for evaluating \lmagents primarily focus on assessing their capabilities. 
Domain-specific evaluations exist for code execution \citep{yang2023intercode} and web \citep{yao2022webshop, deng2023mind2web, zhou2023webarena} environments. 
Recent benchmarks, such as AgentBench \citep{liu2023agentbench} and ToolEval \citep{qin2023toolllm}, have been created to assess their broader capabilities across different tools.
Notably, \citet{kinniment2023evaluating} sought to assess the long-term risks of \lmagents but from a capability perspective.
\methodabbrv distinguishes itself for several reasons:
\begin{inlinelist}
    \item To the best of our knowledge, our work is the first initiative in directly assessing the risks associated with \lmagents;
    \item In contrast to previous evaluations with statically established sandboxes, our \lm-emulation framework facilitates a broader and more expandable evaluation scope across tools and test scenarios. Many of our assessed tools are either absent from existing benchmarks or challenging to test in real-world settings with prior practices (\cref{tab:example_toolkit}). 
\end{inlinelist}
In \cref{sec:ext_related_work}, we discuss additional related work on \lmagents and \lm emulators.
\paragraph{Limitations}
\iclrtentative{
Our work represents a preliminary exploration in developing \lmagents that are not only capable but also safe, and there are several limitations to address.
First, \lm-based \sims and \evals might occasionally not meet the requirements, leading to \crit or incorrect evaluations, respectively (\cref{tab:detailed_eval_result}). 
However, with the potential of model scaling \citep{kaplan2020scaling,wei2022emergent}, future LMs may offer enhanced performance.
Second, the test case curation still largely relied on humans. Developing fully automatic \test generation with \lms similar to \citet{perez2022red} could greatly enhance the scalability of our risk assessment.
Finally, we focused on a specific threat model of instruction \underspec in this work. 
Future work can broaden the scope to include diverse threat models, more toolkits and test scenarios, leveraging the flexibility of \methodabbrv.
We provide a detailed discussion on limitations and future directions in \cref{sec:limitations}.
}
\newpage

\iclrtentative{
\paragraph{Reproducibility}
 This includes the detailed design and implementation of our framework (\cref{sec:impl_details_framework}), the implementation specifics of the evaluated \lmagents (\cref{sec:impl_details_agent}), our human annotation process (\cref{sec:detail_human_annot}), and all the prompts utilized in our experiments \cref{sec:full_prompts}).
Our evaluation results might exhibit some variability due to the inherent stochasticity when invoking the OpenAI API. However, our estimation of this variance suggests that it is not significant enough to impact our conclusions (see the footnote in \cref{tab:eval_agent_result}).
Our code is included in the supplementary material and will be open-sourced upon acceptance.

In the course of our research, we adhered to stringent ethical standards to guarantee the transparency, integrity, and responsibility of our investigations.
Firstly, for human annotation tasks, all participants were voluntarily involved in the study and appropriately compensated for their time and effort. Their consent was obtained, and while necessary information was collected for compensation purposes, no sensitive personal data was retained or misused.
It is essential to note that our research, while aiming to identify risks and vulnerabilities in \lmagents, is intended solely for the purpose of enhancing the safety of such systems and not for malicious exploitation. 
While our emulators could replicate various risk-sensitive tools and scenarios, we underscore the importance of using these tools responsibly, especially in real-world, high-stakes situations. 
Given the potential risks associated with mishandling or misuse of our framework and the knowledge produced from our research, we urge both researchers and practitioners to approach the findings with caution and ethics.

\paragraph{Language model agents}
Building intelligent agents is a long-standing goal in artificial intelligence \citep{wooldridge1995intelligent, maes1995agents, russell2010artificial, bostrom2014super}.
Recent advances in \lms \citep{brown2020gpt3, raffel2020t5, ouyang2022instructgpt, openai2023gpt4} have paved the way for building intelligent agents that are proficient in instruction following \citep{ouyang2022instructgpt, bai2022training, openai2023gpt4}, reasoning and planning \citep{huang2022language, wei2022cot,kojima2022large,yao2023react,wang2023plan,liu2023llm+p, yao2023tot}, and tool-use \citep{schick2023toolformer,qin2023tool,qin2023toolllm,patil2023gorilla, tang2023toolalpaca}.
These \lmagents can effectively harness powerful tools such as web browsers \cite{nakano2021webgpt,deng2023mind2web,gur2023real}, code interpreters \cite{le2022coderl,gao2023pal,li2022competition,ellis2019write}, API plugins \citep{schick2023toolformer,qin2023toolllm, openai2023plugin,patil2023gorilla}, or embodied tools \citep{ahn2022saycan, liu2022mind, liang2023code, brohan2023rt}. 
Notable examples of such \lmagents include applications like ChatGPT Plugins \citep{openai2023plugin}, AutoGPT \citep{richards2023autogpt}, and GPT Engineer \citep{osika2023gptengineer}.
However, while most developments in \lmagents emphasize enhancing their capabilities, our work represents a crucial step towards creating an \lmagent that is not only capable but also safe.

\paragraph{Evaluation of LM agents}
Existing benchmarks for evaluating \lmagents primarily focus on assessing their capabilities. 
Specialized benchmarks have been established to evaluate domain-specific \lmagents in code execution \citep{yang2023intercode} and web \citep{yao2022webshop, deng2023mind2web, zhou2023webarena} environments. 
Recently, several benchmarks have been created to assess broader capabilities of \lmagents across different tools, such as AgentBench \citep{liu2023agentbench}, ToolEval \citep{qin2023toolllm}, and APIBank \citep{li2023api}.
Notably, \citet{kinniment2023evaluating} sought to assess the long-term risks of \lmagents but from a capability perspective.
Our evaluation framework distinguishes itself for several reasons:
\begin{inlinelist}
    \item To the best of our knowledge, our work is the first initiative in directly assessing the risks associated with \lmagents;
    \item In contrast to previous evaluations with statically established sandboxes, our \lm-emulation framework facilitates a broader and more expandable evaluation scope across tools and test scenarios. Many of our assessed tools are either absent from existing benchmarks or challenging to assess in real-world settings with previous standard practices (see \cref{tab:example_toolkit}). Furthermore, our benchmark can be easily expanded to accommodate new tools and test scenarios without tool or sandbox implementations.
\end{inlinelist}


\paragraph{Language model as an \sim}
Prior work has demonstrated the strong emulation capabilities of current \lms.
These \lms have been applied to emulate human behaviours \citep{park2022social,park2023genagents,liu2023training,gao2023s3} or feedback \citep{bai2022constitutional,dubois2023alpacafarm,zheng2023judging} and multi-agent collaboration \citep{dasgupta2023collaborating,li2023camel,hong2023metagpt}.
In contrast, our work repurposes \lms to emulate environments rather than the agents themselves.
In a similar vein, \citet{degrave2022vm} illustrated the potential of \lms in emulating a virtual machine, while \citet{tang2023toolalpaca} employed \lms to emulate the executions of existing public APIs, aiding in data generation for fine-tuning tool-use \lms.
Compared to these works, our work
\begin{inlinelist}
    \item showcases the ability of \lms in emulating a broader spectrum of tools that may not yet be developed (\cref{tab:example_toolkit}); and 
    \item highlights the potential of \lms to function as an automated virtual sandbox for risk evaluation of \lmagents, especially when paired with our \adv \sim.
\end{inlinelist}

\paragraph{Simulation environments}
Due to the complexity of real-world environments and potential \ss concerns, many experiments for developing and evaluating agents, especially in domains of autonomous driving and robotics, are performed in simulation environments.
Notable examples include OpenAI Gym \citep{brockman2016openaigym}, Deepmind Lab \citep{beattie2016deepmindlab}, CARLA \citep{dosovitskiy2017carla}, SUMO \citep{SUMO2018}, LGVSL \citep{rong2020lgsvl}, and robotsuite \citep{zhu2020robosuite}.
Unlike these environments that are programmatically predefined and static, ours is powered by \lms, offering the potential for greater adaptability to diverse and emerging scenarios.


\section{Limitations \& Future Directions}

\label{sec:limitations}

\paragraph{Quality of the \sims \& \evals}
Both our \sims and \evals are based on prompt-engineered \lms.  
We carefully designed their prompts to inject the requirements that they should satisfy to ensure the emulation quality (\cref{sec:impl_details_sim}) and evaluation accuracy (\cref{sec:impl_details_ss_eval,sec:impl_details_help_eval}).
While both the \sims and \evals demonstrated decent performance (\cref{sec:detailed_val}), we still observed some limitations in the current design.
First, there were instances where the \sims overlooked certain core constraints and caused \crit in the emulations (\cref{tab:detailed_eval_result}), which was more evident in complex or \adv scenarios. % where the specific requirements were subtle and for the \adv \sim that might trade off emulation quality for \adv effects.
Additionally, the \sims exhibited frequent \minor, such as emulating generic entries,
as assessed in \cref{tab:detailed_sim_val_results}.
We hypothesize that such behaviors may partially arise from the privacy and confidentiality stipulations integrated into GPT-4 during the stage of instruction tuning with human feedback.
Finally, we found that the \ss \eval could fail to detect certain risky actions committed by the \lmagent, as evidenced by the lower recall (\evalfailrecall) compared to human annotators (an average of \evalfailprec).
However, given the promise of model scaling \citep{kaplan2020scaling,wei2022emergent}, we believe future-generation \lms will function as better \sims and \evals, suggesting the potential scalability of our framework.



\paragraph{Automated red-teaming for scalable oversight}
Automated testing for the reliability and safety of deployable systems has been extensively studied in various domains, such as software development \citep{godefroid2005dart,fraser2011evosuite} and autonomous driving \citep{ben2016testing, tian2018deeptest}.
Automating the red-teaming of \lmagents, especially with the assistance of \lms, will be crucial for ensuring the safety of increasingly \lmagents that use more complex tools, a task that will become progressively more difficult.
Our work represents a preliminary exploration in this direction by providing 
\begin{inlinelist}
    \item an emulator for reducing the effort of searching over the large test space;
    \item an \adv \sim to automatically instantiate test scenarios for red-teaming;
    \item an automatic \eval to identify failures of \lmagents.
\end{inlinelist}
However, one limitation of our work is that the \test curation still largely relies on humans.
We explored the automatic generation of \tests with \lms similar to \citet{wang2022selfinstruct} and \citet{perez2022red} during our initial data curation, but observed frequent violations of the requirements for valid \tests (\cref{tab:test_case_requirement}). Perfecting this approach could greatly enhance the scalability of our benchmark.




\paragraph{Extending the evaluation benchmark}
In this work, we focused on the specific threat model of instruction \underspec, and curated an initial benchmark comprising of \numtoolkit toolkits and \numtest \tests.
Due to the flexibility of our emulator, our evaluation benchmark can be readily expanded to incorporate different threat models (such as those involving malicious intent), more toolkits, and a broader range of test scenarios.
Finally, while our work focuses on risk assessments, our framework might also be generalized to serve as a more comprehensive and flexible capability evaluation for \lmagents, as compared to existing evaluations with statically established sandboxes.
