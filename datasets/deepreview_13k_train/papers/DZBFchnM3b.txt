\title{Navigating the Labyrinth: Evaluating and Enhancing LLMs’ Ability to Reason About Search Problems}

\begin{abstract}


Recently, Large Language Models (LLMs) attained impressive performance in math and reasoning benchmarks. However, they still often struggle with logic problems and puzzles that are relatively easy for humans. To further investigate this, we introduce a new benchmark, \ourbench{}, containing 11 unique search problems, each equipped with automated pipelines to generate an arbitrary number of instances and analyze the feasibility, correctness, and optimality of LLM-generated solutions. We show that even the most advanced LLMs fail to solve these problems end-to-end in text, e.g., GPT4 solves only 1.4\%. \ourbench{} problems require considering multiple pathways to the solution as well as backtracking, posing a significant challenge to auto-regressive models. Instructing LLMs to generate code that solves the problem helps, but only slightly, e.g., GPT4's performance rises to 11.7\%. In this work, we show that in-context learning with A* algorithm implementations enhances performance. The full potential of this promoting approach emerges when combined with our proposed Multi-Stage-Multi-Try method, which breaks down the algorithm implementation into two stages and verifies the first stage against unit tests, raising GPT-4's performance above 57\%.

\end{abstract}

\section{Introduction}



The advent of Large Language Models (LLMs) has revolutionized the field of natural language processing, with models like Gemini\citep{li2024multimodal}, GPT-4\citep{OpenAI2023GPT4TR} demonstrating unprecedented performance on reasoning tasks such as GSM8k\citep{cobbe2021training}. However, these models still exhibit surprising failures on some intuitive tasks\citep{bian2023chatgpt, qin2023chatgpt, marcus2020next} and struggle with multi-step compositional reasoning, combinatorial problems, and planning \citep{dziri2024faith, valmeekam2022large, wu2023reasoning}. Inspired by these observations and to further investigate LLMs' reasoning abilities,  we offer a new benchmark of search problems, \ourbench{}.
The problems in \ourbench{} are combinatorial, defined as tasks that involve finding an optimal object from a finite set of objects, where the set of feasible solutions is either discrete or can be reduced to a discrete set \citep{comb_prob}. These problems are predominantly NP-hard and necessitate systematic exploration of action paths and backtracking to intermediate feasible states; thus, \ourbench{} implicitly investigates the LLM's capacity for non-linear reasoning.

\ourbench{} has five distinct problem categories: (i) pathfinding, (ii) puzzles, (iii) subset sum, (iv) sorting, and (v) under-determined systems; further divided into 11 unique problem types. 
Each problem type is inspired by known puzzles and combinatorial problems but
augmented with modified rules and constraints to ensure substantial differences from similar problems LLMs encountered during their training. And the solution to each problem is a sequence of actions leading from the initial state to the goal state, while optimizing a cost. 
We generate $\sim$100 instances of varying difficulty per problem type using an automatic pipeline, resulting in 1107 problem instances total. 
Each problem type in \ourbench{} is equipped with an automatic pipeline that evaluates LLM-generated solutions on three dimensions: feasibility, correctness, and optimality. Feasibility checks whether the actions taken follow the problem's rules; correctness verifies if a feasible solution reaches the goal state; and optimality checks if the least cost solution was found. 

\ourbench{} is challenging to LLMs due to several factors. Firstly, natural language is less suited for describing or updating accurate representations of complex intermediate states.
Secondly, our experiments show LLMs struggle with exploring a combinatorial exponentially exploding state-space. Despite the fact that some methods were developed for long-context reasoning \citep{chen2023walking,huang2022large,zhao2024expel}, \ourbench{} problems cannot be easily summarized \citep{chen2023walking}, reasoned about \citep{huang2022large}, or processed in parallel due to their size \citep{zhao2024expel, xi2023rise}.
Our findings show that even the strongest LLMs \citep{OpenAI2023GPT4TR} almost completely fail to solve  \ourbench{} problems in 
text-only mode.

To provide further insights, we show that LLMs' performance on \ourbench{} improves by prompting the models to solve the problems using the A* search algorithm \citep{Hart1968AFB}. A* is a heuristic-based graph traversal algorithm known for its time efficiency and provable optimality guarantees, making it the most suitable search algorithm for solving the problems in our benchmark. This method leverages A*'s correctness and optimality, while offloading some of the non-linear computations involved in searching the state-space to code execution.
Additionally, to improve the quality of generated A* codes, motivated that ensembling helps generation quality\citep{wang2022self, Yao2023TreeOT, long2023large}, we introduce the \model{} (\smodel{}) inference strategy. 
In the "Multi-Try" aspect of \smodel{}, before evaluating the solution returned by the code, we first verify whether the code generated by the model satisfies a set of unit tests: (i) it is executable; (ii) it returns a list as output; and (iii) data type of list elements is correct. If the code fails any of the tests, \smodel{} re-runs the LLM until a valid code is generated or allowed number of attempts is exhausted. 
The "Multi-Stage" aspect of \smodel{} generates the code in two steps: (i) `A* Implementation' - the implementation of an instance-agnostic A* algorithm for the problem type; and (ii) Initialization - the instantiation of initial conditions and state variables of the problem instance. In \smodel{} 'Initialization' is generated \textit{conditioned on} the `A* Implementation' (which is generated separately first and provided in `Intitialization' prompt).
We demonstrate that our \smodel{} A* method (Fig. \ref{fig:smt-astar}) significantly enhances the LLMs' ability to solve search problems, outperforming all other prompting strategies we used to evaluate models on \ourbench{}, including 0-shot text, 4-shot Chain-of-Thought (CoT)\citep{Wei2022ChainOT} text, 0-shot code generation, and 4-shot A* prompting with the naive greedy decoding strategy.







 To summarize, our main contributions are as follows:
(i) We contribute the \ourbench{} benchmark designed to assess the capability of LLMs in solving state-based problems requiring combinatorial search;
(ii) We introduce the A* \model{} (\smodel{}) framework that leverages the flexibility and natural language comprehension capabilities of LLMs, reliability and structured nature of the A* algorithm, along with unitests to verify LLMs' code generation in order to address search problems.
(iii) We show a strong advantage of \smodel{} A* prompting for 
solving search problems robustly with LLMs, suggesting interesting future work directions and yet leaving significant room for future improvement on \ourbench{}.

\section{\ourbench{}

\ourbench{} includes five categories of problems: puzzles, subset sum, sorting, pathfinding, and under-determined systems, further subdivided into 11 problem types and instantiated as 1107 natural language problem instances. Each problem type requires a different algorithmic approach to solve.
Our problems are inspired by well-known (mostly NP-hard) puzzles and search problems, though their rules were modified to ensure a solved instance of a problem similar to any SearchBench problem was not observed during LLMs' massive internet-scale training. The \ourbench{} taxonomy and rule modifications are illustrated in Fig. \ref{fig:searchbench-taxonomy}. 
Additionally, \ourbench{} problem instances are of variable difficulty and guaranteed to be solvable.
Finally, we note that only basic algebra skills are required for \ourbench{} problems, ensuring standard model pre-training should suffice for computing the answer to the problems.
In contrast to other reasoning benchmarks \citep{saparov2022language, cobbe2021training, hendrycks2021measuring, patel2021nlp, clark2020transformers, tafjord2020proofwriter, sap-etal-2019-social, le-etal-2019-revisiting} that only measure correctness, to gain a more comprehensive understanding of LLM performance on \ourbench{}, our evaluation pipeline assesses LLM solutions across 3 dimensions: Feasibility, Correctness, and Optimality. 
Feasibility determines if any problem rule violations (e.g. passing through labyrinth walls) occurred along the solution steps. 
Correctness requires that the solution path is both feasible and reaches the desired goal state from the given start state. 
Optimality requires a solution that is both correct and has minimum problem-specific cost w.r.t. known optimum. For each \ourbench{} problem we have implemented a fast A* algorithm with a provably admissible and consistent heuristic that is guaranteed to produce an optimal solution against which we measure optimality.

\section{Evaluated Methods}

We use the following 3 baseline prompting methods to evaluate LLMs on \ourbench{}: 0-shot text, 4-shot CoT text, and 0-shot code. Moreover, we introduce two additional code-based methods demonstrating improved performance: 4-shot A* prompting and \smodel{} A*.

\noindent \textbf{0-shot text and 4-shot CoT text prompting} 
instruct the model to solve the problem step-by-step (CoT \citep{Wei2022ChainOT}) using text only. 
In CoT part of in-context examples we use ASCII character graphics to represent the intermediate states of the problem after each action in order to ground the model's generation and prevent hallucinations or illogical leaps in reasoning. In-context examples were always drawn from the four \ourbench{} problem categories that differ from the category of the evaluated problem instance.

\noindent \textbf{0-shot code} 
instructs the LLM to produce a Python code that solves the given problem instance and explains the reasoning behind each line of code step-by-step (in code comments). Code is executed and its output is evaluated according to our metrics explained above. 
\noindent \textbf{A* Prompting}
prompts the LLM to implement an A* algorithm that solves $\mathcal{P}^C_i$ - a problem instance number $i$ of problem category $C$, providing 4 in-context examples of A* codes for 4 unrelated problems $\mathcal{P}^{\hat{C}}_j$ from different categories $\hat{C} \ne C$. In in-context A* implementations, problem states are modeled as graph nodes, and A* is used to traverse the graph to find an optimal path to the goal state. 
To implement A* for the target \ourbench{} problem, an LLM must perform a kind of abstract reasoning to devise a strategy that can be applied to any state within the search space. Additionally, it must understand the problem's rules and  map them to code by drawing parallels to rules of other (unrelated) problems and their respective A* implementations.
Our in-context examples include detailed comments before each code segment, explaining the reasoning used to develop the strategy implemented in the segment according to the problem statements. This encourages the LLM to implement the same kind of comments, which, in turn, serves as CoT reasoning for the generated A*.
\noindent \textbf{\model{} (\smodel{}) A* Prompting}
receives the same in-context examples as the `A* prompting', but operates in two stages and with different instructions in the prompt (Fig. \ref{fig:smt-astar}). In the first stage, 
the model is instructed to divide the code into two functions: the 'a\_star' function implementing an A* algorithm for the target problem type, and the 'initialize' function, which initializes the data structures and encodes the variables given in the problem statement. 
At this stage we only verify if the generated code satisfies a set of unit tests: (i) code is executable; (ii) code returns a list; (iii) and the list elements match the data type specified by the problem statement. If the code fails any unit test we re-generate the code.
In the second stage, the LLM is instructed to implement a refined `initialize' function, conditioned on the `a\_star' function from stage 1. 
The inclusion of simple unit tests, which can be expanded to more detailed tests if needed, offers a robust method for selecting a higher-quality sample from the model's generations.


\section{Related Work}

\noindent \textbf{Mathematical and Reasoning Benchmarks}: The evaluation of LLMs \citep{brown2020language, OpenAI2023GPT4TR, chatgpt, chung2024scaling, Chowdhery2022PaLMSL, Rae2021ScalingLM, taylor2022galactica,  thoppilan2022lamda} on mathematical and reasoning tasks has been a focus of recent research in natural language processing, leading to the development of benchmarks such as BIG-BENCH\citep{srivastava2022beyond}, GSM8K\citep{cobbe2021training}, AQUA\citep{ling2017program}, SVAMP\citep{patel2021nlp}, CommonsenseQA\citep{talmor2018commonsenseqa}, StrategyQA\citep{geva2021did}, and MATH\citep{hendrycks2021measuring}. However, these benchmarks have limitations. For instance, GSM8K problems are relatively simple and often require a repetitive reasoning pattern to solve. The MATH dataset, while more challenging, may not accurately reflect a model's reasoning or problem-solving capabilities due to the advanced mathematical skills required. Tasks in BIG-BENCH are mostly single-step reasoning tasks which do not challenge the models in effectively combining multiple steps required solve compositionally complex problems. When prompted to solve problems end-to-end using CoT prompting, LLMs perform well on these tasks; however, they almost completely fail on our benchmark's problems, indicating that these benchmarks offer limited insight into LLMs’ ability to systematically explore a state space and explore multiple reasoning chains that might lead to a solution.

\noindent \textbf{Application of LLMs to Combinatorial Problems}:
Several recent studies \citep{yang2023large, liu2024example, masoud2024exploring, mittal2024puzzlebench, iklassov2024self} have explored using LLMs to solve combinatorial problems.  \citet{yang2023large, liu2024example, masoud2024exploring} investigated promting LLMs to solve the Traveling Salesman Problem through multiple inferences. \citet{mittal2024puzzlebench} introduced a dataset of combinatorial problems, "PuzzleBench"; however, they only selected problems that can be represented in a symbolic solver (SMT2.0) and assumed there exists fixed pre-defined symbolic representations for input problems and outputs, somewhat limiting their datasets’ generalizability. Additionally, problems selected by \citet{mittal2024puzzlebench} and \citet{iklassov2024self} are instances of the classical combinatorial problems, raising issues of memorization as algorithm implementations for instances of such problems are often available online.
In contrast, our benchmark features problems with altered rules to ensure they are out of LLM's training data distribution. These problems require optimized solutions based on uniquely defined costs, making them more open-ended and challenging. Moreover, we introduce an automated pipeline for generating new instances and evaluating solutions on multiple dimensions, significantly improving the scalability of generating various instances of each type of problem.

\noindent \textbf{Prompting and Inference Strategies}:
Sophisticated prompting strategies have been developed to enhance models' reasoning abilities. One notable approach is Chain-of-Thought (CoT) prompting \citep{Wei2022ChainOT}, which prompts LLMs to generate the intermediate steps leading to the final output. This technique has led to advanced variations, including Self-consistency with CoT\citep{wang2022self}, Tree-of-Thoughts\citep{Yao2023TreeOT, long2023large}, and Graph-of-Thought\citep{Yao2023BeyondCE, Lei2023BoostingLR, Besta2023GraphOT} methods. Decomposition prompting strategies, such as those by \citet{khot2022decomposed,zhou2022least, zhang2023natural}, simplify complex tasks into smaller, manageable subtasks via symbolic programs or structured algorithms. Other works, like LLM-Augmenter system \citep{peng2023check}, rely on external databases to consolidate evidence and verify segments of the LLM generation.
In our experiments, we found CoT reasoning in text to be an ineffective prompting strategy for SearchBench problems. Hence, we propose the A* prompting strategy, where we prompt the model to solve problems by converting the problem states into a graph and implementing a unique A* algorithm to solve them. Similarly, our A* MSMT approach decomposes the task of implementing the search algorithm into two stages and checks the model's generations against external validators; we use simple unit tests instead of external data sources or solved solution instances in our work.

We evaluated the SearchBench performance of GPT-4 \citep{OpenAI2023GPT4TR}, GPT-3.5, and Code Llama Instruct 34B \citep{roziere2023code} (finetuned on the Phind dataset \citep{phind}), using the five methods explained in Sec. \ref{sec:method}: 0-shot text, 4-shot CoT text, 0-shot code, 4-shot A*, and 4-shot \smodel{} A*. Results are summarized in Fig. \ref{tab:all-results}.
\noindent \textbf{0-shot text and 4-shot CoT text:} The combinatorial nature of the search space of \ourbench{} problems and the difficulty of backtracking on state sequences explored during auto-regressive generation, make it very challenging to solve the problems using text based promoting approaches even using the strongest LLMs.
As shown in Fig. \ref{tab:all-results}, the correct solutions rate of both GPT4 and GPT3.5 is below 1\% using 0-shot text prompting, and less than 9\% of GPT4 solutions are feasible (follow the problem rules).
4-shot CoT text prompting improves the correct rate to 1.4\% for GPT4, and negligibly improves the feasible rate by less than 2\%. 
This validates that the inherent complexity of \ourbench{} search problems cannot be effectively addressed by text-based prompting alone.

\noindent \textbf{0-shot code:} This promoting method results in a small improvement compared to text-based prompting. 
From Fig. \ref{tab:all-results}, less than 20\% of GPT-4’s code generations result in a feasible solution, with only 11.7\% being correct. 
Moreover, on average, GPT-4’s 0-shot code generations, returning a correct solution, run 900 times slower than the optimal A* implementation. Expectedly, GPT-3.5 and Code Llama fall significantly below GPT4. This indicates \ourbench{} problems are indeed difficult even when facilitated through code generation.

Figure \ref{GPT4-code-based} details GPT-4 code-based method performance for each of \ourbench{}'s 11 problems. Consistently 4-shot A* prompting outperforms 0-shot code for most problems. Interestingly for problems in the pathfinding category, prompting GPT4 with 0-shot code outperforms A* prompting. 
Examining closer, GPT-4 mainly uses DFS for pathfinding in 0-shot code. While simpler than A*, DFS doesn't guarantee optimal solutions, as reflected in GPT-4's high feasible and correct rates but lower optimal rates. Implementing A* with an admissible and consistent heuristic requires the model to implement a more complex strategy in the code involving additional constraints and more sophisticated data structures. This increases the likelihood of reasoning or coding errors, which could explain the dip in GPT-4's performance using A* prompting compared to 0-shot code when solving these problems.

\noindent \textbf{\smodel{} A*:}
From Fig. \ref{tab:all-results}, we see that the \smodel{} A* prompting significantly enhances performance of both GPT-4 and GPT-3.5. With \smodel{} A*, GPT-4's code generations correctly solved 57.1\% of \ourbench{} problem instances and attained a 28.6\% rate of optimal solutions, consistently outperforming the model's performance using other promoting strategies for all problem types (Fig. \ref{GPT4-code-based}). A similar strong improvement is observed for other LLMs (only in feasibility in Code Llama as it still has issues with following the instructions even when using \smodel{} A*).
The improvement of \smodel{} A* over A* prompting shows that while LLMs can generate correct code, they often make coding and reasoning errors. \smodel{} unit tests help select higher-quality samples to mitigate these errors. The overall improvement in performance of LLMs promoted with \smodel{} A* demonstrates that emulating a structured algorithm in models through in-context learning and selecting a verified sample can significantly boost LLM's problem-solving capabilities. That said, the 28.6\% optimal performance, although inspiring, still leaves a lot of room for further improvements, underlining the importance of \ourbench{} for future research.

\section{Ablations and Analysis}


\noindent \textbf{Does including a more similar problem in the in-context examples improve GPT-4's performance?} 
In our main experiments with A* and \smodel{} A* (Fig. \ref{tab:all-results}), we used 4 different category problems (different from target evaluated problem) as in-context examples (Sec. \ref{sec:method}). This ensured no segment of the target problem solution was observed by the LLM in the in-context examples, hence better measuring LLM's reasoning generalization.
Here, we evaluated the effect of the prompt including a solved instance of a \ourbench{} problem of a different type than the evaluated problem, but sharing the same category. We used 5 \ourbench{} problems (1 per category) for this evaluation. Results are summarized in Fig. \ref{fig:sim-problem-ablation}.
For all problems we observe small improvements of up to 15 additional instances solved. This underlines that \ourbench{} problems of the same category are still significantly different in terms of their rules, constraints, and the target A* algorithm implementations.
We observe the most significant improvement for the Consecutive Grid problems, from the `under-determined systems' category. Mapping states of the under-determined systems to a graph is a difficult task, and this category more significantly differs from the others in terms of needed reasoning patterns, intuitively supporting our finding that seeing more similar problems in the prompt should lead to greater improvement.

\noindent \textbf{What types of errors occur, and how often, when running GPT-4's codes generated using different prompting methods?} We analyzed the run result of codes generated by GPT-4 that resulted in infeasible solutions, either by returning solutions that violated problem rules or by failing to produce valid solutions. The results of this analysis are summarized in Fig. \ref{fig:error-analysis-infeas}. In this figure "Solution Not Feasible" indicates that the code executed successfully and returned a solution in the correct format, but the solution did not adhere to the problem rules. "Program Returned None" means the program failed to find a solution, despite all instances in our dataset having provable guarantees to be solvable."Program Killed" signifies that the program did not complete execution within the allotted time frame (set between 2200 to 3200 seconds depending on the problem type. Our fast A*  implementation return an optimal solution for all \ourbench{} problems in under 600 seconds on the same system.)

As shown in Fig. \ref{fig:error-analysis-infeas}, prompting the model with the A* method results in a higher number of non-compiling code instances compared to 0-shot code prompting. This is expected as implementing A* is more complex and requires generating longer code than the simpler algorithms typically used by the model in 0-shot code generation, such as the greedy algorithm, BFS, or DFS. However, the number of infeasible solutions significantly decreases with A* prompting, indicating that the model can better reason about the problem when provided with the A* code context.
When comparing A* prompting to the \smodel{} A*method, we notice that all of the errors that lead to failing our unit tests significantly decrease. 'Program Returned None', 'Program Killed', 'Incorrect Solution Type', 'Incomplete Generation', and 'Program Didn't Compile' all fail at least one of the 3 unit tests utilized in our \smodel{} method. 

\noindent \textbf{What are the most common reasoning errors made in GPT-4's A* implementations?} We manually analyzed 50 A* codes generated by GPT-4 that returned an non-optimal solutions across five problems: three pathfinding problems and two puzzle problems. These problems were chosen because for them GPT-4 with A* prompting showed either the least or the greatest improvement compared to 0-shot code, respectively. We identified seven distinct failure modes in the GPT-4-generated A* implementations. Each failure mode corresponds to a critical subtask within the overall search strategy of the A* algorithm (see Tab. ~\ref{table:comparison} for the list of subtasks). Failing any one of these subtasks results in a suboptimal solution.  Results are summarized in Tab.~\ref{table:comparison} where the percent of `correct reasoning' (disregarding coding errors) is reported for each subtask.
As can be seen, in pathfinding problems, the most common reasoning mistake was failing to record the list of coordinates visited (13\% success rate). Specifically, the model often did not record the start coordinate in the list of visited states. This in turn led to feasible yet incorrect solutions, as the intermediate actions taken adhered to the problem's rules. For the puzzle problems, the most frequent reasoning mistake was in encoding the goal state. This is likely because our puzzle problem designs featured unique expected goal states, e.g. different from the conventional 8-puzzle problem.

\section{Conclusions, Limitations, and Broader Impact}

In this work, we introduced \ourbench{}, a pioneering benchmark designed to assess the reasoning capabilities of large language models (LLMs) in solving challenging and ubiquitous search problems using various text-based and code-based prompting methods.We demonstrated that advanced LLMs can, to some extent, successfully solve search problems by implementing structured algorithms with scaled reliability, especially when the models' implementations are verified against unit tests. 

This suggests a potential future path for automating the addition of new problem types to \ourbench{}. Specifically, we could leverage LLMs to generate evaluation and instance generation pipelines for new problem types based on a natural language description of the problem. Our \smodel{} approach could then verify the accuracy of these pipelines using comprehensive unit tests, significantly streamlining the process of scaling the dataset to include new problem types.

\noindent \textbf{Limitations:} The primary challenge in developing the \ourbench{} dataset was scaling the number of problem types. Designing unique search problems and creating pipelines to generate numerous instances with guaranteed solutions is both time-consuming and complex. Additionally, implementing a fast, instance-agnostic A* algorithm and developing evaluation pipelines to assess LLM-proposed solutions on multiple criteria further adds to the complexity. 

\noindent \textbf{Broader Impact:} Our research, which aims to assist the development of models capable of general reasoning and reliable problem-solving, has the potential to yield significant societal benefits. Combinatorial problems, like those in our dataset, are fundamental in fields such as robotics, logistics, network design, and industrial optimization. Developing models that can tackle unique versions of these problems by designing efficient algorithms or performing systematic searches end-to-end could greatly enhance AI's applicability across various domains.  However, this improvement in the reasoning capabilities of language models could also lead to job displacement, as these models could increasingly automate complex tasks traditionally performed by humans.
