\title{PoTable: Programming Standardly on Table-based Reasoning Like a Human Analyst}

\begin{abstract}
    Table-based reasoning has garnered substantial research interest, particularly in its integration with Large Language Model (LLM) which has revolutionized the general reasoning paradigm. 
    Numerous LLM-based studies introduce symbolic tools (\textit{e.g.}, databases, Python) as assistants to extend human-like abilities in structured table understanding and complex arithmetic computations. 
    However, these studies can be improved better in \textit{simulating human cognitive behavior} when using symbolic tools, as they still suffer from limitations of non-standard logical splits and constrained operation pools. 
    In this study, we propose \textsc{PoTable} as a novel table-based reasoning method that simulates a human tabular analyst, which integrates a Python interpreter as the \textit{real-time} executor accompanied by an LLM-based operation planner and code generator. 
    Specifically, \textsc{PoTable} follows a human-like logical stage split and extends the operation pool into an open-world space without any constraints. 
    Through planning and executing in each distinct stage, \textsc{PoTable} standardly completes the entire reasoning process and produces superior reasoning results along with highly accurate, steply commented and completely executable programs. 
    Accordingly, the effectiveness and explainability of \textsc{PoTable} are fully demonstrated. 
    Extensive experiments over three evaluation datasets from two public benchmarks on two backbones show the outstanding performance of our approach. 
    In particular, GPT-based \textsc{PoTable} achieves over 4\% higher absolute accuracy than runner-ups on all evaluation datasets. 

\end{abstract}

\section{Introduction}


Tables are widely applied in various scenarios (\textit{e.g.}, healthcare \citep{Healthcare-Table}, finance \citep{Finance-Table}), since they can visually present the core information in various types of scientific documents (\textit{e.g.}, articles, reports, websites) \citep{Table-Survey} through a structured format. 
With the growing development of AI techniques, there has been an increasing demand for automated table processing, attracting significant attention from both academia and industry \citep{Table-DL-Survey}. 
Recently, the evolution of Large Language Model (LLM) \citep{LLM-Survey} has raised a brand new prompting paradigm for table processing \citep{Table-LLM-Survey}. 
This training-free method facilitates complex understanding and reasoning procedures in table question answering \citep{WikiTQ}, table fact verification \citep{TabFact} and other downstream tasks (shown in Figure \ref{introduction}(a)). 

Throughout the history of humankind, tools have been regarded as the crystallization of human wisdom and a core factor in social productivity development \citep{Tools}. 
This consensus has inspired LLM-based techniques to go a step further in simulating more extensive human behavior, \textit{i.e.}, collaborating with symbolic tools to overcome LLMs' inherent limitations \citep{Tools-LLM}. 
In table processing, two unique challenges have been issued in earlier studies \citep{Table-LLM-Survey, Table-LLM-Tutorial}:
(1) Tables are structured in two-dimension, leading to unstable memorization of LLMs trained in next-token prediction mode \citep{TableMeetLLM}. 
(2) Table-based reasoning inevitably involves logical and arithmetic operations, and LLMs may produce misleading results due to their limited calculation abilities. 
Nevertheless, with a rising trend to utilize databases \citep{LLM-SQL}, Python \citep{PoT, PAL} and other symbolic tools as assistants, recent approaches effectively reduce table processing errors and misleading computational results by storing the tabular data into internal structure types (\textit{e.g.}, arrays, database tables) and executing syntactic computation commands (\textit{e.g.}, SQL, Python code) \citep{Binder, API-TableQA, TabSQLify}. 

Despite promising results of the existing studies, there is still room for improvement in \textbf{simulating human cognitive behavior in table-based reasoning}.
As shown in Figure \ref{introduction}(b), the human analyst follows a standard tabular data analysis process, considering all possible open-world operations in each stage to reach the local target and finally solve the given tabular task. 
In general, all the above stages and operations are implemented through a symbolic tool, such as Python with \texttt{pandas}\footnote{https://pandas.pydata.org/} package. 
However, existing studies ignore the standardization of logical split and only consider a few specialized operations for execution.
Specifically, some studies attempt to generate the overall program in one go for execution \citep{Binder}, while a few studies iteratively make decisions from pre-defined operation pools without logical boundary \citep{Chain-of-Table}. 
On the other hand, partial studies generate executable SQL or Python code of only sub-table and cell content extraction \citep{Dater,TabSQLify}, while a few studies only specify several commonly used operations for execution \citep{Chain-of-Table}. 
In summary, existing executor-based approaches still suffer from \textit{non-standard logical splits} and \textit{constrained operation pools} in tool execution. 
More effective utilization of symbolic tools is required to achieve better performance.

Along this line, we propose \textsc{PoTable} (\textbf{P}rogramming \textbf{o}n \textbf{Table}s Standardly) as a novel table-based reasoning method to simulate a human tabular data analyst, which integrates a Python interpreter as the \textit{real-time} executor accompanied by an LLM-based operation planner and code generator. 
In \textsc{PoTable}, we split the entire process into several standard table analysis stages, including initialization, row selection, data type cleaning, reasoning and final answering. 
In each stage, we set a macroscopic goal and expect \textsc{PoTable} to complete the goal through planning and executing. 
The planning module is in charge of generating chains including any helpful operations under the stage goal. 
The executing module is responsible for generating executable code based on the current operation and existing generated code, and calling the runtime to execute it at once. 
Notably, any raised errors lead to the status rollback of the interpreter and the LLM regeneration of the legal corresponding code with returned error information, otherwise it proceeds to the next operation. 

It can be clearly seen that \textsc{PoTable} follows a human-like analysis stage split and extends the constrained operation pool into an open-world space for symbolic tool execution. 
As a result, \textsc{PoTable} produces superior reasoning results with highly accurate, steply commented and completely executable code, which demonstrates its effectiveness and explainability.
Finally, we conduct extensive experiments over three evaluation datasets from two public benchmarks of table-based reasoning tasks on two backbones.
\textsc{PoTable} achieves much more outstanding accuracy results than all LLM-based baselines. 
In particular, GPT-based \textsc{PoTable} achieves over 4\% higher absolute accuracy than runner-ups on all evaluation datasets.
All experimental results and analyses validate the strong effectiveness of \textsc{PoTable}. 
In summary, our main contributions can be listed as follows:
\begin{itemize}
    \item We propose \textsc{PoTable}, a novel table-based reasoning method that programs standardly to simulate a human analyst. 
    Our method follows a human-like analysis stage split and extends the constrained operation pool into an open-world space for symbolic tool execution. 
    \item We integrate a Python interpreter as the real-time executor along with an LLM-based operation planner and code generation. 
    \textsc{PoTable} produces high-quality reasoning results with highly accurate, steply commented and completely executable programs, demonstrating its strong effectiveness and explainability. 
    \item Experimental results over three evaluation datasets from two public benchmarks of table-based reasoning tasks show the outstanding performance of \textsc{PoTable}. 
\end{itemize}



\section{PoTable}


\subsection{Task Formulation}

Our study focuses on two table-based reasoning tasks, \textit{i.e.}, table question answering and table fact verification. 
Each sample can be represented as $(T, Q, A)$, where $T$ denotes the structured table, $Q$ denotes a question to be answered or a statement to be verified. 
Given $T$ and $Q$, our goal is to find the answer $A$ in the table question answering task, while in the table fact verification task, we have to decide $A=1$ or $A=0$ indicating whether the statement is true or false, respectively.

\subsection{Overview}

We propose \textsc{PoTable} (\textbf{P}rogramming \textbf{o}n \textbf{Table}s Standardly), a novel table-based reasoning method shown in Figure \ref{potable}, where we integrate a Python interpreter as the \textit{real-time} executor along with an LLM-based operation planner and code generator.
In \textsc{PoTable}, the entire analysis process is split into five logical stages: initialization, row selection, data type cleaning, reasoning and final answering. 
In each distinct stage, the planning module is given a macroscopic stage goal to generate operation chains, while the executing module sequentially generates code for the current operation with the existing code base. 
In most prior studies, symbolic tools are utilized to obtain intermediate results for certain specified operations of decomposition or computation, as LLMs in reality play a dominant role as the global planner and the main processor. 
In contrast, \textsc{PoTable} offloads the duty of \textit{all operation execution} to the Python interpreter installing \texttt{pandas} package, while the LLM is responsible for planning reasoning operations and generating code. 
Consequently, \textsc{PoTable} better leverages LLMs' advantages in thinking decomposition and code generation, reducing errors from their disadvantages in structured table processing and arithmetic computations.

\subsection{Human-like Analysis Stage Split}

In tabular analysis, humans follow a standard processing pipeline with several stages, such as initialization, pre-processing, comprehensive analysis and post-processing. 
Standard and clear logical stage splits enhance reasoning effects and enable humans to draw highly accurate and well-supported conclusions.  
Inspired by human cognitive behavior in tabular analysis, we split the overall analysis procedure into several standard logical stages. 
These stages will be implemented through Python code with \texttt{pandas} methods as a common choice of human tabular analysts. 
Specifically, the overall analysis procedure is split into five stages with their own macroscopic goal:
\begin{itemize}
    \item \textbf{Initialization}: Store the table data into \texttt{pandas.DataFrame} object.
    \item \textbf{Row Selection}: Remove redundant rows that do not represent distinct records.  
    \item \textbf{Data Type Cleaning}: Transform the data type of table columns into a suitable form. 
    \item \textbf{Reasoning}: Conduct flexible reasoning operations that are useful to find the final answer. 
    \item \textbf{Final Answering}: Print out the final answer as the output of the evaluated sample.
\end{itemize} 
In the above stages, the initialization stage is implemented by executing the pre-defined Python code as \texttt{import pandas as pd} and \texttt{df = pd.DataFrame(data=..., columns=...)}, and then the LLM and the Python interpreter collaborate to traverse the other stages through meticulous planning and execution sequentially. 
The detailed procedure is explained in the next subsection.
We posit that this stage division is plausible to align with human cognitive behavior in tabular data analysis, which benefits the production of accurate answers and high-quality programs. 

\subsection{Planning and Executing}

To implement the whole table analysis procedure, we adopt a planning module and an executing module to complete the macroscopic goal in each stage. 
Such deployments leverage the LLM's advantage in thinking decomposition and code generation, and enjoy the benefits of robust memorization of structured tables and precise computational results of the symbolic tools simultaneously.

\textbf{Planning}. Inspired by Chain-of-Thought (CoT) \citep{CoT} prompting, the LLM decomposes the stage target into operation chains based on the current status of table \texttt{df}, while the output is always formatted as \texttt{<START>->[OP.]->[OP.]->$\cdots$-><END>} for easy operation extraction. 
We do not restrict the scope of planned operations but only require the operations to be useful in achieving the stage target even the overall tabular task goal. 
To prompt the LLM, we adopt a few-shot learning strategy \citep{GPT3} with three self-made examples for the planning module. 

\textbf{Executing}. Given an operation, the LLM generates code based on the current table status \texttt{df} and the existing code base. 
For the final answering stage, we adopt few-shot prompting with three self-made examples to obtain the code to print out the answer, while in other stages we adopt zero-shot prompting to generate the code.
Next, the generated code is sent to the Python interpreter for real-time execution. 
Most of the time, the execution is successful and then the table status is updated as the next input from \texttt{df} stored in the Python interpreter. 
Occasionally, the execution fails as the interpreter raises grammar error information or returns illegal output in the final answering stage. 
In this case, \textsc{PoTable} will roll back the interpreter to the status before the current execution, and urge the LLM to regenerate suitable code based on the abnormal information. 

Consequently, the final answer is obtained from the output of the executed code, instead of the direct LLM response of an LLM query. 
The overall algorithmic procedure is shown in Algorithm \ref{alg}.

\RestyleAlgo{ruled}
\SetKwComment{Comment}{/* }{ */}

\begin{algorithm}[]
\caption{\textsc{PoTable}}
\label{alg}
\KwIn{Table $T$, Question or statement $Q$, LLM $M$ and Python Interpreter $R$}
\KwOut{Answer $A$ to the question or statement}

$\operatorname{codeBase} \gets \operatorname{initalCode}(T)$

$R.\operatorname{executeCode}(\operatorname{codeBase})$

\For{$\operatorname{stage}$ $\operatorname{in}$ $\{\operatorname{``RowSelection''}, \operatorname{``DataTypeClean''}, \operatorname{``Reasoning''}, \operatorname{``FinalAnswer''}\}$}{
    $\operatorname{stageModule} \gets \operatorname{PoTableBlock(PlanPrompt[stage], CodePrompt[stage])}$
    
    $\operatorname{operationList} \gets \operatorname{StageModule.plan}(T, Q, M)$
    
    \For{$\operatorname{operaion}$ $\operatorname{in}$ $\operatorname{operationList}$}{
        $\operatorname{code}\gets \operatorname{stageModule.codeGen}(T, Q, M, \operatorname{operation}, \operatorname{codeBase})$
        
        $\operatorname{errorCnt} \gets 0$
        
        \While{$\operatorname{catchError}(R.\operatorname{executeCode(code)})$ $\operatorname{as}$ $ \operatorname{error}$ $\operatorname{and}$ $\operatorname{errorCnt}<10$}{
            $R.\operatorname{resetEnvironment().executeCode(codeBase)}$

            $\operatorname{code}\gets\operatorname{stageModule.codeReGen}(T, Q, M, \operatorname{operation, codeBase, error})$

            $\operatorname{errorCnt}\gets\operatorname{errorCnt}+1$
        }
        $\operatorname{codeBase} \gets \operatorname{codeBase} + \operatorname{code}$
        
        $T \gets R.\operatorname{getCurrentStatus}(T)$
    }
}
$A\gets R.\operatorname{getProgramOutput}()$

\Return $A$
\end{algorithm}

\subsection{Summarization}

According to the detailed procedure, we can conclude that \textsc{PoTable} overcomes two explicit limitations in the previous symbolic tools utilization, which enables our work to make great progress in simulating human cognitive behavior in tabular data analysis:
(1) \textbf{Human-like analysis stage split}: \textsc{PoTable} programs on tabular data following a standard logical stage split as a human analyst does. 
As a result, the LLM and the Python interpreter collaborate to complete the planning and executing with little interference in distinct stages. 
(2) \textbf{Open-world operation space}: \textsc{PoTable} extends the operation pool of the symbolic tools into an open-world space. 
If the operation benefits the completion of the target goal and the overall process, it will be possibly considered.

As a result, \textsc{PoTable} produces superior reasoning results with high-quality Python programs. 
The programs are highly accurate, steply commented and completely executable, since they correspond to clear operations and have experienced real-time execution and validation. 
These advantages and features demonstrate the strong effectiveness and explainability of \textsc{PoTable}.



\section{Experiments}


\subsection{Experimental Setup}

\textbf{Datasets}. We conduct experiments on three evaluation sets of two public benchmarks: \textbf{WikiTQ} \citep{WikiTQ} and \textbf{TabFact} \citep{TabFact}. 
WikiTQ is a benchmark for table question answering, which requires answering the question with a short corpus based on the given table. 
We conduct experiments over the validation (dev.) set with 2,831 questions and the test set with 4,344 questions as previous studies do, and use the official denotation accuracy for evaluation.
TabFact is a benchmark for table fact verification, which requires judging whether the given statement is true or false based on the given table. 
We conduct experiments over the released small test set with 2,024 statements as previous studies do, and use the binary classification accuracy for evaluation. 

\textbf{Backbones}. We select two representative language models as the backbones of \textsc{PoTable} and other baseline approaches in our experiments. Specifically, we choose GPT-4o-mini (2024-07-18)\footnote{https://openai. 
In addition, we choose Llama-3.1-70B-Instruct\footnote{https://ai.meta. 
\textbf{Baselines}. We select four competitive LLM-based approaches as baselines for comparison.
\textbf{Binder} \citep{Binder} is a neural-symbolic framework that maps the reasoning task into a specific program and then executes the program binding LLM as a unified API to extend its grammar coverage and tackle the commands that cannot be executed normally. 
\textbf{Dater} \citep{Dater} first decomposes the table into sub-evidence with column and row selection through LLM queries and then decomposes the question into simpler sub-questions through intermediate SQL generation, followed by a joint reasoning stage with simplified tables and questions. 
\textbf{Chain-of-Table} \citep{Chain-of-Table} pre-defines several common atomic operations for dynamic selection by the LLM, forming an operation chain to process the table with pre-defined code to simplify the table for the final LLM answer querying.
\textbf{TabSQLify} \citep{TabSQLify} leverages Text-to-SQL to decompose the table into sub-tables and conduct comprehensive reasoning and answer generation through LLM queries. 
All these selected approaches are competitive as LLM-based baselines on table-based reasoning. 

\textbf{Implementation Details}. To implement \textsc{PoTable}, we carefully design prompting templates for planning and executing modules of each stage. 
In addition, we respectively prepare three few-shot prompting examples for WikiTQ and TabFact, including query-answer pairs for both operation planning and final answer code generation.

To be more specific, we make a more comprehensive analysis of results from all approaches and base models. 
Firstly, Binder is always the runner-up in GPT-based approaches, while its accuracy drop based on LLAMA is 6\%-9\%. 
As Binder contains an important step to generate the whole program for the question, it seems that GPT-4o-mini enjoys a higher ability of code generation in one go. 
In comparison, \textsc{PoTable} has a standard logical split of the whole tabular analysis process and generates code once for a single operation with error checking, reducing possible blurred and uncleared code in the overall programs. 
Consequently, this may be one reason that our method achieves significant improvement over Binder and others in accuracy. 
Secondly, in LLAMA-based approaches, Chain-of-Table is the second-best approach although it has a constrained operation pool for dynamic selection, while its accuracy drop based on GPT is around 6\% in WikiTQ and 1.44\% in TabFact. 
Its reasoning performance mainly depends on the LLM's ability to plan and decompose the operations rather than code generating since the codes for all operations are pre-defined, which may indicate that Llama-3.1-70B-Instruct enjoys a stronger ability to plan and reason. 
In our \textsc{PoTable}, the two LLM abilities are fully stimulated, integrating the advantages of the open-world operation space of symbolic tools for more flexible planning and executing simultaneously. 
This may be another reason that our method outperforms Chain-of-Table and others in accuracy. 

As a result, \textsc{PoTable} overcomes the two limitations in the utilization of symbolic tools by following a human-like logical stage split and executing with an open-world operation space. 
Compared with the baselines, the way of standard programming in \textsc{PoTable} leads to its best accuracy, strongly validating the effectiveness in table-based reasoning scenarios.

\subsection{Ablation Study on Logical Stages}

In \textsc{PoTable}, the overall tabular analysis procedure is split into five stages inspired by standard human cognitive behavior. 
To validate the effect of the logical stage split, we present an ablation study by adopting different stage splits in the compared settings. 
Specifically, we compare the original GPT-based \textsc{PoTable} with the following four settings: 
(1) \textbf{Only Reasoning}: we discard all other unnecessary stages except for initialization, reasoning and final answering. In fact, this setting shows no explicit stage split.
(2) \textbf{Removing Row Selection}: we give up checking redundant rows before further processing and reasoning stages, which is commonly regarded as an operation of sub-table data extraction.  
(3) \textbf{Removing Data Type Cleaning}: we give up checking whether the table column data needs type transformation. As all table columns are stored with an initial type of string, discarding this operation may cause more error execution.  
(4) \textbf{Adding Column Selection}: we add a new column selection stage to select relative columns before further processing and reasoning stages. This stage has been included in most studies as an operation of sub-table data extraction.
The overall results of the ablation study on logical stages are shown in Figure \ref{ablation}. 

We can see that the original GPT-based \textsc{PoTable} outperforms all ablated settings in the three evaluation datasets. 
To be more specific, we make a more comprehensive analysis of results from all settings. 
Firstly, we focus on the ``only reasoning'' setting (abbreviated as \textit{only-rea.} below). 
Compared with the original setting, \textit{only-rea.} scores nearly 0.6\%-1\% less in WikiTQ and around 3\% less in TabFact. 
These results indicate that a standard logical split benefits the tabular analysis process. 
In addition, \textit{only-rea.} shows few weaknesses among all other settings in WikiTQ but has more accuracy drop in TabFact. 
From the task perspective, WikiTQ is about a clear task to answer the question directly, while TabFact asks to judge the statement, containing intermediate reasoning processes to judge the potential sub-facts. 
Therefore, the logical split for TabFact may be more necessary than WikiTQ, and it is also crucial to make the logical stage split as reasonable as possible. 

On the other hand, the results of settings ``removing row selection'' and ``removing data type cleaning'' demonstrate the importance of these stages as expected. 
A more interesting fact is the addition of ``column selection'' results in worse performance, which is widely adopted in previous approaches. 
We speculate that the selected backbones are competitive enough to handle full table columns, yet eliminating seemingly irrelevant columns may cause a dilemma, \textit{i.e.}, potentially useful columns are accidentally removed and the LLM reasoner cannot find adequate data for processing. 
Therefore, the operation of column selection is not suitable to be regarded as a distinct stage. 

As a completion, we also recompute the performance results grouped by task difficulty and table size.

\subsection{Case Study}

We conduct a case study of \textsc{PoTable} in Figure \ref{case} by presenting an evaluated sample from WikiTQ (T) with its generated Python program and output answer. 
The tabular task sample is fed into \textsc{PoTable}, experiencing a standard analysis process including five logical stages. 
From the complete program present, we notice the planned operations (shown as split comments in the stage block) and high-quality generated code of each operation (matching the former comment) for real-time execution, which allows us to review the whole process precisely and discover the true reason why it leads to right or wrong answers. 
In addition, the generated operations for execution are open-world as long as they are helpful to solve the stage goal, including some helpful commands like inter-mediate variable definition and finding the correct variable as the correct answer to output. 
Along with the answer, \textsc{PoTable} produces highly accurate, steply commented and completely executable code. 
These produced outputs indicate the strong effectiveness and explainability of our pipeline.

\section{Related Work}


\textbf{Table Processing with Language Models}.
Table processing has been a popular research domain over the past decade. 
Before the era of LLMs, numerous efforts were made to process tables with pre-trained language models.
TaPas \citep{TaPas} extends BERT \citep{BERT} by conducting masked pre-training with joint encoding of questions and flattening tables. 
TaBERT \citep{TaBERT} combines content snapshot and vertical attention based on BERT to obtain joint textual and tabular representations for further understanding. 
TUTA \citep{TUTA} enhances transformers \citep{Transformer} with structure-aware mechanisms to effectively capture spatial, hierarchical and semantic information.
TAPEX \citep{TAPEX} pre-trains BART \citep{BART} on a large synthetic SQL dataset to imitate the SQL executor that better understands tabular structure information. 
With the development of LLMs, the paradigm of table processing has been deeply revolutionized, especially in tabular data encoding and reasoning. 
In prompting methods, \citet{TableMeetLLM} designs a benchmark to evaluate the structural understanding capabilities of LLMs, followed by a novel self-augmentation for effective structural prompting. 
Dater \citep{Dater} and DIN-SQL \citep{DIN-SQL} adopt task decomposition for better understanding with simplified queries, while Chain-of-Table \citep{Chain-of-Table} defines atomic operations for dynamic selection in CoT prompting. 
Some other approaches explore training or tuning LLMs as generalists. 
TableLlama \citep{TableLlama} develops an open-source tabular LLM by fine-tuning Llama 2-7B \citep{Llama2} with LongLoRA \citep{LongLoRA}, while Table-LLAVA \citep{TableLLAVA} trains a multi-modal tabular LLM that can handle table images as vision inputs. 

\textbf{Table Processing with Symbolic Tools}. 
Symbolic tools have been widely utilized as assistants to produce more accurate and robust mid-results in LLM-based table reasoning scenarios. 
Most studies adopt databases and Python as affiliated executors to interact with LLMs. 
Binder \citep{Binder} and \citet{API-TableQA} parse the tasks into integral SQL or Python programs for further execution, incorporating LLM-assistant APIs to handle abstract code blocks for complete execution. 
TabSQLify \citep{TabSQLify} generates SQL queries to extract sub-tables and executes them to get simplified tables for further LLM reasoning. 
Some works target boosting the code generation ability for tabular reasoning and other scenarios. 
TroVE \citep{TroVE} asks the code LLMs to curate reusable high-level functions and use them to write solutions for Python execution on the table question answering and other tasks, while Self-Debugging \citep{Self-Debug} teaches LLMs to debug their predicted SQL or Python programs on Text-to-SQL \citep{Spider} and other tasks. 
Recently, research in LLM-based table reasoning has been extended into more sophisticated tools environments and more advanced reasoning tasks. 
SheetCopilot \citep{SheetCopilot} and SpreadsheetBench \citep{SpreadsheetBench} address a novel spreadsheet manipulation task, which maneuvers table analysis software like Microsoft Excel\footnote{https://www.microsoft.  
MatPlotAgent \citep{MatPlotAgent} addresses the task of scientific data visualization, which includes a code agent integrating \texttt{Matplotlib}\footnote{https://matplotlib.org/} responsible for generating the code to plot figures from input tables. 
As a result, symbolic tool utilization has become a crucial component in table processing.


\section{Conclusion}


In this paper, we focused on effective utilization of symbolic tools in LLM-based tabular reasoning.
We proposed \textsc{PoTable}, a novel method integrating a Python interpreter as the real-time executor along with an LLM-based operation planner and code generator. 
\textsc{PoTable} followed a human-like analysis stage split with an open-world operation space for execution. 
Through standard programming style, \textsc{PoTable} returned answers with highly accurate, steply commented and completely executable code, demonstrating its strong effectiveness and explainability. 
Extensive experiments under three evaluation datasets of two benchmarks on different backbones presented a dominating performance of \textsc{PoTable} on table-based reasoning. 
This study targeted standardized tables in the two fundamental reasoning tasks, yet automatic processing of complicated tabular data (\textit{e.g.}, hierarchical tables, multiple tables) and more advanced reasoning tasks (\textit{e.g.}, spreadsheet manipulation, sophisticated machine learning) remained less studied in LLM-based research. 
In the future, we will explore more effective ways to make our improved method competent on more complicated table-based reasoning scenarios, simulating more advanced human behavior in tabular analysis.
