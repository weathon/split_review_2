\title{OctoPack: Instruction Tuning Code Large Language Models}

\begin{abstract}

Finetuning large language models (LLMs) on instructions leads to vast performance improvements on natural language tasks. We apply instruction tuning using code, leveraging the natural structure of Git commits, which pair code changes with human instructions. We compile \data{}: 4 terabytes of Git commits across 350 programming languages. We benchmark \data{} against other natural and synthetic code instructions (xP3x, Self-Instruct, OASST) on the 16B parameter StarCoder model, and achieve state-of-the-art performance among models not trained on OpenAI outputs, on the HumanEval Python benchmark (46.2\% pass@$1$). We further introduce \eval{}, expanding the HumanEval benchmark to a total of 3 coding tasks (Code Repair, Code Explanation, Code Synthesis) across 6 languages (Python, JavaScript, Java, Go, C++, Rust). Our models, \model{} and \modelx{}, achieve the best performance across \eval{} among all permissive models, demonstrating \data{}'s benefits in generalizing to a wider set of languages and natural coding tasks.



\end{abstract}

\newpage

\label{sec:intro}

Finetuning large language models (LLMs) on a variety of language tasks explained via instructions (instruction tuning) has been shown to improve model usability and general performance~\citep{wei2021finetuned,sanh2022multitask,min2021metaicl,ouyang2022training}. The instruction tuning paradigm has also proven successful for models trained on visual~\citep{liu2023visual,li2023otter}, audio~\citep{zhang2023video} and multilingual~\citep{muennighoff2022crosslingual,wang2022super} data.

In this work, we instruction tune LLMs on the coding modality. While Code LLMs can already be indirectly instructed to generate desired code using code comments, this procedure is brittle and does not work when the desired output is natural language, such as explaining code. Explicit instructing tuning of Code LLMs may improve their steerability and enable their application to more tasks. Concurrently to our work, three instruction tuned Code LLMs have been proposed: PanGu-Coder2~\citep{shen2023pangucoder2}, WizardCoder~\citep{luo2023wizardcoder} and InstructCodeT5+~\citep{wang2023codet5+}. These models rely on more capable and closed models from the OpenAI API\footnote{\url{https://openai. This approach is problematic as \textbf{(1)} closed-source APIs keep changing and have unpredictable availability~\citep{pozzobon2023challenges,chen2023chatgpts}, \textbf{(2)} it relies on the assumption that a more capable model exists \textbf{(3)} it can reinforce model hallucination~\citep{gudibande2023false} and \textbf{(4)}, depending on legal interpretation, OpenAI's terms of use\footnote{\url{https://openai...You may not...use output from the Services to develop models that compete with OpenAI...''. Thus, we consider models trained on OpenAI outputs not usable for commercial purposes in practice and classify them as non-permissive in this work.

We focus on more permissively licensed data and avoid using a closed-source model to generate synthetic data. We benchmark four popular sources of code instruction data: \textbf{(1)} xP3x~\citep{muennighoff2022crosslingual}, which contains data from common code benchmarks, \textbf{(2)} Self-Instruct~\citep{wang2022self} data we create using a permissive Code LLM, \textbf{(3)} OASST~\citep{kopf2023openassistant}, which contains mostly natural language data and few code examples and \textbf{(4)} \data{}, our new 4TB dataset of Git commits. Instruction tuning's primary purpose is to expand models' generalization abilities to a wide variety of tasks and settings. Thus, we extend the code synthesis benchmark, HumanEval~\citep{chen2021evaluating,zheng2023codegeex}, to create \eval{}: A code benchmark covering code synthesis, code repair, and code explanation across six programming languages.

Instruction tuning StarCoder~\citep{li2023starcoder} on a filtered variant of \data{} and OASST leads to our best model, \model{}, which surpasses all other openly licensed models (\autoref{fig:main}), but falls short of the much larger GPT-4~\citep{openai2023gpt4}. GPT-4 is close to maximum performance on the code synthesis variant, notably with a pass@$1$ score of 86.6\% on Python HumanEval. However, it performs significantly worse on the code fixing and explanation variants of \eval{}, which we introduce. This suggests that the original HumanEval benchmark may soon cease to be useful due to models reaching close to the maximum performance. Our more challenging evaluation variants provide room for future LLMs to improve on the performance of the current state-of-the-art.

In summary, we contribute:
\begin{itemize}
\item \data{} and \dataft{}: 4TB of permissively licensed code commits across 350 programming languages for pretraining and a filtered 2GB variant containing high-quality code instructions used for finetuning
\item \eval{}: A benchmark for Code LLM generalization, spanning three scenarios (Code Repair, Code Explanation, Code Synthesis) and 6 programming languages (Python, JavaScript, Java, Go, C++, Rust)
\item \model{} and \modelx{}: The best permissive Code LLMs
\end{itemize}

Prior work has shown that models can generalize to languages included in pretraining, but absent during instruction tuning ~\citep{muennighoff2022crosslingual}. However, they also show that including such languages during instruction tuning boosts their performance further. We hypothesize that code data exhibits the same behavior. To improve performance on code-related tasks, we thus construct a code instruction dataset leveraging the natural structure of Git commits.

\footnote{\url{https://www.gharchive.org/}} We apply quality filters, filter for commercially friendly licenses, and discard commits that affect more than a single file to ensure commit messages are very specific and to avoid additional complexity from dealing with multiple files. This leads to almost 4 terabytes of data covering 350 programming languages (\data{}). As instruction tuning does not require so much data~\citep{zhou2023lima,touvron2023llama2}, we apply several strict filters to reduce the dataset to 2 gigabytes and 277 languages (\dataft{}). These include filtering for samples where the commit message has specific words in uppercase imperative form at the start (e.g. "Verify ..."), consists of multiple words, and does not contain external references. All filters are detailed in~\autoref{sec:datacreation}. \autoref{fig:data} depicts the distribution of both datasets and the tasks contained in \dataft{}. For instruction tuning our models, we select 5,000 random samples from \dataft{} across the 6 programming languages that we evaluate on. In~\autoref{sec:pretraining}, we also experiment with pretraining on the entirety of \data{}.

\paragraph{Alternatives} We consider three additional datasets for instruction tuning presented in~\autoref{tab:ablationsdata}. 
\textbf{xP3x}: xP3x is a large-scale collection of multilingual instruction data with around 532 million samples~\citep{muennighoff2022crosslingual}. We focus only on the code subset of xP3x, excluding NeuralCodeSearch~\citep{li2019neural} which is not licensed permissively, and select 5,000 samples. \\
\textbf{Self-Instruct}: Using the Self-Instruct method~\citep{wang2022selfinstruct} and the StarCoder model~\citep{li2023starcoder}, we create 5,003 synthetic instructions and corresponding answers.\\ 
\textbf{OASST}: OASST is a diverse dataset of multi-turn chat dialogues~\citep{kopf2023openassistant}. Only a few of the dialogues contain code. We reuse a filtered variant from prior work~\citep{dettmers2023qlora} and additionally filter out moralizing assistant answers (\autoref{sec:datacreation}) leading to 8,587 samples.



\section{\eval{}

\label{sec:eval}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{figures/humanevalpack.pdf}
    \caption{\textbf{\eval{} overview.} The first HumanEval problem is depicted across the three scenarios for Python. The bug for \evalf{} consists of a missing "abs" statement.}
    \label{fig:eval}
\end{figure}

When instruction tuning LLMs using natural language (NL) data, the input is an NL instruction with optional NL context and the target output is the NL answer to the task~\citep{wei2021finetuned}. When instruction tuning with code (C) data, code may either appear \textit{only in the input} alongside the NL instruction (NL+C$\rightarrow$NL, e.g. code explanation), \textit{only in the output} (NL$\rightarrow$C, e.g. code synthesis), or in \textit{both input and output} (NL+C$\rightarrow$C, e.g. code modifications like bug fixing). While prior benchmarks commonly only cover variants of code synthesis, users may want to use models in all three scenarios. Thus, we expand the code synthesis benchmark HumanEval~\citep{chen2021evaluating,zheng2023codegeex} to cover all three input-output combinations for six languages (\autoref{fig:eval}).

\paragraph{\evalf{} (NL+C$\rightarrow$C)} Given an incorrect code function with a subtle bug and accompanying unit tests, the model is tasked to fix the function. We manually add a bug to each of the 164 HumanEval solutions across all 6 languages (984 total bugs). For a given sample, the bugs are as similar as possible across the 6 languages enabling meaningful comparison of scores across languages. Bugs are written such that the code still runs but produces an incorrect result leading to at least one unit test failing. Bug statistics and examples are in \autoref{sec:bugs}. We also evaluate an easier variant of this task where instead of unit tests, models are provided with the correct function docstring as the source of truth to fix bugs, see \autoref{sec:docstrings}.

\paragraph{\evale{} (NL+C$\rightarrow$NL)} Given a correct code function, the model is tasked to generate an explanation of the code. Subsequently, the same model is tasked to regenerate the code given only its own explanation. The second step allows us to score this task via code execution and measure pass@$k$~\citep{chen2021evaluating} instead of evaluating the explanation itself using heuristic-based metrics like BLEU~\citep{papineni2002bleu} or ROUGE~\citep{lin2004rouge} which have major limitations~\citep{reiter2018structured,schluter2017limits,eghbali2022crystalbleu,zhou2023codebertscore}. To prevent models from copying the solution into the description, we remove any solution overlap of at least 20 characters from the description. We further enforce a character length limit on the model-generated explanation equivalent to the length of the docstring describing the function. This limit is specified in the prompt for the model. Note that the function docstring itself is never provided to the model for this task.

\paragraph{\evals{} (NL$\rightarrow$C)} Given a natural language docstring or comment describing the desired code, the model is tasked to synthesize the correct code. This task corresponds to the original HumanEval benchmark~\citep{chen2021evaluating}. For instruction tuned models, we add an explicit instruction to the input explaining what the model should do. For models that have only gone through language model pretraining, we follow \cite{chen2021evaluating} and provide the model with the function header and docstring to evaluate its completion of the function.

For all tasks we execute the code generations to compute performance using the pass@$k$ metric~\citep{chen2021evaluating}: a problem is considered solved if any of $k$ code generations passes every test case. We focus on the simplest version of pass@$k$, which is pass@$1$: the likelihood that the model solves a problem in a single attempt. Like \citet{chen2021evaluating}, we use a sampling temperature of $0.2$ and $top_p=0.95$ to estimate pass@$1$. We generate $n=20$~samples, which is enough to get reliable pass@$1$ estimates~\citep{li2023starcoder}. For GPT-4, we generate $n=1$~samples. Using $n=1$ instead of $n=20$ for GPT-4 only changed scores from 75.0\% to 75.2\% pass@$1$ on \evals{} Python while providing 20x cost savings.

Python HumanEval is the most widely used code benchmark and many training datasets have already been decontaminated for it~\citep {kocetkov2022stack}. By manually extending HumanEval, we ensure existing decontamination remains valid to enable fair evaluation. However, this may not hold for all models (e.g. GPT-4), thus results should be interpreted carefully.



\section{\model{}

\label{sec:model}

\subsection{Ablating instruction data choices}
\label{sec:ablate}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\linewidth]{figures/ablations.pdf}
    \caption{\textbf{Comparing permissively licensed instruction datasets by instruction tuning StarCoder.} Models are evaluated on the Python subset of \eval{}.}
    \label{fig:ablations}
\end{figure}

We instruction tune the pretrained StarCoder model~\citep{li2023starcoder} on different combinations of our instruction datasets (\autoref{sec:data}). We evaluate all models on the Python subset of \eval{} as depicted in~\autoref{fig:ablations}. Similar to prior work~\citep{alpaca}, we format all instructions into a consistent schema to distinguish question and answer (see \autoref{fig:octocoder}).

\paragraph{\dataft{} enables CodeLLMs to fix bugs} \dataft{} is critical for the performance boost on code repair (\evalf{}), where instruction tuning on only OASST or other variants results in a significantly lower score. This is likely due to \dataft{} including around 20\% of bug fixes among other code-related tasks (\autoref{fig:data}).

\paragraph{Importance of samples with natural language targets} The pretrained StarCoder model, as well as the Self-Instruct variant, perform poorly on code explanation (\evale{}). This is because both models are only conditioned to write code instead of natural language. We find that to perform well at explaining code, it is necessary to include samples with natural language as the target output during instruction tuning. Only relying on data with code as the target, such as the Self-Instruct data, will lead to models always outputting code even if the question requires a natural language output. Thus, we mix all other ablations with OASST, which contains many natural language targets. While the xP3x subset also contains samples with natural language output, many of its target outputs are short, which leads to models with a bias for short answers. This is impractical for the explanation task leading to the comparatively low score of mixing xP3x with OASST.

\paragraph{\dataft{}+OASST yields best performance} All instruction datasets provide similar boosts for code synthesis (\evals{}), which has been the focus of all prior work on code instruction models~\citep{wang2023codet5+,luo2023wizardcoder,muennighoff2022crosslingual}. We achieve the best average score by instruction tuning on \dataft{} mixed with our filtered OASST data yielding an absolute 23\% improvement over StarCoder. Thus, we select \dataft{}+OASST for our final model dubbed \model{}. Using the same data, we also instruction tune the 6 billion parameter CodeGeeX2~\citep{zheng2023codegeex} to create \modelx{}. Training hyperparameters for both models are in~\autoref{sec:hyperparameters}.

We benchmark \model{} and \modelx{} with state-of-the-art Code LLMs on \eval{} in \autoref{tab:humanevalpack}. For all models, we use the prompt put forward by the model creators if applicable or else a simple intuitive prompt, see \autoref{sec:prompts}. 

\paragraph{\model{} performs best among permissive models} \model{} has the highest average score across all three evaluation scenarios among all permissive models. With just 6 billion parameters, \modelx{} is the smallest model benchmarked, but still outperforms \emph{all} prior permissive Code LLMs. GPT-4~\citep{openai2023gpt4} performs best among all models benchmarked with a significant margin. However, GPT-4 is closed-source and likely much larger than all other models evaluated.

\paragraph{Instruction tuning generalizes to unseen programming languages} Trained primarily on natural language, not code, BLOOMZ~\citep{muennighoff2022crosslingual} performs worse than other models despite having 176 billion parameters. Go and Rust are not contained in BLOOMZ's instruction data, yet it performs much better than the random baseline of 0.0 for these two languages across most tasks. 
This confirms our hypothesis that models are capable of generalizing instructions to programming languages only seen at pretraining, similar to crosslingual generalization for natural languages~\citep{muennighoff2022crosslingual}. 
To improve programming language generalization further, we tune \model{} and \modelx{} on many languages from \dataft{}, and this generalization improvement is reflected in the performance on \eval{}'s new languages.

\paragraph{Pretraining weight correlates with programming language performance after instruction tuning} Prior work has shown that the performance on natural languages after instruction tuning is correlated with the weight of these languages during pretraining~\citep{muennighoff2022crosslingual}. The more weight during pretraining, the better the performance after instruction tuning. We find the same to be the case for programming languages. Python, Java, and JavaScript collectively make up around 30\% of the pretraining data of StarCoder~\citep{li2023starcoder}. After instruction tuning StarCoder to produce \model{}, we see the best performance among these three languages, especially for \evals{}. \model{} performs weakest on Rust, which is the lowest resource language of StarCoder among the languages we benchmark (1.2\% of pretraining data).

\paragraph{Models struggle with small targeted changes} \evalf{} is the most challenging task for most models. They commonly regenerate the buggy function without making any change (e.g. WizardCoder in \autoref{fig:wizardcoderpy}) or they introduce new bugs (e.g. GPT-4 in \autoref{fig:gpt4pyaddbugs}). We analyze model performance by bug type in \autoref{sec:modelbugs} and find bugs that require removing excess code are the most challenging. \model{} performs comparatively well across all languages. Instruction tuning on \dataft{} has likely taught \model{} to make small, targeted changes to fix bugs.

\paragraph{Models struggle switching between code and text} Some models fail at \evale{}, as they do not generate natural language explanations. We manually inspect explanations for the first ten samples of the Python split and disqualify a model if none of them are explanations. This is the case for StarCoder and CodeGeeX2, which generate code instead of natural language explanations. BLOOMZ and InstructCodeT5+ also occasionally generate code. Other models exclusively generate natural language explanations, not containing any code for inspected samples.

\paragraph{Models struggle adhering to a specified output length} \evale{} instructs models to fit their explanation within a given character limit (\autoref{sec:eval}). Current models appear to have no understanding of how many characters they are generating. They commonly write very short and thus underspecified explanations (e.g. BLOOMZ in \autoref{fig:bloomzjs}) or excessively long explanations that end up being cut off (e.g. StarChat-$\beta$ in \autoref{fig:starchatbetacpp}). Future work could investigate how to enable models to be aware of their generated output length to improve \evale{} performance.

\paragraph{HumanEval code synthesis is close to saturation} Pure code synthesis on \evals{} is the easiest task for all models. With a pass rate of 86.6\% for a single solution, GPT-4 is close to fully saturating the Python subset. GPT-4 was originally found to score 67\% on Python HumanEval~\citep{openai2023gpt4} and 81\% in later work~\citep{bubeck2023sparks}. Our score for GPT-4 is significantly higher, possibly due to improvements made to the API by OpenAI, contamination of HumanEval in GPT-4 training, or slightly different prompting and evaluation. An example of our prompt is depicted in~\autoref{fig:eval} (right). We perform very careful evaluation to ensure every generation is correctly processed. We reproduce the HumanEval score of WizardCoder~\citep{luo2023wizardcoder,xu2023wizardlm} and find it to also perform well across other languages. For BLOOMZ and InstructCodeT5+ our evaluation leads to a higher Python score than they reported, likely because of our more careful processing of generations. \model{} has the highest performance for every language among permissively licensed models. With a pass@$1$ of 46.2\% on the original Python split, \model{} improves by a relative 38\% over its base model, StarCoder. 


\section{Related Work}

\label{sec:rel}

\subsection{Code Models}

There has been extensive work on code models tailored to a specific coding task, such as code summarization~\citep{iyer2016summarizing,ahmad2020transformer,zhang2022survey,shi2022evaluation} or code editing~\citep{drain2021deepdebug,zhang2022coditt5,he2022distribution,zhang2022repairing,wei2023coeditor,prenner2023runbugrun,fakhoury2023towards,skreta2023errors} (also see work on edit models more generally \citep{reid2022learning,schick2022peer,dwivedi2022editeval,raheja2023coedit}). These works use task-specific heuristics that limit the applicability of their methods to other tasks. In contrast, we aim to build models applicable to all kinds of tasks related to code and beyond. 

Through large-scale pretraining more generally applicable code models have been developed~\citep{nijkamp2022codegen,nijkamp2023codegen2,xu2022systematic,christopoulou2022pangu,gunasekar2023textbooks,li2023starcoder,bui2023codetf,scao2022bloom,scao2022language}. However, these models only continue code making them hard to use for tasks such as explaining code with natural language (\evale{}). Teaching them to follow human instructions is critical to make them applicable to diverse tasks.

\subsection{Instruction Models}

Training models to follow instructions has led to new capabilities in text \citep{ouyang2022training, wang2022super, chung2022scaling} and visual modalities \citep{xu2023multiinstruct, openai2023gpt4}. Prior work has shown its benefits for traditional language tasks \citep{wei2021finetuned, longpre2023flan, iyer2022optiml}, multilingual tasks \citep{muennighoff2022crosslingual,muennighoff2024generative,yong2022bloom+,ustun2024aya}, and dialog \citep{kopf2023openassistant,bai2022training,gangulired}. For coding applications, PanGu-Coder2~\citep{shen2023pangucoder2}, WizardCoder~\citep{luo2023wizardcoder} and InstructCodeT5+~\citep{wang2023codet5+} are recent models trained with coding instructions. However, they all use the CodeAlpaca dataset \citep{codealpaca}, which is synthetically generated from OpenAI models. Using data from powerful closed-source models provides a strong advantage, but limits the model use and has other limitations highlighted in~\autoref{sec:intro}. CoEditor \citep{wei2023coeditor} proposes an ``auto-editing'' task, trained on 1650 python commit history repositories. Our work expands this to more general coding tasks via instructions, more languages, and orders of magnitude more commit data.

\subsection{Code Benchmarks}

Many code synthesis benchmarks have been proposed~\citep{wang2022execution,wang2022mconala,yu2023codereval,lai2023ds,du2023classeval}. HumanEval~\citep{chen2021evaluating,liu2023your} has emerged as the standard for this task. Prior work has extended HumanEval to new programming languages via automatic translation mechanisms~\citep{athiwaratkun2022multi,cassano2023multipl,orlanski2023measuring}. These approaches are error-prone and only translate tests, not the actual solutions, which are needed for tasks like code explanation. Thus, we rely only on humans to create all parts of \eval{} including test cases, correct solutions, buggy solutions, and other metadata across 6 languages.

Code repair is commonly evaluated on Quixbugs~\citep{lin2017quixbugs,prenner2021automatic,ye2021comprehensive,xia2023conversational,jiang2023impact,sobania2023analysis} or Python bugs~\citep{he2022distribution,bradley2023diffmodels}. The latter does not support code execution, which limits its utility. While Quixbugs supports execution with unit tests, it only contains 40 samples in Python and Java. Further, the problems in Quixbugs are generic functions, such as bucket sort. This makes them easy to solve and hard to decontaminate training data for. Our benchmark, \evalf{}, contains 164 buggy functions for six languages with solutions and unit tests. Further, our coding problems, derived from HumanEval, are very specific, such as keeping track of a bank account balance (see \autoref{fig:operatormisuse}). 

Prior work on evaluating code explanations~\citep{lu2021codexglue,cui2022codeexp} has relied on metrics such as METEOR~\citep{banerjee2005meteor} or BLEU~\citep{papineni2002bleu}. By chaining code explanation with code synthesis, we can evaluate this task using the execution-based pass@$k$ metric overcoming the major limitations of BLEU and other heuristics-based metrics~\citep{reiter2018structured}.

Large-scale benchmarking has proven useful in many areas of natural language processing~\citep{wang2019superglue,kiela2021hateful,bigbench,muennighoff2022mteb}. By producing 18 scores (6 languages across 3 tasks) for 9 models, we take a step towards large-scale benchmarking of code models. However, we lack many models capable of generating code~\citep{black2021gpt,fried2022incoder,black2022gpt,wang2021gpt,biderman2023pythia}. Future work may consider more models or extending \eval{} to new languages or tasks, such as code efficiency~\citep{madaan2023learning,yetistiren2022assessing} or code classification~\citep{khan2023xcodeeval}.



\section{Conclusion}


This work studies training and evaluation of Code LLMs that follow instructions. We introduce \data{}, a 4TB dataset of Git commits covering 350 programming languages. We filter this large-scale dataset to create \dataft{}, 2GB of high-quality code with commit messages that assimilate instructions. To enable a comprehensive evaluation of instruction code models, we construct \eval{}, a human-written benchmark covering 3 different tasks for 6 programming languages. We ablate several instruction datasets and find that \dataft{} combined with natural language data leads to the best performance. While our models, \model{} and \modelx{}, are the best permissively licensed Code LLMs available, they are outperformed by closed-source models such as GPT-4. In addition to improving the instruction tuning paradigm, future work should consider training more capable base models.
