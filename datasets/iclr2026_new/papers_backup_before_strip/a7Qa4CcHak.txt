## ABSTRACT

AI agents may soon become capable of autonomously completing valuable, long-horizon tasks in diverse domains. Current benchmarks either do not measure real-world tasks, or are not sufficiently difficult to meaningfully measure frontier models. To this end, we present Terminal-Bench 2.0: a carefully curated hard benchmark composed of 89 tasks in computer terminal environments inspired by problems from real workflows. Each task features a unique environment, human-written solution, and comprehensive tests for verification. We show that frontier models and agents score less than 65% on the benchmark and conduct an error analysis to identify areas for model and agent improvement. We publish the dataset and evaluation harness to assist developers and researchers in future work at [tbench.ai](http://tbench.ai).

## 1 INTRODUCTION

As AI agents gain the abilities to operate autonomously over long time horizons (Kwa et al., 2025), complete complex tasks (Ghareeb et al., 2025), and function in high-risk and valuable domains (Miserendino et al., 2025), benchmarks must also evolve to capture the diversity and difficulty of frontier tasks in realistic environments (Jimenez et al., 2024).

One such environment is the terminal: a ubiquitous, versatile, and powerful interface that is used for highly-skilled and valuable work like software engineering, scientific computing, cybersecurity, and machine learning. This degree of utility, coupled with its text-based nature, has recently made it a standard tool for AI agents like Cursor, Codex CLI, Claude Code, and Gemini CLI. These agents interact with the environment by directly issuing shell commands like `grep`, `find`, and `cat`, or by invoking more complicated custom tools to search the web, edit files, or execute code. Agents that use the terminal have become exceedingly popular for their simplicity and capability. For example, as of time of writing Anthropic claims that Claude Code drives \$1B in run-rate revenue (Anthropic, 2025).

In this paper we introduce Terminal-Bench, a framework to evaluate agents on realistic tasks in command line interfaces. Terminal-Bench evaluates whether agents can perform the kind of high-skill work that professionals are paid to do, including configuring legacy systems, reimplementing research papers, and solving general software engineering problems. Each *task* consists of (1) a containerized environment initialized with relevant packages and files, (2) an *instruction* that describes the task to be completed, (3) a set of *tests* to verify completion, and (4) a *reference solution* manually written to solve this task. We also introduce the Terminal-Bench 2.0 dataset, a set of 89 challenging tasks that have been manually verified by three human reviewers for correctness. These tasks require extensive domain knowledge, long chains of interdependent actions, and autonomous problem-solving that characterizes valuable technical work.

The remainder of this paper is structured as follows. First, we describe the process of creating Terminal-Bench 2.0. Then, we benchmark frontier LLMs and agents on the 89 tasks in Terminal-Bench 2.0, and find that frontier models and agents resolve less than 65% of tasks, with smaller models scoring around 15%. Finally, we provide a taxonomy of failure modes to assist future LLM and agent development.

## 2 TERMINAL-BENCH

Terminal-Bench is a framework for building realistic tasks that can be solved by agents using a terminal. Tasks range from training a machine learning model, to building and running Linux from its source code, to reverse engineering binary files.

### 2.1 TASK FORMULATION

A Terminal-Bench task consists of an instruction, a Docker image, a set of tests, an example solution, and a time limit (Figure 2). The instruction describes the task that the agent must complete within the specified time limit in the Docker container. The tests verify that all outcomes described in the instruction have been achieved by testing properties of the final container state; they do not test the agent’s commands or console output. This is intentional as Terminal-Bench is an *outcome-driven* framework where each agent is free to accomplish the task using a variety of approaches.<sup>1</sup>

Terminal-Bench tasks are interactive. Once the instruction and Docker container are provided to an agent, it must explore and manipulate the environment by calling tools (e.g., editing files or running Bash commands) to complete the task. Tasks are specified using the Harbor task format and are run using the Harbor harness, which supports popular agents, including Claude Code, Codex CLI, OpenHands, and Mini-SWE-Agent, as well as our own agent, Terminus 2, which we developed as a neutral testbed for comparing model performance (Section 3.4).

<sup>1</sup>The flexibility of this specification has allowed us to adapt 26 other preexisting benchmarks into the same format for compatibility with Terminal-Bench (Appendix E).

### 2.2 DATASET CONSTRUCTION

The Terminal-Bench task formulation is flexible and expressive, allowing for a diverse set of tasks in the benchmark. In order to design a diverse benchmark, we crowd-sourced tasks through open-source contributions, with 93 contributors creating 229 tasks. Contributors assigned expert and junior-engineer completion time estimates to their tasks. Of those 229, we selected 89 for the Terminal-Bench 2.0 dataset based on the author’s difficulty assessment and a quality assessment by three experienced human reviewers (Section 2.3). These tasks are described in detail in Appendix I.

### 2.3 VERIFICATION

We consider a task to be verified if experienced task reviewers determine that a task meets our standards in the following criteria:

**Specificity.** A terminal bench task is considered well-specified if the unit tests will pass if and only if the container ends in an acceptable state. That is to say, the task’s instructions describe all correct end states and that the task’s tests capture all correct end states.

**Solvability.** A task is solvable if it is possible for the final container state to pass the test cases. To confirm this, each task has an oracle solution script that mirrors a real workflow and, when executed, causes all test cases to pass.

**Integrity.** It should not be possible for an agent to “cheat” on a task by taking a shortcut that would not exist in a real-world deployment. For example, if a task involves editing a git repository at a particular commit, all future commits should be removed from the history so that the agent cannot cheat by viewing the repository’s future state.

### 2.4 COMPOSITION

Terminal-Bench tasks vary widely. For example, one task instructs the agent to write a function to parallelize  $n$  asynchronous jobs and properly execute each job’s cleanup code on keyboard interrupt, requiring the agent to understand the intricacies of Python asynchronous job management and test its implementation interactively by issuing keyboard interrupts. Another task asks the agent to rewrite a COBOL program in Python and tests for completion by ensuring identical input-output mappings for both programs.

Task authors were asked to report how long they thought a junior software engineer with little familiarity with the topic would take to complete their task (a “junior time estimate”) and how long a domain expert would require (“expert time estimate”). Table 1 shows the distribution of these estimates in Terminal-Bench 2.0. Authors also reported a high-level category for each task (Figure 4).

## 3 EXPERIMENTAL SETUP

We evaluate six state-of-the-art agents on Terminal-Bench 2.0 across 16 frontier models. For each supported model and agent combination, we run the benchmark at least five times, resulting in a total of 32,155 *trials*, where each *trial* is one agent’s attempt at solving a single task.

### 3.1 TERMINUS 2

Because Terminal-Bench is an interactive framework, agent and model performance are hard to decouple. Many agent scaffolds have been engineered to accommodate the tendencies of certain models, especially when the model and agent are developed by the same organization. Additionally, despite the name, we do not explicitly require agents to use a terminal as their sole tool. Instead, they are free to manipulate the container however they please. Many agents are installed directly into the container by a package manager and wield tools that are actually executable programs, far more complex than a typical Bash command.

To account for the constraints and biases of most agents, and to remain true to the benchmark’s premise, we created a simple scaffold, Terminus 2, which serves as a neutral testbed for comparing model performance. Terminus 2 has a single tool, a headless terminal, and completes tasks using only Bash commands. More details are available in Appendix G.

### 3.2 AGENTS

We evaluate three popular command-line agents (Claude Code, Codex CLI, and Gemini CLI) and three open-source software engineering agents (OpenHands (Wang et al., 2025), Mini-SWE-Agent (Yang et al., 2024), and Terminus 2) on Terminal-Bench 2.0.

### 3.3 MODELS

We select top closed-source models (GPT-5.2 (Int, 2026), GPT-5-Mini (OpenAI, 2025), GPT-5-Nano (OpenAI, 2025), Claude Opus 4.5 (Int, b), Claude Sonnet 4.5(Int, c), Claude Haiku 4.5 (Int, a), Claude Opus 4.1 (Anthropic, 2025), Gemini 3 Pro (Google DeepMind, 2025b), Gemini 3 Flash (Google DeepMind, 2025a), Gemini 2.5 Pro (Comanici et al., 2025), Gemini 2.5 Flash (Comanici et al., 2025), Grok 4 (xAI, 2025a), Grok Code Fast (xAI, 2025b)) and several popular open-weight models (GPT OSS 120B (OpenAI, 2025), GPT OSS 20B (OpenAI, 2025), Llama 4 Maverick (Meta AI, 2025), Qwen 3 Coder 480B (Yang et al., 2025a), Kimi K2 Instruct (Moonshot AI Team, 2025), Kimi K2 Thinking (Moonshot AI, 2025), GLM 4.6 (Zhipu AI (Z.ai), 2025), and Minimax M2 (Minimax, 2025)). Models with configurable reasoning effort are run with the provider’s default (i.e., “medium” for Anthropic and OpenAI models).

We evaluate each model using its compatible agent scaffolds. We run Claude Code, Gemini CLI, and Codex CLI with their respective companies’ models. Closed-source models are accessed through their first-party APIs, whereas open-weight models are queried through the Together.AI API.

### 3.4 HARBOR

Harbor is a framework we released for building and running agent evaluations at scale. Terminal-Bench tasks are implemented in the Harbor task format and executed using the Harbor harness. Terminal-Bench 2.0 is distributed via the Harbor registry and can be run with `harbor run -d terminal-bench@2.0`.

Harbor comes pre-integrated with multiple container sandbox providers. For our experiments, we use Daytona and run between 32 and 100 containers in parallel. The Harbor configuration files we use in the experiments are available at [github.com/laude-institute/terminal-bench-experiments](https://github.com/laude-institute/terminal-bench-experiments).

### 4.1 COST AND MODEL PERFORMANCE

Running Terminal-Bench 2.0 costs anywhere from one to a hundred dollars, depending on the model’s price (Figure 5). Most agents attempt tasks for less than 20 minutes. However, in some cases, they take up to two hours, making hundreds of API calls and using almost 100 million tokens on a single task, demonstrating the long-horizon potential of Terminal-Bench tasks (Figure 10). Despite this wide variation in interaction patterns, we find essentially no correlation between the number of average turns per trial and model success rates (Figure 35). Similarly, while models vary significantly in their token generation patterns, our analysis shows that higher token count does not necessarily correlate with better performance (Figure 36). In Appendix A we show that model performance has rapidly increased over time.

### 4.2 PREDICTED VS. EMPIRICAL DIFFICULTY

Each task in Terminal-Bench 2.0 includes an author-estimated difficulty for a human to complete the task (medium or hard). These labels, combined with task categories, support finer-grained categorization but are subjective and may not reflect the difficulty faced by agents.

To provide a more objective measure, we define “empirical difficulty” based on Terminus 2’s average pass rate across the frontier models in Section 3.3. Tasks are categorized as follows: Easy if Terminus 2 resolves the task with  $\geq 66.7\%$  of the selected frontier models, Medium if the resolution rate lies between  $33.3\%$  and  $66.7\%$ , and Hard if the resolution rate is  $< 33.3\%$ .

{7}------------------------------------------------

In general, there is a positive correlation ( $r = 0.436$ ,  $p < 0.001$ ) between human-predicted and empirical difficulty, and 93.3% of human-hard tasks are also empirically hard (Figure 6). These include complex problems such as **feal-differential-cryptanalysis** (differential cryptanalysis of the FEAL cipher) and **path-tracing** (implementing a physics-based renderer), which call for deep domain knowledge and non-trivial algorithmic implementation.

The largest discrepancy occurs when humans rate tasks as medium but models find them hard (54.5%), highlighting cases where human intuition provides advantages that models lack. These often require creative or adversarial reasoning rather than pattern-following, as in **break-filter-js-from-html** (XSS filter bypasses) and **winning-avg-corewars** (Redcode strategy). A notable share of medium tasks are empirically medium (29.1%) or empirically easy (16.4%), typically procedural sub-tasks (e.g., documentation adherence) that models execute reliably. For tasks that humans rate as hard, only 3.3% are empirically medium and 3.3% are empirically easy, indicating strong alignment at the upper end of difficulty.

### 4.3 TRAJECTORY-LEVEL ERROR ANALYSIS

To inform future agent and model development, we conduct an error analysis of model trajectories. Prior work has shown that failures can be systematic and can be clustered into several overlapping categories (Nathani et al., 2025; Pan et al., 2025; Zhu et al., 2025; Yang et al., 2025c). We derive a failure categorization building from the Multi-Agent System Taxonomy (MAST) (Pan et al., 2025), which defines broad classes and subcategories of failures. In our analysis, several of the MAST sub-categories were indistinguishable or irrelevant to our setup, and thus dropped accordingly. The result is a simplified taxonomy with three high-level classes – Execution, Coherence, and Verification — each with subclasses. A detailed breakdown with examples is provided in Appendix D.

For each task, we sample two failed trials per model. We use the same agent (Terminus 2) to provide a consistent evaluation setting and highlight differences between models. The failed trials are analyzed with Docent (Meng et al., 2025), together with a custom pipeline, to annotate, refine, and validate the rubrics in Pan et al. (2025). Docent uses language models to summarize, cluster, and search over agent transcripts, while our pipeline aggregated annotations from two human annotators. We iterate this process to refine the rubrics and labeling consistency. On a calibration subset of 20 trials, annotators achieve high agreement (93% Cohen’s- $\kappa$ ). GPT-5 (high-reasoning mode) serves as our primary judge. Compared against 120 human-labeled traces, this process achieves the closest alignment with human annotations, with an agreement of 90% (92% precision, 90% recall).

Figure 7 shows the distribution of failure modes across three models (closed and open sourced), with percentages reflecting the share of total failures in each category. The frontier closed sourced models evaluated display similar error profiles. Execution errors dominate for Opus 4.5 and GPT-5.2, while coherence and verification errors occur at lower rates. Conversely, the open sourced model evaluated (Qwen Coder) displays a more balanced error pattern, with higher errors across all failure modes. These distinct failure signatures suggest that different models require distinct strategies for improvement. Systems characterized by execution errors may benefit most from stricter adherence to instructions, while those with more balanced lapses require mechanisms for improved consistency and self-monitoring.

## 5 LIMITATIONS

Terminal-Bench is designed to test agents in a realistic environment; therefore, we allow agents to access the internet to install packages and query the web for relevant information. In theory, an agent could locate our dataset and cheat by reading the oracle solutions. In practice, we have not observed this behavior in tens of thousands of agent trajectories, though benchmark users should remain vigilant.

A related concern is that model developers could train on our dataset. We include the Big-Bench (Srivastava et al., 2023) canary string in each file in our repository to aid in training corpus decontamination. Options for preventing intentional contamination are more limited. We consider the development of a private test set to be outside the scope of this paper, given the substantial community investment required to build the benchmark. Future work should consider this option.

Terminal-Bench tasks are designed for reproducibility by pinning package versions, providing pre-built Docker images, and requiring dependencies to be included in the Docker context. Internet access, however, introduces external dependencies: agents may call APIs or download packages, and even stable resources can change over time. Additionally, variability in machine resources and container runtime enforcement can lead to differences in effective task environments.

Finally, despite the substantial emphasis placed on manual and language-model-assisted task quality review, there remains the possibility that some tasks could fall short of our verification criteria (Section 2.3). A less diverse benchmark without crowd contributions would be easier to verify, but we believe that the value of diversity and realism makes this an acceptable tradeoff. We invite the community to submit requests for changes to tasks to our repository.

## 6 RELATED WORK

**Related Benchmarks.** Many agent benchmarks focus on software engineering tasks including SWE-Bench (Jimenez et al., 2024), SWE-Bench Multimodal (Yang et al., 2025b), SWE-Lancer (Miserendino et al., 2025), HumanEval (Chen et al., 2021), and DevEval (Li et al., 2025a). Others measure tool-use, including  $\tau$ -Bench (Yao et al., 2025) and the Berkeley Function Calling Leaderboard (Patil et al., 2025). Computer use is another popular area of benchmark research including WebArena (Zhou et al., 2024), Visual Web Arena (Koh et al., 2024), AppWorld (Trivedi et al., 2024), and OS World (Xie et al., 2024). A fourth category is benchmarks for scientific discovery, including ReplicationBench (Ye et al., 2025), MLGym-Bench (Nathani et al., 2025), and Auto-Bench (Chen et al., 2025). Terminal-Bench is distinct in its emphasis on diverse, long-horizon tasks collected from experts. This ensures that the tasks are hard enough for frontier models, realistic, and economically valuable. Furthermore, in contrast to the synthetic environments used by other benchmarks, Terminal-Bench tasks are conducted inside a real terminal shell.

**Language Models and the Terminal.** Other benchmarks measure narrow aspects of the command line interface, like optimizing shell scripts (Lamprou et al., 2025), configuring software environments (Eliseeva et al., 2025), or translating natural language to Bash commands (Westenfelder et al., 2025). In comparison, Terminal-Bench is focused on general agentic manipulation of computers.

## 7 CONCLUSION

We have introduced Terminal-Bench, a new evaluation framework and a corresponding dataset, Terminal-Bench 2.0, that can be used to evaluate agentic LLMs on challenging tasks. As LLMs become increasingly capable, it will be necessary to benchmark them on increasingly challenging datasets. Taking real-world tasks that developers and researchers have encountered in the past is one such way to do so. We have found that validating the correctness of these tasks is extremely difficult, and as future work develops challenging agentic environments, we urge dataset curators to invest significant effort into manual verification (as we have done here), both ensuring that cheating is difficult and also verifying that all properties tested have been adequately specified in the task description.
