## Summary

This paper identifies two rigidity issues in heuristic multimodal RAG (non-adaptive and overloaded retrieval queries) and argues that existing VQA datasets cannot surface these flaws. It contributes Dyn-VQA, a dataset of 1,452 "dynamic" questions spanning three challenging categories (rapidly changing answers, multi-modal knowledge, multi-hop reasoning), and proposes OmniSearch, a self-adaptive planning agent that iteratively decomposes complex questions into sub-question chains with retrieval actions. Experiments show OmniSearch (GPT-4V) at 50.03% F1-Recall substantially outperforms heuristic mRAG baselines (best: 37.15%) and commercial search engines (best: 37.69%) on Dyn-VQA.

## Strengths

1. **Well-motivated problem with concrete failure cases.** The paper grounds the limitations of heuristic mRAG in two precise, observable failure modes (Non-adaptive Retrieval Queries and Overloaded Retrieval Queries), each illustrated with a clear example in Figure 1 (e.g., Cillian Murphy's latest film, Ling Jia vs. Teng Shen gross). This is not a generic framing — the examples directly motivate why fixed retrieval processes fail.

2. **Systematic dataset construction with empirical difficulty validation.** Dyn-VQA is built via a careful three-step human annotation process (Section 3.1) that decouples question writing, multimodal rewriting, and translation. The dataset's difficulty is empirically confirmed: human performance on Dyn-VQA (55.12%, Table 2) is substantially lower than on VQAv2 (74.31%), A-OKVQA (60.19%), and InfoSeek (63.67%), with humans averaging 1.57 web searches per question. This validates that the dataset captures genuinely harder retrieval challenges.

3. **OmniSearch outperforms heuristic mRAG baselines by a wide margin.** On Dyn-VQA, OmniSearch (GPT-4V) achieves 50.03% overall vs. 37.15% for the best two-step heuristic mRAG (GPT-4V with image caption + web search) and 37.69% for Gemini (Table 1). Even the Qwen-VL-Chat-based OmniSearch (41.20%) surpasses GPT-4V with two-step heuristic mRAG (37.15%), demonstrating the value of adaptive planning independent of backbone size.

4. **Detailed cost-performance analysis validating modularity.** Table 6 (token cost) shows that swapping the sub-question solver from GPT-4V to Qwen-VL-Chat nearly halves expense ($44.6 → $24.4 per sample) with under 4 points absolute performance loss (50.03% → 46.07%), empirically supporting the claimed plug-and-play scalability.

5. **Insightful analysis of model complementarity and domain-specific behavior.** The prediction overlap analysis (Figure 3) reveals that no model gets all questions correct and even the weakest model answers some questions GPT-4V misses, providing useful evidence for ensemble-based approaches. The domain radar chart (Figure 2) honestly identifies that OmniSearch can over-retrieve in low-sample domains (transportation), offering a balanced view of the method's limitations.

## Weaknesses

### Fatal
None.

### Major

- **No comparison against existing adaptive or agent-based baselines.** The paper motivates OmniSearch by arguing that heuristic fixed-query mRAG is insufficient, and claims OmniSearch is "the first multimodal retrieval agent for VQA tasks with self-adaptive planning." Yet all baselines are heuristic (single-hop/two-hop retrieval) or commercial search engines. There is no comparison to any existing adaptive retrieval approach — e.g., a ReAct-style agent with the same backbone and tools but without the trained planning module, or simpler iterative retrieval with chain-of-thought prompting. Without isolating the contribution of the trained planning mechanism, it is unclear whether OmniSearch's gains come from its self-adaptive planning or simply from using GPT-4V with multiple retrieval steps. This is the most significant evidential gap in the paper's experimental design.

### Minor

- **Evaluation metric ("F1-Recall") is poorly defined.** The paper describes it as calculating "the ratio of common tokens between model-generated responses and ground truth" and "the ratio of tokens generated by models belonging to the golden token list." The name "F1-Recall" is non-standard and the description is ambiguous — it is not precisely clear how precision and recall are computed and combined. While the description suggests two ratios are computed (supporting an F1-like measure), the paper should clarify the exact formula. If the metric does not penalize verbosity, longer answers could inflate scores and comparisons could be unreliable.

- **Upper bound is a simplified-query bound, not a true oracle for the original task.** The "Estimated Upper Bound" replaces the original question with a "golden query" that simplifies to the last hop only (Section 4), which changes the retrieval task (fewer steps, no visual disambiguation). The paper is transparent about this simplification, but calling it an "Upper Bound" is somewhat misleading — a proper task-level upper bound would provide the exact evidence needed for the original question, not a simplified query. This is a presentation issue rather than a fatal flaw, since the bound still serves as a useful reference point.

- **Training details for Qwen-based OmniSearch are under-specified.** The paper mentions using GPT-4V synthetic data, the InfoSeek dataset, and general instruction data for fine-tuning (Section 4), but provides no training hyperparameters (learning rate, batch size, number of steps, mixing ratios). This limits reproducibility.

### Trivial

- **No confidence intervals or variance bars** are reported for the main results (Table 1), which would be helpful for a 1.5K-instance benchmark.
- **Dataset size (1,452)** is relatively small. The paper argues for quality over quantity, which is reasonable, but statistical reliability would benefit from more instances.

## Nice-to-Haves

- Compare against a simple ReAct-style agent using the same backbone (GPT-4V) and tools but without the trained planning module, to isolate the benefit of OmniSearch's explicit sub-question decomposition.
- Report precision alongside the F1-Recall metric to verify that gains are not driven by verbosity.
- Conduct a small-scale human evaluation on a held-out sample to validate that the gold answers are unambiguous and that questions truly require the described dynamic retrieval steps.
- Add a dedicated limitations section discussing dataset size, reliance on Google APIs, potential annotator bias, and the over-retrieval issue observed in low-sample domains.

## Novel Insights

The prediction overlap analysis (Figure 3) offers a genuinely useful observation that extends beyond the paper's own claims: even the weakest model (InstructBLIP-Vicuna-7B at 12.87%) answers some questions that GPT-4V misses, and 31% of Dyn-VQA questions are not answered correctly by any model. This suggests that (1) current MLLMs have heterogeneous failure modes that are not simply a function of overall capability, and (2) the dataset captures challenges orthogonal to what existing benchmarks measure, making it a potentially valuable diagnostic tool. The domain-specific finding that OmniSearch over-retrieves in low-sample domains (transportation) is also noteworthy — it suggests the planning module lacks a reliable stopping criterion and becomes overly cautious when evidence is sparse, a concrete direction for improvement.

## Suggestions

1. **Add at least one adaptive/agentic baseline.** The simplest credible baseline would be: use the same backbone (GPT-4V) with the same retrieval tools but prompted with a generic "think step-by-step, retrieve as needed" instruction (ReAct-style), without the trained planning module or explicit sub-question decomposition. This would directly isolate the benefit of OmniSearch's trained planning.
2. **Clarify the metric definition precisely** — state the exact formula for precision, recall, and F1, or confirm that the reported "F1-Recall" is indeed the harmonic mean of precision and recall over tokens.
3. **Report variance** (e.g., bootstrapped confidence intervals) for the main results.
4. **Rename "Estimated Upper Bound"** to something like "Simplified-Query Reference" to avoid implying it is a task-level oracle.
