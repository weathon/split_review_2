## Summary

This paper investigates self-debugging in code generation when tests are themselves generated by the LLM (rather than oracle/human-written tests). It distinguishes two paradigms — post-execution (using final outputs and error messages) and in-execution (using intermediate runtime states) — and evaluates them on HumanEval, MBPP, and LiveCodeBench with four LLMs. The key findings are: (1) post-execution self-debugging with self-generated tests hurts performance on basic problems due to bias from inaccurate tests, but can help on competitive problems; (2) in-execution self-debugging mitigates this bias by focusing on intermediate states rather than test outputs, yielding improvements on both problem types.

## Strengths

1. **Clear empirical demonstration that post-execution self-debugging with self-generated tests degrades performance on basic benchmarks.** Table 2 shows consistent declines on HumanEval and MBPP for multiple models (e.g., Llama-3-70B-Instruct drops substantially), while Table 1 confirms that the same models improve when oracle tests are available. This clean contrast directly establishes the bias problem.

2. **Analysis of the bias mechanism through label-change distributions.** Figure 2 quantifies how self-generated tests produce a dominance of false-negative labels (correct programs flagged as failing) on basic benchmarks, while the label distribution shifts on competitive problems (LiveCodeBench). Table 3 further shows the accuracy of self-generated tests. This analysis goes beyond simple pass-rate reporting to explain *why* post-execution self-debugging fails or succeeds.

3. **Formalization of two distinct self-debugging paradigms.** Section 3 provides explicit mathematical definitions for post-execution (comparing execution output $\tilde{Y}_i$ to expected output $Y_i$) and in-execution (tracing variable states $V_i^k$ across basic blocks $B^k$), structuring a previously vague research space.

4. **Evaluation across multiple difficulty levels within LiveCodeBench.** Table 4 reports results separately for easy, medium, and hard problems, showing that the effect of post-execution feedback varies substantially with difficulty — label feedback helps across all levels for GPT-4o, while detailed feedback hurts easy problems.

### Minor

1. **The claim that in-execution "consistently outperforms" post-execution is partially undermined by insufficiently documented iteration counts.** The paper mentions "iterations" for post-execution results (Tables 1 and 2 are described as "showcasing significant improvements as iterations progress" and "with more detailed feedback and iterations"), and for in-execution it explicitly states "after two iterations." However, the exact number of iterations for post-execution is never clearly stated — the paper says "iterations" in a general sense. While the critic's specific claim that post-execution shows only "one round" is contradicted by the paper's own text (which references multiple iterations), the broader point stands: the paper should explicitly state the number of self-debugging rounds for each paradigm and ensure they are matched for a fair comparison. Without this clarity, the reader cannot fully assess whether the advantage of in-execution is due to the paradigm or simply more iterations.

2. **Garbled description of the LiveCodeBench bias pattern.** The paper states (Section 4.3): "We observed that testing on self-generated tests is more likely to result in false negative labels than true negative ones on both HumanEval and MBPP. However, a different pattern emerges on LiveCodeBench, where false negatives are more than true negatives." The phrase "different pattern" is directly contradicted by the subsequent description (FN > TN in both cases). The intended meaning — that on harder problems, true negatives increase relative to false negatives — is discernible from context but the writing as-is is confusing. This obscures the key analytical finding of Figure 2.

3. **Prompt design and intermediate-state representation details are not described.** The paper explains the high-level approach for in-execution self-debugging (using basic blocks and execution traces) but does not show example prompts or describe how the model is instructed to reason from traces. While an appendix may partially address this, the main paper's reproducibility would benefit from at least a representative example.

4. **No analysis of false repairs from in-execution.** The paper reports slight performance declines in some conditions (e.g., Llama-3 on MBPP) but does not analyze whether these stem from misinterpretation of intermediate states. An error analysis would deepen the understanding of when in-execution helps vs. hurts.

## Nice-to-Haves

- **Compare in-execution (self-generated tests) against oracle-based in-execution.** The paper shows oracle-based post-execution (Table 1) for reference but does not provide the analogous oracle-based in-execution comparison. Doing so would position the gains from in-execution relative to the upper bound.
- **Report statistical significance or confidence intervals.** Pass rates are point estimates; on small benchmarks like HumanEval (164 problems), differences of a few percentage points may not be meaningful.
- **Discuss computational cost.** In-execution requires extracting intermediate states per basic block, which plausibly increases tokens and runtime. A brief cost comparison would strengthen practical recommendations.

## Suggestions

1. **Explicitly state the number of self-debugging iterations used for each paradigm in every table**, and ensure both paradigms are evaluated with the same iteration budget for any comparative claims. Currently the paper is vague about post-execution iteration counts.
2. **Fix the garbled description of Figure 2** so that the claimed "different pattern" on LiveCodeBench is properly described (TN > FN, not FN > TN, or clarify what the actual difference is).
3. **Add a brief error analysis for in-execution**: how often does the model misinterpret intermediate states, and what types of bugs does it successfully identify vs. miss?
