## Summary

The paper introduces SASS, a semi-supervised framework for open-source LLMs to generate their own instruction-tuning data without relying on closed-source model outputs. It systematically compares two strategies — Self-Training (generating responses for existing instructions) and Instruction-Generation (generating instructions for existing documents) — finding the latter superior. Two enhancements are proposed: a perplexity-based instruction filtering strategy to improve instruction-response alignment, and an extract-then-generate strategy to increase instruction diversity. Experiments on the LongForm benchmark and AlpacaEval show that instruction tuning with SASS-generated data (using only LLaMA-7B) outperforms several baselines, including methods that distill from GPT-4 or other closed-source models.

## Strengths

- **Clean head-to-head comparison of IG vs. ST strategies.** Section 3.4 and Figure 1 provide a controlled experimental contrast between Self-Training and Instruction-Generation across two seed instruction datasets (Lima, Dolly). IG consistently outperforms ST with little variance, supporting the paper's core design choice with clear empirical evidence.

- **Perplexity-based instruction filtering is well-motivated and ablated.** Section 4.1 proposes selecting the candidate instruction that minimizes response perplexity. Figure 4(a) shows this filtering step yields a significant improvement (roughly +1 METEOR point), directly confirming its effectiveness.

- **Extract-then-generate improves both diversity and performance, with careful ablations.** Section 4.2 evaluates three fragment extraction methods (Keywords, Random Sentence, LLM Extraction). Figure 4(b) demonstrates LLM Extraction outperforms simpler heuristics, and combining it with the original document yields the best result. Figure 5 provides linguistic evidence that extracted fragments increase instruction diversity.

- **Self-alignment finding for weaker models is surprising and well-demonstrated.** Section 5.5 and Figure 6 show that Baichuan2-7B and BLOOMZ-7B1 trained on their own self-generated data perform on par with training on data generated by the stronger LLaMA-7B. This finding — that a weaker model can generate effective instruction data for itself — is non-trivial and well-supported.

- **Main result shows SASS outperforming baselines that rely on closed-source models.** Table 1 reports that LLaMA-7B fine-tuned with SASS-generated data achieves the highest average METEOR on the 8-task LongForm benchmark, outperforming methods like Evol-Instruct (which uses GPT-3.5/4) and Dromedary (which uses LLaMA-65B). This directly supports the paper's central claim that open-source-only instruction generation can match or exceed closed-source distillation.

## Weaknesses

### Fatal

None. No verified criticism invalidates the paper's core claims or results outright.

### Major

- **Potential training/evaluation overlap between minipile and LongForm is not discussed.** The paper uses documents from `minipile` (which draws from CommonCrawl, Wikipedia, books, and code) as the unsupervised response corpus (Section 3.2). The LongForm benchmark (line 75) includes sub-tasks from C4 (CommonCrawl-sourced), Wikipedia, Stack Exchange, WikiHow, and other sources — all of which are present in `minipile`. If any documents used as training responses (or near-duplicates) appear in the LongForm test set, the model's METEOR scores could be artificially inflated because the model was explicitly trained on instruction–response pairs for those same texts. The paper contains no decontamination analysis or discussion of this issue. This does not invalidate the results (the baselines are evaluated on the same benchmark and AlpacaEval provides a contamination-free signal), but it substantially weakens the evidential basis of the primary quantitative claim. The authors should either perform an overlap analysis or evaluate on a held-out benchmark known not to overlap with `minipile`.

### Minor

- **Training set sizes of baselines are not reported.** The paper (Section 5.1) lists baseline datasets (Lima, Dolly, Evol-Instruct, LLaMAGPT4, Dromedary, DYNASAUR, LongForm training split) without stating how many examples each contributes. For example, Lima has ~1k examples, Dolly ~15k, Evol-Instruct ~52k, and LLaMAGPT4 ~52k. Without this information, readers cannot assess whether the comparison confounds method quality with data quantity. The authors' method uses 50k examples (stated in line 64), which is larger than some baselines but comparable to or smaller than others (Evol-Instruct, LLaMAGPT4). Reporting sizes would strengthen the comparison considerably.

- **Primary automatic metric (METEOR) has limited fidelity for instruction following.** METEOR is an n-gram overlap metric that poorly captures instruction-following quality, especially for open-ended generation. While the paper partially addresses this by also using GPT-4 evaluation on AlpacaEval (Figure 3), that evaluation is a single head-to-head comparison (win rate vs. Davinci003) and is not applied to the LongForm tasks where the core claims are made. This weakens confidence in the main results.

- **No error bars, confidence intervals, or multiple-run statistics.** All reported METEOR scores and win rates are single numbers with no variance estimates. Given stochasticity in nucleus sampling and fine-tuning, it is unclear whether performance differences (e.g., the ~52% vs. ~50% win rate on AlpacaEval, or small METEOR differences between methods) are statistically meaningful.

- **The perplexity-filtering model is underspecified.** Section 4.1 says to use "the instruction-following model" to compute PPL, but does not specify which checkpoint is used — the seed instruction-following model (fine-tuned on Lima/Dolly), the original LLaMA-7B, or something else. This affects reproducibility.

### Trivial

- The paper describes the ShareGPT input instructions as falling outside closed-source usage restrictions (line 53). While this is a reasonable argument, it is worth noting that these instructions originate from user interactions with a closed-source model, which some might consider a grey area. This does not affect the paper's contributions but is worth acknowledging.

## Nice-to-Haves

- A human evaluation sample (e.g., 100–200 examples) would greatly strengthen credibility given the known limitations of automated metrics.
- Evaluating on held-out reasoning/coding/math tasks (e.g., MMLU, GSM8K) would demonstrate that the method generalizes beyond text generation.
- Controlling for training set size across all baselines (e.g., subsampling to a common size) would make the comparison cleaner.
- Reporting computational cost (GPU-hours for generation, filtering, and training) would be useful for practitioners.

## Suggestions

1. **Perform a decontamination analysis** between the minipile documents used for training and the LongForm test set. Report overlap statistics and either exclude overlapping examples or evaluate on a contamination-free benchmark (e.g., MMLU, HellaSwag, or a manually curated set).

2. **Report the number of examples** for each baseline dataset in Table 1, and ideally include a controlled comparison where all methods use the same number of training examples.

3. **Report variance** (mean and std over 3 runs with different seeds) for the main METEOR scores and AlpacaEval win rates.

4. **Clarify which model checkpoint** is used for the PPL-based instruction filtering.
