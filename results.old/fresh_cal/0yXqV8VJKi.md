## Summary

This paper introduces CodePlexity, a method that uses code complexity metrics on visual programs (generated by LLM-based code generation models for VideoQA) to estimate question difficulty. The approach mines subroutines from program ASTs to quantify difficulty and identify interpretable challenging patterns (e.g., reasoning about event order, fine-grained object details). It also constructs a new benchmark, CodePlex-QA, by automatically generating questions and filtering by CodePlexity complexity scores. The paper demonstrates that code-based metrics outperform human estimates and text-based baselines at predicting which questions models will struggle with.

## Strengths

- **Code-based complexity is shown to predict model performance better than human estimates and text-based metrics.** The paper provides direct evidence (Figure 3, Table 1) that even simple code metrics like cyclomatic complexity correlate more strongly with model success rates than human judgments. Lines of Code beats all text-based metrics on held-out models (e.g., InternVideo: 8.9 LoC vs 4.0 dependency tree depth).

- **CodePlexity achieves the best predictive power across all held-out models.** Table 1 shows CodePlexity achieves the highest mPEG on every held-out model (e.g., InternVideo 13.7, Tarsier 12.0), substantially improving over cyclomatic complexity (10.9 and 9.8 respectively). This demonstrates that learning which code subroutines correlate with model failures adds value beyond purely structural measures.

- **The approach yields interpretable insights about model failure modes.** The subtree analysis (Section 4.3, Figure 4) identifies 8 subroutines shared across three diverse architectures (SeViLA, ViperGPT, VIOLET), translating code patterns into interpretable failure modes: reasoning about event order and fine-grained object details. These align with known VideoQA weaknesses but are systematically discovered from data.

- **The benchmark generation pipeline is practical, requiring only 12% manual filtering.** Out of 2261 automatically generated questions, only 12% were removed for answerability issues, demonstrating that the approach can produce usable datasets with minimal human effort (Section 5.2).

## Weaknesses

### Fatal
None.

### Major

- **The 1.9× difficulty comparison between CodePlex-QA and NExT-QA is not properly controlled.** The paper reports that CodePlex-QA is "1.9 times harder" than NExT-QA (Table 2), but does not clarify whether the NExT-QA numbers for VIOLET and InternVideo come from fine-tuned or zero-shot evaluation. The paper describes VIOLET and InternVideo as "fine-tuned for VideoQA" (Section 4.1). If their NExT-QA performance is from fine-tuned variants while CodePlex-QA performance is zero-shot (which is how the paper evaluates them), the gap is inflated by comparing different evaluation regimes. While SeViLA-ZS (zero-shot on both), ViperGPT (inherently zero-shot), and ATP (inherently zero-shot) all show large gaps, the exact 1.9× figure reported uses the average of all five models without clarifying the evaluation settings. This weakens the headline quantitative claim. The paper must either report zero-shot performance of all models on NExT-QA under identical conditions or clarify what the NExT-QA numbers represent. This is a significant issue but not fatal because the other three models with fair comparisons also show substantial gaps.

### Minor

- **No multiple testing correction for subtree significance analysis.** Section 3.3 identifies subtrees whose presence correlates with decreased performance at p<0.01. With potentially thousands of subtrees in S_merged, the expected number of false positives is substantial. The paper does not report how many subtrees were tested or apply any correction (Bonferroni, FDR). The qualitative findings (e.g., temporal ordering, fine-grained object details) are plausible and align with prior work, but their statistical grounding is weaker than claimed.

- **No discussion of regularization or feature frequency thresholds for the logistic regression.** CodePlexity trains on one-hot vectors of subtree presence, which could be high-dimensional with many rare subtrees. The paper does not discuss whether rare subtrees were filtered or whether L1/L2 regularization was used to prevent overfitting. Given that the evaluation uses held-out models (Table 1), this partially addresses the concern, but the design choices are underreported.

- **No minimum frequency threshold for subtrees in the proportion tests.** Section 3.3 uses one-sided proportion tests, which can produce unreliable p-values when a given subtree appears in very few questions. The paper should report a minimum frequency threshold used for inclusion.

- **No confidence intervals or significance tests for mPEG differences in Table 1.** Several improvements are modest (e.g., CodePlexity 0.266 vs cyclomatic 0.250 for SeViLA-ZS), and it is unclear whether these differences are statistically significant. Reporting confidence intervals or paired significance tests would strengthen the claims.

### Trivial

- **Human study lacks inter-annotator agreement metrics.** The study uses 150 questions and 30 subjects (Section 4.1), but does not report agreement (e.g., Kendall's W) or the quantified correlation between human rankings and model accuracy. While the qualitative finding that humans struggle is clear, the effect size is not quantified.

- **The formula for "1.9× harder" is vaguely described.** The paper says "dataset complexity estimated by taking the average performance of the 5 methods and subtracting random chance" (Section 5.2). The exact computation is inferable but should be explicitly stated.

## Nice-to-Haves

- **Ablate the benchmark generation pipeline.** Show that CodePlexity filtering is responsible for increased difficulty, not the LLM-based question generation itself, by comparing CodePlexity-filtered vs. randomly-filtered or baseline-filtered candidate pools.

- **Validate generalizability beyond NExT-QA.** Train CodePlexity on NExT-QA and evaluate its predictive power on a different VideoQA dataset (e.g., TGIF-QA, MSRVTT-QA) to demonstrate that learned subtrees are not dataset-specific.

- **Analyze how generated program quality affects the metric.** Compare complexity scores for questions where the generated program's answer matches ground truth vs. where it does not, to verify robustness to program errors.
