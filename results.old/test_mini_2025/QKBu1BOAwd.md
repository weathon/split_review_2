## Summary

This paper proposes DRAFT, a framework that iteratively refines tool documentation for LLMs through a trial-and-error process with three phases: an Explorer generates diverse tool-use instances, an Analyzer suggests documentation improvements based on tool execution feedback, and a Rewriter updates the documentation. Two auxiliary mechanisms—diversity-promoting exploration and tool-adaptive termination—are introduced. Experiments on ToolBench and RestBench (TMDB, Spotify) with three LLMs (GPT-4o, GPT-4o-mini, Llama-3-70B) show that DRAFT-improved documentation yields higher task success rates than raw documentation, ReAct, DFSDT, and EasyTool.

## Strengths

1. **Consistent improvements across diverse settings.** Table 1 reports that DRAFT achieves the highest Correct Path Rate (CP%) and Win Rate (Win%) compared to all baselines across all three datasets (TMDB, Spotify, ToolBench) for all three LLMs tested. For example, on ToolBench with GPT-4o, DRAFT achieves 51% CP vs 45% for EasyTool and 37% for ReAct. These results are presented in a clear, well-organized table.

2. **Ablation confirms the value of both proposed mechanisms.** Table 2 shows that removing the diversity-promoting exploration strategy drops CP from 88% to 84% on TMDB, and removing the adaptive termination mechanism drops CP further to 80%. This provides direct evidence that both design choices contribute to the overall performance, even though the effect sizes are moderate.

3. **Human evaluation shows improved documentation quality.** Table 4 reports that human annotators rate DRAFT-refined documentation as more complete (40% vs 16% on RestBench), more concise (36% vs 20%), and more accurate (30% vs 0%) than the original documentation. This complements the automated metrics and speaks to the method's practical utility.

4. **Clear methodology and reproducible specification.** Algorithm 1 provides a precise specification of the iterative process with well-defined equations (Eq. 1-5). The three-phase design (Explorer, Analyzer, Rewriter) is clearly described, and the prompt templates are provided. Code is released.

## Weaknesses

### Fatal
None.

### Major

1. **The "robust cross-model generalization" claim partially outpaces the evidence.** The paper states this claim prominently in the abstract. Table 1 does show that documentation generated by a GPT-4o backbone improves performance on Llama-3-70B (e.g., CP from 41 to 53 on ToolBench), which is genuine cross-model evidence. However, the experiment using a different backbone (Llama-3-70B) is conducted on only one dataset (RestBench-TMDB) and presented as bar charts without numerical values (Figure 7). With only two backbones tested and one of them only on a single dataset, the claim of "robust" generalization is stronger than the evidence warrants. The paper would benefit from testing at least 2-3 diverse backbones across all datasets, or tempering the claim.

2. **No statistical characterization of results.** The paper does not report confidence intervals, standard deviations, or statistical significance tests for any of its main results. The improvements over baselines are modest (typically 2-10% in CP%). Without error bars, the reader cannot assess whether these differences are reliable or could be within the range of evaluation noise. This is a significant gap for a paper whose central evidence consists of numerical comparisons.

### Minor

3. **Win% metric relies on a ChatGPT-based evaluator, creating a potential confound.** The Win% comparisons are performed by a ChatGPT-based evaluator, and the documentation was generated using GPT-4o as the backbone. This raises the concern that the evaluator may prefer outputs aligned with GPT-model patterns rather than reflecting genuine documentation quality. The paper partially mitigates this by including Llama-3-70B in the evaluation and by reporting CP% (an objective path-matching metric), but the Win% results should be interpreted with this caveat in mind, and a robustness check with a different evaluator would strengthen the conclusions.

4. **Hyperparameters chosen without sensitivity analysis.** The similarity threshold φ=0.9, termination threshold τ=0.75, and max iterations=5 are set without any sensitivity study. The ablation for the termination mechanism only tests the extreme of removing it entirely (always running 5 iterations) rather than probing different τ values. The paper claims the termination mechanism prevents overfitting, but never demonstrates this with a controlled experiment varying τ or max iterations.

5. **Missing practical efficiency and convergence details.** The paper does not report how many exploration instances are generated per tool on average, the mean or median number of iterations before the termination mechanism fires, or any cost comparison (token usage, API calls) against EasyTool. These details are important for assessing the practical viability of the method, given that DRAFT requires multiple LLM calls per tool.

6. **Human evaluation's "0% accuracy for raw documentation" warrants explanation.** Table 4 reports that raw documentation never won on accuracy (0% on both RestBench and ToolBench). This is suspicious and suggests either sample selection bias (tools with known poor documentation were sampled) or evaluation criteria that inherently favored the longer/revised documentation. The paper should clarify the sampling procedure and report inter-annotator agreement.

## Novel Insights

None beyond the paper's own contributions. The key insight—that iteratively generating diverse tool-use experiences, analyzing execution feedback, and rewriting documentation can improve LLM tool use—is well-motivated but not surprising given prior work on self-correction and tool-use refinement (PLAY2PROMPT, self-reflection methods). The two auxiliary mechanisms (diversity constraint and adaptive termination) are reasonable engineering contributions that the ablation study confirms are helpful.

## Suggestions

1. Soften the "robust cross-model generalization" claim to acknowledge the limited backbone diversity, or add experiments with at least one more backbone (e.g., a smaller model like Llama-3-8B or Qwen2.5-7B) across all datasets.
2. Report confidence intervals or standard deviations for the main results (Table 1), ideally from multiple runs or bootstrapping.
3. Add a sensitivity analysis for φ and τ, or at minimum justify the chosen values with reference to the data.
4. Report practical details: average iterations per tool before termination, number of exploration instances generated, and a rough cost comparison against the baselines.
5. Clarify the human evaluation sampling procedure and report inter-annotator agreement.
